# Правила безопасной работы Codex с HOOKAH POS

## 1. Границы среды

- По умолчанию работаем только в локальной копии проекта.
- VPS, production, SSH и deploy не трогаем без отдельного прямого разрешения пользователя.
- Локальная проверка не считается серверным деплоем.

## 2. Перед началом работы

Всегда проверить:

```powershell
git status --short --branch
git branch -vv
git remote -v
```

Нужно определить текущую ветку, её upstream и наличие незакоммиченных изменений.

## 3. Перед merge, reset или публикацией

- Не выполнять `reset --hard`, `clean`, merge или rebase при незакоммиченных изменениях без локальной резервной точки.
- Резервировать изменения через именованный stash или отдельную ветку.
- Проверять состав резервной копии и не включать секреты в коммиты.
- Не смешивать в одном коммите несвязанные задачи, если это можно избежать.
- После объединения проверить diff и убедиться, что удалённые файлы действительно устарели.

## 4. Секреты

- Не коммитить `.env`, SSH private keys, токены, пароли и VPS-ключи.
- Такие файлы можно сохранять только локально и проверять через `git status` и `.gitignore`.
- В handoff и сообщениях передавать только имена переменных и расположение настроек, без значений секретов.

## 5. Проверка перед push

Минимальный порядок:

```powershell
node --check portal.js
node --check server.js
node scripts/sidebar-menu-audit-contract.mjs
node scripts/local-role-contract.mjs
git diff --check
git status --short --branch
```

Для изменений конкретного раздела запускаются его профильные контракты и локальная браузерная проверка.

## 6. Коммит и push

- Коммитить только после проверки diff и тестов.
- После push сверять `HEAD` с `origin/<branch>`.
- В отчёте указывать hash коммита, ветку, результаты проверок и отдельно писать, выполнялся ли deploy.

## 7. Deploy

- Deploy выполняется только после отдельного разрешения пользователя.
- Перед deploy проверять закреплённую схему адресов и портов в `PORTS.md`.
- Нельзя самостоятельно менять IP, порты, compose-проект или занимать порт, используемый другим сервисом.

## 8. Очистка локальных Docker-стендов

- До готовности общего выпуска финансового и зарплатного модулей локальные контейнеры и тома не удалять: сначала закончить разработку и проверки.
- Перед очисткой заново инвентаризировать `docker ps -a`, `docker compose ls --all`, порты, Compose project/service labels и все mount/volume каждого целевого контейнера. Не полагаться только на имя или видимый статус.
- Основной локальный проект `hookah-pos` и его PostgreSQL-том не удалять и не пересоздавать при очистке QA. Исходники функций находятся в рабочем дереве; QA-контейнеры содержат тестовые базы и иногда отдельный тестовый UI.
- Удалять только стенды, которые после завершения релевантных QA однозначно классифицированы как временные и больше не нужны. Перед удалением контейнера отдельно установить судьбу его тома; не удалять том автоматически и не считать остановленный контейнер ненужным.
- Не запускать широкие команды очистки (`docker system prune`, массовое удаление volumes или compose-проектов). Удаление выполнять точечно по проверенным именам контейнера/тома; сторонние Docker-проекты не трогать.
- Перед точечным удалением сверить целевой список и подтвердить, что в нём нет основного проекта, его БД, исходников или единственной нужной QA-базы. В итоговом отчёте перечислить сохранённые и удалённые объекты и затронутые QA-данные.
- После завершения финансовой и зарплатной частей и формирования выпуска выполнить такую инвентаризацию и предложить очистку; публикацию в GitHub и VPS проводить отдельными действиями по правилам разделов 6–7.
