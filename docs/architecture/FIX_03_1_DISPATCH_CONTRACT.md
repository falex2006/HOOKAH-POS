# FIX-03.1: передача и исполнение позиций заказа

08.10.2026. Контракт уточнён решением координатора: отдельная таблица исполнения, без изменения финансовых guards. Роли system_architect/backend/data/security; данные меняются только миграцией 099. FIX-01/02 и существующий dirty diff сохраняются.

## Основание

`schema.sql:507–514` уже содержит `order_items.station` и `status` (по умолчанию new). `db.js:71` отдаёт station/status строк заказа; для pricing snapshot station берётся из сохранённых product facts. `db.js:671–688` пока использует category AS station. Кнопки рабочего места отправляют статус всего заказа; handler `/api/orders/:id/status` не создаёт исполнение строк. `/api/tasks` - отдельные поручения с исполнителем, их жизненный цикл не связан с готовностью товарных строк. Дублировать каждую строку в tasks для этого пакета не нужно.

## Принятое решение: отдельное исполнение

`guard_pos_order_item_after_snapshot` запрещает обновления order_items после частичной оплаты. Его не ослабляем. `order_item_execution` содержит одну строку на order_item_id (PK/FK CASCADE), nullable station bar/hookah, status new/queued/in_progress/ready, dispatched_at/started_at/ready_at. Tenant и заказ определяются JOIN order_items → orders. Финансовые snapshots, legacy station/status и цены не изменяются.

Products получает nullable preparation_station bar/hookah независимо от category. При добавлении строки сервер копирует это направление в execution в той же транзакции; нельзя получать направление из текущего продукта при дальнейшей передаче. OrderRepository возвращает preparationStation, preparationStatus, preparationDispatchedAt, preparationStartedAt, preparationReadyAt вместе с существующими полями. Отсутствующая execution читается как new/null; сервер должен отличать отсутствующую legacy запись при мутации.

Миграция 099 replay-idempotent: создаёт таблицу/поле, переносит только активные заказы ON CONFLICT DO NOTHING. Только точные oi.station bar/hookah определяют направление, прочие NULL. Общий legacy ready → execution ready, in_progress → queued, open → new. Время исторической передачи не выдумывается. Закрытые исторические заказы не backfill-ятся. Новые оплаченные строки сохраняют execution и остаются в очереди до готовности.

## Операции

Dispatch активного заказа требует orders, открытой смены, station и обязательный непустой itemIds[]. Все строки должны принадлежать одному выбранному заказу/venue. Неразмеченная строка получает явно выбранное направление при первой передаче; уже заданную иную станцию переопределять нельзя. new → queued. Повтор для тех же переданных IDs безопасен и не захватывает новые строки. Для legacy queued/null требуется явный путь первичного назначения станции без сброса исполнения; его нельзя молча исключить из очереди.

Исполнитель своей станции выполняет queued → in_progress → ready. Запрос содержит желаемый status; тот же status идемпотентен, неверный переход 409. Нужны orders плюс bar_tasks/hookah_tasks или согласованный управленческий override. Чужая станция 403, чужой item/order/venue 404. Каждая операция блокирует родительский order до execution и проверяет актуальные права. Отмена исключает работу из очереди.

Очередь выводит queued/in_progress текущей станции, включая финансово closed заказы с незавершённым исполнением. Готовность такого заказа разрешена и не меняет orders.status/цены/платежи/склад. Исполнение не требует новой финансовой операции или повторного открытия смены. Для активного заказа общий ready допускается только когда все оставшиеся execution ready; новая строка снимает ready, не сбрасывая готовность старых. Старый endpoint общего ready не должен обходить построчную проверку.

Изменения количества/удаления уже переданной работы требуют явного ограничения: минимально отклонять их 409 и добавлять новую строку для новой работы; не терять поручение молча. Финансовые ограничения существующих endpoints остаются в силе. Передача/готовность не списывает ингредиенты повторно: списание остаётся в финансовом сценарии закрытия.

UI показывает отдельные направления, выбор new строк и «Передать»; у исполнителя отдельные «В работу»/«Готово». Это не универсальные /api/tasks. Успех отображается только после persisted ответа; reload и другой исполнитель видят ту же execution. Endpoint названия согласует координатор в API.md.

## Проверки приёмки

1. Смешанный заказ: бар + кальян, независимая передача, reload/второй сотрудник видит persisted очередь, бар ready не делает весь заказ готовым, обе станции ready дают общий ready активного заказа; оплаченный заказ сохраняет финансовый closed.
2. Повторные запросы и одновременная готовность: одно изменение; повтор dispatch не захватывает новые позиции.
3. Добавить после ready: новая работа видна, общий ready сброшен, прежние цены/готовность сохранены.
4. Бармен против кальянной строки и наоборот; сотрудник с отозванным orders; чужая точка/order/item; owner/manager override по согласованному helper.
5. Оплата/закрытие параллельно dispatch/ready/add: единая сериализация; нет возврата closed в in_progress и нет двойного списания ингредиентов. Отправка/готовность сама не списывает склад, если списание остаётся на финальной оплате.
6. Существующие legacy станции, отсутствие направления и оплаченные snapshots: ясное состояние, отсутствие необоснованного backfill, цена и история неизменны.

Релиз требует миграционного preflight, совместимости нового nullable поля со старым приложением, воспроизводимого PG QA и Edge обоих исполнителей. Не публиковать в этом пакете без общего workflow.


`expectedVenueId` — дополнительная необязательная защита dispatch/preparation: UI передаёт зафиксированную точку; если поле задано и не совпадает с активной точкой, сервер возвращает409. Отсутствие поля не отменяет обязательные tenant/order/item проверки.
