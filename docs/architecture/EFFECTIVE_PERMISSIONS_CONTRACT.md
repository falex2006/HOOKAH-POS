# Контракт эффективных прав, версия 1

Дата: 08.10.2026. Область FIX-01: backend resolver, login/session/profile. Frontend, маршруты и настройка меню принимаются отдельно в FIX-02. Этот документ фиксирует политику; факт прохождения runtime QA хранится в отчёте соответствующего пакета.

## Источники и значения

| Источник | Отсутствует | Явно пустой список |
|---|---|---|
| Базовая роль | Неизвестная роль не получает прав | Точный пустой набор |
| Персональные scopes | Наследование | Наследование согласно миграции 007 |
| Активная custom role | Используются персональные или базовые | Нет выбранных направлений |
| System override | Нет системного потолка | Никаких бизнес-направлений |

Наличие custom role определяется `customRoleActive=true` от успешного JOIN активной роли того же organization/venue, а не длиной массива или наличием произвольного ID. Наличие system override определяется `rolePermissionOverrideActive=true` от строки в БД. Null нормализуется в пустой массив только после сохранения признака наличия источника.

На записи POST staff / PATCH staff/:id/profile персональное `permissionScopes:null` означает сброс к наследованию и сохраняется как `[]` (колонка NOT NULL). Это действие остаётся owner-only. System/custom `permissionScopes:null` отклоняется HTTP 400; для явного запрета используется `[]`.

## Алгоритм

1. Owner и platform_owner сохраняют точный защищённый базовый набор. Tenant override не изменяет владельца платформы или заведения.
2. При отсутствии custom, непустых персональных scopes и system override сохраняется точный `rolePermissions`. Значения редактора `systemRoleScopeDefaults` не подменяют фактические defaults.
3. Активная custom role выбирается вместо персональных scopes. Иначе выбираются непустые персональные scopes.
4. Если есть выбранный набор и system override, результат равен пересечению развёрнутых permissions. System override является потолком, а не ещё одним источником расширения.
5. Если выбранного набора нет, используется system override. Без override действует п. 2.
6. `bar_tasks`/`hookah_tasks` добавляются только своей базовой роли и при наличии `orders`; `diagnostics` сохраняется только базовым обладателям с итоговым `settings`. Это предотвращает обход запрета через OR-проверки API.

Пересечение вычисляется после раскрытия scopes: `finance` и `finance_read` могут пересекаться по чтению; `inventory` и `inventory_categories` по `inventory_read`. Простое пересечение названий scopes неверно. Никакие поля permissions от клиента не являются источником серверной авторизации.

## Объяснение результата

Resolver возвращает `permissions` и `policy`: `version=1`, `source` (`base`, `protected`, `system`, `custom`, `personal`), `systemRoleCeilingActive`, `blockedPermissions`. Последнее перечисляет capabilities выбранного профиля, исключённые системным потолком. `source=custom` не означает, что все custom права разрешены: при активном потолке клиент обязан показать ограничение.

`user.workspacePermissions` и верхнеуровневые `permissions` login/session должны совпадать. `user.permissionPolicy` и верхнеуровневая policy дают одинаковое объяснение. Profile содержит тот же расчёт для роли сотрудника в его venue. Session использует активный venue сессии; сравнение profile/session корректно при одинаковом venue. Переключение филиала требует отдельной приёмки.

## Сквозной контракт

| UI/операция | API и сохранение | Разрешение | Повторное чтение / QA |
|---|---|---|---|
| Настройка системной роли | PATCH staff/system-roles/:role, строка override | Владелец; owner override запрещён | Session того же токена немедленно применяет потолок и пустой список |
| Создать/изменить custom role | POST/PATCH staff/roles, active scopes | Владелец | Пустая custom role не превращается в базовую; проверка profile/session |
| Назначить custom или личные scopes | PATCH staff/:id/profile | Существующие owner/target guards | Чужая/архивная роль отклоняется; собственная действует с тем же токеном |
| Вход | POST login; PostgreSQL auth session | Реальные credentials и membership | permissions + workspacePermissions совпадают со следующим session |
| Открытие рабочего места | GET session | Валидная активная сессия | UI получает актуальные permissions до рендера; реализация FIX-02 |
| Просмотр карточки | GET staff/:id/profile | staff/staff_view либо собственная карточка | Единый resolver; персональные данные остаются под прежними guards |
| Trusted PIN | Существующий endpoint разблокировки | Валидный trusted context и PIN | Использует текущий req.user, не старую копию прав из памяти |

## Ошибки и совместимость

Ошибка загрузки joined источников не означает отсутствие override. Login возвращает ошибку доступности, session не авторизует пользователя, profile возвращает `503 staff_profile_permissions_unavailable`. Старый fallback, объявлявший базовые права при ошибке SQL, запрещён. Это осознанное изменение поведения устаревших схем: миграции должны быть применены.

Memory mode обновляет роль и персональные scopes из существующего staff на запрос; он не заменяет PostgreSQL-проверку custom/system. Legacy personal `[]` продолжает наследовать права. Политика может сузить существующие настройки system+custom/personal до пересечения; автоматического повышения доступа ради исправления интерфейса нет.

FIX-02 должен устранить локальное объединение с базовыми правами, объяснить потолок и отличить пустую настройку от наследования. До этого backend корректность не означает готовность интерфейса и не закрывает ROLE-03/04.
