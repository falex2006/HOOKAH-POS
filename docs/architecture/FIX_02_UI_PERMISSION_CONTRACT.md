# FIX-02: актуальные права в интерфейсе

08.10.2026. Владельцы контракта: system_architect/security, визуальные требования design_lead. Область: portal/login и рабочий app; backend-политика уже задана EFFECTIVE_PERMISSIONS_CONTRACT.md. Product changes этим документом не выполняются.

## Общий каркас

Сохранить SITE_TREE.md: канонические маршруты, независимую прокрутку, порядок групп, максимум одну открытую административную группу, активность маршрута и сохранение раскрытия отдельно по пользователю/venue. Проверка прав управляет доступностью элементов, а не создаёт другое дерево для каждой страницы. Верхняя панель сохраняет название заведения, раздел, состояние смены и действия профиля.

## Инициализация

До чтения cached role для редиректов, построения навигации, route guard, renderer и обработчиков, захватывающих локальные разрешения, получить GET /api/session. Нужны user и массив permissions. Единственный набор business permissions - ответ сервера. Локальный user пригоден для косметического placeholder, но не для разрешения или запрета действия. Не объединять permissions с базовым role map или индивидуальными scopes. UI-only dashboard можно разрешить для общей оболочки; это не разрешение на подстраницы.

Практический ограниченный вариант: единый async bootstrap вокруг существующей инициализации portal. Init выполняется ровно один раз после успешной сессии. При ошибке показывается отдельный блок «Не удалось проверить доступ» с повтором и входом; защищённые действия/навигация не доступны. Валидная сессия без прав означает «Нет доступа», а не ошибку соединения и не бесконечный redirect.

Static demo, если сохраняется, имеет явную отдельную ветку. Его role map не должен быть fallback реальной авторизации.

## Обновление без выхода из учётки

Нужны повторная проверка при возвращении фокуса/видимости и ограниченный таймер активной страницы. Deduplicate запросы, сравнивать подпись userId/venueId/role/отсортированные permissions/policy. На реальное изменение полномочий обновить весь защищённый UI; если старые renderer захватили booleans, безопаснее однократная перезагрузка после принятия новой подписи, чем неполная мутация Set. Не создавать циклы reload и не отправлять повторно формы.

При сетевой ошибке скрыть/заблокировать защищённые действия и показать retry, сохранив по возможности черновик. Нельзя сохранить старое разрешение как fallback. Сервер продолжает проверять каждый запрос, даже до клиентского обновления. Несохранённый ввод и конкурентный платёж не должны автоматически отправляться заново.

## Маршруты и действия

| Экран/действие | Контракт |
|---|---|
| Гости /clients | ANY orders, staff, staff_view; одинаково ссылка/guard/API GET clients |
| Склад | Чтение inventory_read; изменения только inventory; настройки категорий отдельно inventory_categories согласно серверным guards |
| Заказы | orders; возвраты чтение finance_read/finance плюс нужный доступ к источникам, создание finance |
| Брони | reservations; проверка до прежнего общего route guard |
| Финансы | Точное соответствие чтению/записи серверного endpoint, без расширения finance_read в finance |
| /admin#staff | staff/staff_view; write дополнительно staff_manage и серверные ограничения роли/цели |
| /admin#permissions | Собственно редакторы системных/custom ролей доступны owner; не обещать всем staff_manage возможность изменения ролей |
| /admin settings hashes | Проверить settings и специальные owner/admin ограничения действия |
| /admin#diagnostics | Серверный набор diagnostics/settings по endpoint; фиксированное имя роли не заменяет permission |

Проверить hashchange и прямой URL, включая уже открытый /admin. Разрешение общей dashboard-оболочки не должно пропускать кадровые/настроечные render и запросы. Ссылка и renderer не должны предъявлять разные требования. Role-specific ограничения сервера остаются явными и не отменяются scope.

## Объяснение владельцу

- Персональные scopes: «Пустой список - наследовать права роли. Если назначена пользовательская роль, используются её права».
- Custom scopes: «Пустой список - нет выбранных направлений. Системная настройка роли может дополнительно ограничивать доступ».
- System scopes: «Доступный максимум для сотрудников этой должности. Пустой список отключает направления».
- Итог показывать по workspacePermissions/permissionPolicy сервера, а не по галочкам. Если systemRoleCeilingActive и blockedPermissions непусты, явно сообщить, что выбранные права ограничены системной ролью.
- После сохранения повторно прочитать данные. Не показывать «всё доступно» только из-за успешного PATCH. Ошибка не скрывается под success toast.

Нужны читаемые loading/error/empty/denied состояния в текущей светлой/тёмной теме, без скачка боковой панели. Адаптация проверяется на ноутбуке 1366×768 и desktop 1920×1080; Fold вне текущего пакета.

## Приёмка

Owner меняет system/custom/personal → открытая учётка сотрудника обновляет доступ → разрешённые действия работают, запрещённые не отображаются и отвергаются API. Проверить admin, manager, bartender, hookah_master; пустой system/custom, legacy personal пустой, grants/revokes, profile/login/session parity, cached role устарел, две вкладки, фокус, reload, ошибка сессии. Проверить прямой и меню-переход к гостям без выдачи кадрового доступа. Визуально подтвердить общую навигацию и шапку минимум на рабочем экране, гостях, складе и административной странице.
