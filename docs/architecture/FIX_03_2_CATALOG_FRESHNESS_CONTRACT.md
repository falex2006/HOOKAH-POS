# FIX-03.2: актуальность каталога на рабочем месте

08.10.2026 · Контракт архитектора для сквозной правки рабочего места. Область — каталог продажи для POS и добавление позиции в заказ. Навигация и верхняя панель не меняются.

## Диагноз и основания

Дефект D02 подтверждён в синтетической Edge-сессии: кальянщик загрузил товар за 200 ₽; владелец отдельной авторизованной сессией изменил цену на 275 ₽; при повторном открытии каталог продолжал показывать 200 ₽, а сервер добавил строку за 275 ₽. Уже существующая строка заказа сохранила 200 ₽. См. docs/qa/AUDIT_2026_10_08_BROWSER_FINAL.md, раздел D02.

Причина — каталог хранится в локальном массиве и загружается только при получении сессии или при ошибке загрузки. Открытие каталога не вызывает обновление (app.js:440–446). При этом добавление заказа уже использует возвращённую сервером цену строки (app.js:465), а сервер читает текущую цену только активного товара текущего заведения (server.js:6063–6100). Серверный список также фильтрует venue_id и is_active=true (db.js:668–673).

В итоговом аудите отмечено, что самостоятельное архивирование и создание позиции нужно проверить в этом этапе. Полное браузерное подтверждение редактирования товара через интерфейс владельца и архивации здесь не заявляется; исходное воспроизведение смены цены использовало авторизованный API владельца.

## Контракт актуальности

1. **Источник:** GET /api/products по действующей авторизованной сессии и активному заведению. POS передаёт активный идентификатор заведения как необязательный query-параметр expectedVenueId; если он указан и не совпадает с заведением, определённым сервером для запроса, вернуть 409 и не выдавать каталог. Проверка на клиенте по venueId и поколению сессии всё равно обязательна, чтобы отбросить ответы, пришедшие после переключения контекста. В ответе только активные товары этого заведения. Не считать клиентский массив источником цены или доступности.
2. **Обновление:** загрузить каталог при каждом открытии. Пока каталог открыт и вкладка видима — обновлять раз в 60 секунд. При возврате фокуса или переходе вкладки из скрытой в видимую — обновить немедленно, если каталог открыт. События открытия/focus/visibility и таймер координировать single-flight; закрытие каталога, потеря доступа или скрытие вкладки приостанавливают периодический опрос. Не опрашивать каталог в фоне, когда пользователь им не пользуется.
3. **HTTP-кэш:** запрос каталога отправлять с cache: 'no-store'; ответ API должен запрещать хранение через Cache-Control: no-store. Это исключает повторное использование устаревшего браузерного или промежуточного HTTP-кэша между обновлениями.
4. **Защита от устаревшего ответа:** до запроса сохранить поколение доступа/сессии, идентификатор активного заведения (POS floorVenueId) и поколение запроса каталога. Применять ответ только если все значения по-прежнему совпадают, пользователь сохраняет floor и orders, а каталог открыт. Изменение пользователя, прав, сессии или заведения инвалидирует запрос и очищает данные прежнего контекста. Более ранний ответ никогда не перезаписывает результат более позднего запроса.
5. **Ошибка — закрытый отказ:** после сетевой ошибки, тайм-аута, 403 или неверного контекста запретить добавление товара из неактуального списка. Если сохранён прежний список, явно пометить его как устаревший и отключить товары; показать повтор загрузки. При отсутствии прежнего списка показать ошибку с повтором. Успешная загрузка снимает предупреждение и возвращает доступные товары. Пустой ответ показать как пустой каталог, не как ошибку.
6. **Поиск и заказ:** обновление не очищает текст поиска и не закрывает каталог. Фильтр поиска повторно применяется к свежему списку. Уже открытый заказ, текущий стол и строки заказа не заменяются ответом каталога. Архивирование товара убирает его из нового выбора, но не удаляет исторические строки.
7. **Цена и история:** при добавлении отображать фактические name и unitPrice, вернувшиеся от POST /api/orders/:orderId/items; при расхождении со значением на кнопке синхронизировать цену каталога при следующем успешном GET. Никогда не пересчитывать и не переписывать уже добавленные строки при смене цены в справочнике. Серверная проверка активности и цены остаётся окончательной: деактивированный товар отклоняется product_not_found.
8. **Границы обновления:** создать/изменить/архивировать товар и изменить изображение через API панели каталога отражается при следующем GET рабочего места. В этом этапе не менять рецептуры, остатки, складские категории, списание или цены исторических позиций. Обновление автоматически при следующем открытии достаточно для изменений из другой сессии; отдельная система событий и постоянный фоновый polling не требуются.

## Изменяемая область и критерии приёмки

Ожидаемые файлы реализации: app.js (каталог, состояния загрузки, актуализация, защита ответа и рендер цены), server.js (ответ GET с запретом HTTP-кэширования, только если общий json() не задаёт нужную политику), тесты каталога, QA-отчёт. portal.js меняется только если сквозная проверка обнаружит, что сохранённая операция меню не обновляет собственный список. Обновление dist/ и опубликованных ревизий — только через установленный скрипт синхронизации проекта. Боковая навигация, маршруты и верхняя панель не затрагиваются.

Приёмка:

1. Два авторизованных контекста одной точки: владелец меняет цену 200→275; POS после закрытия и повторного открытия (без повторного входа) показывает 275. При добавлении сервер возвращает 275; существующая строка 200 остаётся 200 после reload.
2. Созданная позиция появляется после открытия/обновления; архивированная исчезает и не добавляется. Проверить бармена и кальянщика. Интерфейс владельца для создания/архивации должен быть проверен браузером, если он включён в заявленный результат.
3. Пока каталог открыт — видимый опрос 60 секунд и обновление при возвращении вкладки; при закрытом каталоге/скрытой вкладке таймер не делает запросов. Открытый заказ и поиск сохраняются.
4. Ошибка сети/403 не позволяет продавать по stale цене; повтор возвращает свежий список. Ответ старого запроса после смены сессии/заведения/прав или после более нового запроса игнорируется.
5. Нет изменений исторической цены, платежей, рецептур, ингредиентов или складских движений. Tenant isolation проверена серверным чтением и добавлением.

Исполнительный backend/frontend контракт можно уточнить при реализации, но требования fail-closed, интервал только для видимого открытого меню, no-store, stale-response guard и сохранение поиска/заказа остаются обязательными. Полный аудит ролей и разрешений FIX-01 остаётся источником прав; этот контракт не расширяет доступ.
