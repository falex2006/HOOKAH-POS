## Ожидаемый доступ и отдельные границы

Ожидания CSV взяты из default **real-session** профиля принятой матрицы. До прохода снять обезличенный `/api/session`: роль, permissions, tenant/venue и отсутствие пользовательских/системных overrides. Кастомная роль или персональные права требуют отдельного указания фактических permissions и согласования ожидания, не скрытой замены default. `platform_owner` проверяется в отдельной SaaS-сессии, остальные — в tenant-сессиях. Публичный `/login` представлен для всех пяти целевых ролей; значение PUBLIC не доказывает, что авторизованная сессия останется на форме, поэтому фиксировать redirect/logout-free сценарий в отдельном временном browser context.

| Код CSV | Ожидание, требующее доказательства |
|---|---|
| ALLOW | Разрешён вход; действия и поля требуют собственных прав/API |
| READ | Manager: чтение склада/финансов; нет `inventory`/`finance` для записи |
| SHELL | `/admin` доступен tenant-роли; каждый hash имеет отдельный gate |
| PUBLIC | Публичная форма авторизации; не считать отдельным tenant-бизнес-доступом |
| OWN_TODAY | Hookah master/bartender: собственные оплаты текущего дня, не общий финансовый реестр |
| OWN_TASKS | Только свои задачи и доступные изменения статуса; без кадрового управления |
| SHELL_API_DENIED | Notifications сотрудников: shell доступен, события API запрещены |
| PAYROLL_API_DENIED | Manager: финансовая оболочка по `finance_read`; payroll API запрещён без `finance` |
| OWN_TODAY_NO_PAYROLL | Сотрудник по payroll hash получает собственные оплаты; payroll workspace отсутствует |
| DENY | Маршрут/hash запрещён при default profile; отсутствие доступа не равно отсутствию данных |

Manager в `#company` может читать настройки, но изменение идентичности заведения ему запрещено. `#permissions` — только owner. `#diagnostics` для manager запрещён. `#help` — локальная справка/feedback; не заявлять отправку в поддержку. У разрешённых страниц запрещённые кнопки/поля проверять в baseline и keyboard, фиксируя локальные границы из ROUTE_ROLE_MATRIX §7. Наличие payroll hash или notifications shell не является доказательством разрешённого API.

## Что именно снимать

| Состояние | Минимальное доказательство и различение |
|---|---|
| baseline | Прямой URL и переход из меню, конечный URL/hash/view, выбранный пункт, оболочка, доступные/запрещённые действия; reload и сохранение контекста без записи бизнеса |
| empty | Пустые временные данные и отдельно no-results при фильтре; не подменять пустоту ошибкой/403/неподготовленной БД |
| loading | Контролируемый pending реального чтения в тестовой среде: placeholder, стабильность геометрии, доступность состояния, повтор submit на формах; описать механизм задержки |
| error | Раздельно read/service error и invalid/failed action где есть форма; сообщение, retry, сохранённый ввод/фильтр. 401/403 сюда не прятать |
| long-content | Искусственные длинные названия/ФИО/суммы/даты и много строк; overflow контейнера, переносы, доступ к действиям, скролл и footer; данные только временные |
| keyboard-focus | Tab/Shift+Tab, видимый фокус, доступные имена; клавиатурный dropdown/tab, Escape, dialog focus trap/возврат фокуса, PIN/top layer где применимо. Пассивным badge не добавлять tabindex |

Для DENY baseline снять ожидаемый отказ/redirect в валидной разрешённой для данной роли сессии, исключить leakage/появление бизнес-данных; keyboard пройти доступные элементы отказа/возврата. Четыре состояния запрещённого бизнес-содержимого допускают N/A только с этим доказательством и причиной. Для SHELL_API_DENIED, PAYROLL_API_DENIED и OWN_TODAY_NO_PAYROLL состояния относятся к реально доступной оболочке/личным оплатам; недоступный вложенный API/workspace объясняется отдельно, поэтому строки не удаляются.

При диагностике результата писать отдельно: **DENIED_EXPECTED** (подтверждённый policy/403 при валидной сессии), **AUTH_FAILURE** (401, истёкшая/отсутствующая сессия, login redirect по этой причине), **SERVICE_FAILURE** (5xx/timeout/недоступная БД/зависимость), **ROUTE_FAILURE** (404/неверный hash/asset), **VISUAL_DEFECT**, **BLOCKED_ENV**. Разрешённый маршрут, открывшийся экраном ошибки сервиса, не получает PASS визуального baseline содержимого. Запрет действия при доступной странице отмечать отдельно от запрета page gate.

Две темы обязательны для поддерживаемых CRM/POS поверхностей. По EX-07 login/PIN/platform имеют собственные поверхности: если второй режим отсутствует, `UNSUPPORTED_THEME` допустим только после подтверждения исходником и фактической UI-проверкой, с причиной и одобрением architect/design. Отсутствующий toggle, ошибка переключения или неполные light overrides не являются достаточной причиной автоматически убрать light из покрытия. Непроверенная тема остаётся UNCHECKED/BLOCKED, дефект поддерживаемой темы — FAIL.

## Связь с каталогом и измерения

Это базовая фиксация существующих дефектов; несоблюдение целевых размеров не требует продуктовой правки в UI-01.2. Использовать IDs C01–C18, не копировать общий каталог. Для каждого фактически присутствующего семейства указать страницу/элемент, screenshot и состояние. У component N/A должна быть предметная причина (например, нет таблицы в auth surface).

Для каждого доступного shell/frame/theme/viewport измерить C01: sidebar width, header height, content offset, scroll bounds, активный пункт, порядок/доступность действий. Для C03–C06: hit area, высоту/ширину, font/line-height, отступы, focus ring, текст/поверхность/границу и фактический contrast pair. Для C09/C10: row/header height, минимальную ширину и локальный overflow; staff table 5 колонок и сохранение view/scale 1–4. Для C11/C12/C18: rendered/max width/height, sticky header/footer, z-index/top layer, черновик и возврат фокуса. C15/C16: читаемость суммы/статуса/времени и единиц/периода. C17: фирменный эффект, reduced-motion и cursor fallback. Целевые параметры берутся из STANDARD/каталога; CSS declaration сама по себе не считается замером.

## Доказательства и gate приёмки

Координатор хранит manifest доказательств: case IDs CSV, дата, временная роль, обезличенные permissions/tenant, среда и сборка, requested/final URL, actual theme, реальные размеры, fixture/state trigger, screenshot path, DOM/computed measurements, network outcome при необходимости и defect ID/владелец. Пароли, cookies, токены и production-содержимое в evidence не сохраняются.

Одна фотография может покрывать несколько идентичных строк только при явной ссылке на case IDs и объяснении одинакового отображения/actual viewport. Нельзя переносить permissions между ролями по сходству экрана. Для статических разделов без async/data региона N/A конкретного состояния возможен после описания отсутствующего региона и ссылки на исходник/снимок, а не по общему предположению.

Пакет UI-01.2 принят, когда все 6 480 строк имеют фактический исход: CHECKED с evidence/замерами и дефектами, обоснованный N/A или явный BLOCKED с точным недостающим условием; каждая из 180 пар и каждый поддерживаемый viewport/theme имеют baseline+keyboard доказательства. Статус BLOCKED документирует непроверенную часть и **не закрывает полный визуальный критерий**. FAIL существующего дизайна может входить в честную принятую базу с воспроизводимостью и владельцем, но не объявляется исправленным. Приёмка базы требует полноты наблюдений, не выдуманного отсутствия дефектов.

На момент подготовки: 6 480 UNCHECKED, 0 runtime PASS, фактический viewport неизвестен; нужны изолированная auth+БД среда, пять временных аккаунтов с defaults, empty/long fixtures, безопасный механизм pending/error, браузерные скриншоты/замеры и подтверждение тем отдельного SaaS/auth контура. Финальную границу доступов утверждает system_architect, визуальную — design_lead, полноту evidence — QA/координатор. Следующий UI-подэтап автоматически не начинается.
