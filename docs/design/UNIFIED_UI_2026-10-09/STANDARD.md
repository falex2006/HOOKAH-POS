# Единый стандарт UI — контракт 1.0

Версия **UI contract 1.0 · 2026-10-09**, UI-01.1. **Принят как документальный контракт и направление миграции**, с уточнениями D07/D08 ниже; это не утверждение о внедрении или визуальной приёмке продукта. Владелец — `design_lead`; shell/маршруты/права — `system_architect`; реализация — `frontend_engineer`, проверка — `qa_engineer`/`visual_auditor`.

Источники одной редакции: [правила страниц](../../../VISUAL_PAGE_RULES.md), [токены](../../../DESIGN_TOKENS.md), [каталог компонентов](COMPONENT_CATALOG.md), [исключения](EXCEPTIONS.md), [route×role](ROUTE_ROLE_MATRIX.md) и канонические `SITE_TREE.md`/`site-map.json`. Этот файл задаёт общие принципы и контракт окна; значения токенов принадлежат DESIGN_TOKENS, предметное поведение — VISUAL_PAGE_RULES, отклонения — EXCEPTIONS. При расхождении исправляется вся затронутая часть редакции, без выбора удобного документа. AUDIT — историческое основание, не текущий source of truth.

Числа геометрии и новые hex остаются **кандидатами для реализации**: UI-01.2 снимает исходники, последующие профильные подэтапы проверяют эталоны. UI-01.1 не принимал скриншоты, итоговый контраст, высоты или widths. Текущая реализация отмечена отдельно в каталоге; отсутствующий общий компонент нельзя считать существующим.

## 1. Общая композиция

### Обязательное пожелание пользователя: без шаблонного нейросетевого оформления

Дизайн должен выглядеть как продуманный рабочий инструмент конкретного кальянного заведения. Сохраняем характер HOOKAH POS и решения, которые сотрудникам уже удобны. Этот критерий действует для всех этапов плана.

- Не добавлять ради украшения стеклянные панели, разноцветный неон, градиенты на каждой карточке, чрезмерные скругления и декоративные иконки.
- Не раздувать страницы огромными заголовками, приветственными баннерами, пустыми карточками показателей и повторяющимися пояснениями. Пространство нужно столам, заказам и рабочим данным.
- Каждое выделение имеет смысл: статус, главное действие, выбор или ошибка. Фирменный градиент, согласованный курсор и мягкая пульсация допустимы в своих оговорённых местах; не распространять их на весь интерфейс.
- Использовать предметные детали: оборудование стола, время визита, статус приготовления, состав заказа. Не подменять их абстрактными декоративными блоками из шаблонного dashboard.
- Писать короткие рабочие подписи. Не добавлять рекламные фразы вроде «Управляйте бизнесом с лёгкостью» внутрь служебных экранов.
- До массового переноса страниц показать эталоны зала, списка и формы на реальных по длине данных. Оценивать иерархию, читаемость, плотность и число действий; одной визуальной эффектности недостаточно.

Критерий приёмки: сотрудник сразу находит нужный стол, статус и действие; оформление последовательно и узнаваемо, декоративные решения не мешают работе. Каждый новый декоративный элемент должен иметь объяснимое назначение. Эти требования включаются в задания и дизайн-ревью, а не остаются пожеланием в переписке.

Сохраняем Manrope, тёмную и светлую темы CRM/POS и красно-оранжевый брендовый акцент. Авторизация и платформа сохраняют существующие поверхности; новый переключатель для них не вводится этим контрактом. Не добавляем новый визуальный стиль каждому модулю. Владелец видит управленческие данные, сотрудник — действия своей работы; общий язык компонентов одинаковый.

Типовой экран: один заголовок → короткое пояснение при необходимости → основные действия и фильтры → рабочие данные. Один доминирующий CTA для основного действия. Если заголовок уже есть в шапке, не повторять его огромным баннером без причины.

Страница списка не должна одновременно показывать пустой постоянный редактор и кнопку открытия того же редактора. Создание — по кнопке в окне, кроме случаев, где постоянная панель нужна для частой работы: например, выбранный заказ в POS. Это исключение закрепить явно.

## 2. Токены

| Группа | Предложение |
|---|---|
| Поверхности | Семантические `page`, `panel`, `raised`, `input`, `overlay`; отдельная карта для каждой поддерживаемой темы |
| Текст | `primary`, `secondary`, `muted`, `on-action`, `link`; dark link сейчас коралловый `#ffb08f`, исторический голубой отменён; не задавать новые hex в отдельных страницах |
| Статусы | success — мятный; warning/бронь — янтарный; danger — розово-красный; neutral — серый. Цвет всегда сопровождается текстом/значком |
| Акцент | Фирменный градиент в согласованных главном действии/активной навигации и бренде; вторичные кнопки спокойные; контраст текста требует замера, см. EX-05 |
| Отступы | 4 / 8 / 12 / 16 / 24 / 32px; между секциями 24px, внутри форм 12–16px |
| Радиусы | 8px мелкие элементы, 12px контролы, 16px панели/окна; pill только для статусов |
| Поля и кнопки | Базовая высота 44px; крупный CTA 48px; область нажатия иконки не меньше 44×44px |
| Иконки | Один SVG-набор, одна толщина линий, 18px в shell; 16/20px по назначению; не заменять системные иконки случайными emoji |
| Шрифт | Основной 14–16px, вторичный 12–14px; заголовок страницы 24–28px, панели 18–22px; столы по плотности, без обрезания названия |
| Числа | Табличные цифры, единый ru-RU формат; деньги со знаком ₽; время за столом HH:MM с доступным пояснением |
| Контраст | Целевые критерии: обычный текст ≥4,5:1; значимые границы, иконки и focus ≥3:1; измерять обе темы |

Не назначать одинаковую высоту каждому блоку. Таблица остатков, плитка стола и редактор заказа решают разные задачи. Компактность обеспечивается сокращением лишних баннеров/отступов, а не нечитаемым шрифтом.

Тёмные базовые оттенки можно сохранить из текущего проекта; light theme должна иметь собственные семантические значения. Нельзя считать любой старый цвет правильным без замера контраста.

## 3. Оболочка и плотность

Предлагаемый desktop shell сотрудников: sidebar 210px, header 68px; согласовать по реальным ограничениям. Для владельца допустим более широкий sidebar, но он одинаков между его страницами. `/platform` сохраняет отдельный состав навигации.

Проверяем 1366×768 и 1920×1080 при обычном масштабе браузера, дополнительно фактический рабочий viewport сотрудника, в обеих поддерживаемых темах. Ни имя, ни часы, ни смена не должны перекрывать действия. Длинные подписи имеют понятный перенос/tooltip, не теряют смысл. Galaxy Fold — отдельный UI-10.1 после UI-09.3 и отдельного запроса; обычные регрессии существующей узкой раскладки фиксируются по затронутому сценарию, без объявления полной mobile-приёмки.

Плотность зала хранится для пользователя и точки. Список может прокручиваться, но основные действия и контекст не исчезают. Не обещать уместить произвольное число столов в любом окне: при ограничении размера сохраняем читаемость и предсказуемую прокрутку.

## 4. Компоненты и состояния

Для интерактивных компонентов задать применимые default, hover, focus-visible, active/selected, disabled, pending и error. У пассивного badge нет искусственного hover/focus, у checkbox есть checked/indeterminate. Точная матрица — в COMPONENT_CATALOG. Loading, empty, denied и error — разные состояния. Не показывать отказ в доступе пока ещё проверяются права.

Ошибка поля остаётся рядом с ним до исправления. Ошибка сохранения остаётся в форме и не очищает введённое. Короткое успешное действие допускает toast 4–6с с live region; критическая ошибка не исчезает автоматически. Колокольчик системных уведомлений остаётся отдельным механизмом.

Таблицы: компактная обычная и операционная с ограниченной областью скролла. Заголовки, суммы, действия и сортировка согласованы; не прятать финансовые колонки ради декоративной компактности. Существующие карточки узкого `/orders` сохраняются. `/admin#staff` хранит пользовательский вид и размер плиток, таблица сохраняет колонки с локальной прокруткой; «Список» — явная альтернатива. Новые mobile-варианты — поздняя работа, без универсального автоматического превращения всех таблиц.

## 5. Контракт окна

Размерный контракт: small 440px для короткого подтверждения; medium 640px для формы; large 880px для составного редактора. В UI-04.1 medium внедрён для одного пилота; UI-04.2 переносит четыре ordinary редактора и трёхшаговую бронь в medium. Small/large остаются эталонными вариантами для последующих миграций. Фактическая ширина — не больше `viewport - 32px`, высота — не больше `100dvh - 48px`, с учётом safe-area. Заголовок/закрытие и footer действий остаются доступны, прокручивается содержимое. UI-04.2 закрывает EX-01 только для прежней геометрии брони 560px/скролла всего dialog: shared 640px, закреплённые head/footer и scroll body подтверждены. Финансовые сценарии и PIN этим закрытием не охватываются.

Обязательные свойства общей оболочки:

1. Доступное имя, начальный фокус, удержание Tab внутри, inert фона, блокировка фонового скролла.
2. Возврат фокуса инициатору или документированному fallback после rerender.
3. Escape сначала закрывает раскрытый select; затем окно по его политике.
4. Backdrop не закрывает окно случайно после drag изнутри.
5. Явные параметры будущей оболочки: `size`, `draftPolicy`, `pendingClosePolicy`, `initialFocus`, `returnFocus`, `onClose`; это спецификация, не существующий JS API. Бизнес-расчёты остаются в доменном модуле.
6. Простая чистая форма может закрываться сразу; изменённая форма сохраняет черновик или спрашивает об утрате по утверждённому контракту. Оплата/проведение имеют собственную политику ожидания.
7. Защита от повторной отправки, устаревшего ответа и смены точки/роли сохраняется. Закрыть окно не означает отменить уже отправленный запрос.

Native dialog был первоначальным кандидатом; выбор UI-04.1 после локального PIN/top-layer эксперимента — custom overlay, с ограничениями ниже. Native/mixed-window интеграция пересматривается в UI-04.3. Не переписывать все окна одновременно. Первая миграция — простая нефинансовая форма.

| Сценарий | `draftPolicy` | `pendingClosePolicy` | Фокус/выход |
|---|---|---|---|
| Короткое подтверждение | Нет полей; результат только после ответа | Блокировать закрытие/повтор после отправки | Начально безопасное действие; вернуть инициатору |
| Простая форма | Сохранить ввод при ошибке; при выходе явно preserve либо confirm-discard | Явно выбранная доменная политика; без молчаливой потери результата | Первое поле/ошибка, после выхода инициатор или заголовок списка |
| Бронь (UI-04.2) | `preserve`: ввод/шаг остаются в припаркованном DOM текущего render; явный переход в другую редакцию/New и успех имеют сбросы; смена verified контекста очищает | `block`: submit/поля/шаги/закрытие до известного результата | Select Escape первым; инициатор/стабильная CTA, после GET readback возврат только в текущем контексте без перехвата нового окна |
| Оплата/приход/возврат | Домен хранит сумму, идентификатор и итог; закрытие не откатывает запрос | Доменно определённая блокировка до известного результата | Повторное чтение/защита от дубля обязательны; миграция UI-07.1 |
| PIN поверх окна | Не терять черновик нижнего окна | Политика безопасности сохраняется | Порядок top layer/focus требует UI-04.3; обход auth не установлен |

Для каждой миграции фиксировать создание → ошибку → повтор → успех → повторное чтение → закрытие/открытие и смену роли/точки. Бронь остаётся трёхшаговой формой; постоянная боковая форма запрещена. Создание новой общей оболочки не меняет серверные права, tenant isolation, idempotency или финансовые расчёты.

### Внедрённый общий контракт UI-04.1 — 2026-10-10

Общий модуль `ui-dialog.js` предоставляет `HOOKAH_UI.open`, `feedback`, `fieldError` и адаптеры `portal`/`staff`. В принятом baseline UI-04.1 единственный перенесённый редактор — **«Новая задача» на `/admin#tasks`**. UI-04.2 расширяет эту ограниченную миграцию ниже; legacy `portalAction`, POS action/payment и PIN сохраняют свои обработчики.

Выбран custom overlay с `role=dialog`/`aria-modal`, поскольку короткий локальный эксперимент показал: native dialog перекрывает обычную PIN-поверхность и не позволяет её полю получить фокус. Эксперимент использует текущие классы/CSS PIN, но **не проверяет авторизацию, API PIN или автоматическую блокировку**. Native/mixed-window stack и полная PIN-интеграция остаются UI-04.3. Одновременно допускается только одна shared форма: второй `open` явно отклоняется. При существующем `dialog[open]` либо `body.screen-locked` shared форма отдаёт фокус и становится inert/aria-hidden, сохраняя DOM; модуль не меняет состояние блокировки и не вызывает разблокировку.

Оболочка требует непустое имя и явные `draftPolicy`/`pendingClosePolicy`; принимает `size`, `initialFocus`, `returnFocus`, `fallbackFocus`, `onClose`, `onSubmit`, `context`, `isCurrent`, `validate`, `errorMessage`. В пилоте используется `medium` 640px; 440px/880px реализованы как размерные варианты для эталона, но не означают миграцию остальных окон. Ширина ограничена доступным viewport−32px, высота — `100dvh−48px`; шапка/footer не прокручиваются вместе с содержимым. Семантические токены и существующие C03–C06 используются без нового декоративного эффекта.

Tab/Shift+Tab удерживаются внутри активной shared формы. Escape сначала закрывает раскрытый custom select, затем действует по политике окна. Backdrop закрывает только после pointerdown и pointerup на самом backdrop; drag из содержимого или внутрь него и pointercancel не считаются закрытием. Фоновый inert сохраняет прежние значения, включая ранее inert узлы, и восстанавливает их при завершении; body overflow восстанавливается. Открытые native поверхности и PIN исключены из собственного inert. Возврат фокуса выбирает доступный инициатор либо заголовок/контейнер страницы; при PIN/native блокировке откладывается до её завершения и проверяет текущий контекст. Это совместимость одного пилота, не подтверждение безопасности всех старых стеков.

Пилот выбирает `draftPolicy: preserve`: ввод сохраняется при ошибке, отмене и повторном открытии **только в памяти текущего экземпляра `renderTasks`**. После успеха или смены контекста draft очищается; reload/пересоздание страницы не обещает сохранённого черновика. Контекст — стабильная primitive-строка verified user id + venue id + role, вместе с проверкой актуального списка; существующие session gate/API guards сохраняются. `pendingClosePolicy: block` блокирует повтор submit, поля и закрытие до ответа API. Запрос выполняется внутри `onSubmit`; успех закрывает форму только после ответа, затем выполняется прежнее повторное чтение списка. Закрытие не отменяет отправленный запрос.

Адаптер `portal` сохраняет прежнее правило `required !== false`, строки FormData и Boolean checkbox (`value` задаёт checked, включая false для снятого). `staff` сохраняет `Boolean(required)`, `checked` и обычную FormData-сериализацию checkbox (`on` только для отмеченного). Числовая проверка использует прежнее Number-coercion, без общей смены формата API. В «Новой задаче» required остаются название, ответственный, приоритет и дата; описание необязательно. Общая field error связана через `aria-invalid`/`aria-describedby` с полем и видимым trigger enhanced select, сохраняя help IDs; сообщение не подменяет серверную валидацию.

Общий feedback использует `role=status`/polite для обычного сообщения и `role=alert`/assertive для явно классифицированной ошибки. Обычные сообщения читаются 4–6с, error не исчезает по таймеру. Адаптер POS сохраняет существующие явно заданные 8–12с для длинных предупреждений; в этом этапе sticky error явно подключён к ошибке выхода, остальные старые POS business-error call sites ещё не классифицированы. Все финансовые pending/idempotency остаются в доменных обработчиках.

### Принятая миграция UI-04.2 — 2026-10-10

**ACCEPTED_SCOPED_WITH_DOCUMENTED_DEBT.** Shared lifecycle применён к редактированию зоны, объекта зала, точки сети, задачи и новой/редактируемой брони. Ordinary helper сохраняет entity-keyed draft только в памяти текущего render, выбирает `preserve`/`block`, выполняет API внутри awaited `onSubmit`, удерживает ввод при ошибке и очищает draft при успехе/смене verified user+venue+role. После GET readback четыре редактора возвращают фокус актуальному heading; временный tabindex очищается однократно на blur. Расписание минимума объекта optional: пустая пара отправляет прежний `null/null`, серверная проверка неполной/одинаковой пары сохранена.

Узкое optional расширение `mount`/`validateMounted`/`onPending` размещает существующую форму брони в shared shell, сохраняет IDs/шаг/guest matching и domain validation, паркует DOM при закрытии и очищает per-open listeners. Владелец исключения scope — system_architect. Default generated fields/adapters сохраняются. API payload, role/tenant guards, tableId/reservationId/action=seat, финансовые/prepayment/refund/idempotency обработчики не меняются. Shared форма отдаёт фокус PIN/native по прежнему ограниченному контракту; полная автоблокировка/mixed stack — UI-04.3.

Приёмка UI-04.2: 98 final JPG/JSON пар, 294 актуальных source refs, 86 открытых shared кадров и 2 pending; desktop 1366/1920 и actual 1228×764, обе темы, ограниченная narrow 390×844 регрессия. 20 принятых API изменений и 7 конечных entities подтверждены отдельным API/readback collector; manager create/edit/reload/error/focus и 4 worker-deny кадра проверены. ## 6. Эффекты и курсоры

Не использовать бесконечный бегущий свет вокруг каждого блока. По ранее выбранному пользователем направлению сохраняется одна мягкая пульсация контура `/admin#company` с периодом 8с, без изменения размеров; не размножать эффект на другие страницы и окна. При reduced-motion — статичный контур. Существующий sweep других окон — долг EX-05, не новый разрешённый паттерн.

Hover/focus переходы 120–180мс, открытие окна до 180–220мс, без перемещения соседних блоков. Busy должен иметь текстовую альтернативу, включая reduced-motion.

Красный комплект курсоров сохранить у кальянщика и бармена для fine pointer. Сохранить значения text/pointer/grab/wait/not-allowed и нативный fallback. Не переносить его владельцу/платформе без отдельного решения.

## 7. Как закрепить правило навсегда

UI-01.1 закрепляет одну редакцию `VISUAL_PAGE_RULES.md`, `DESIGN_TOKENS.md`, `SITE_TREE.md`, `site-map.json`, настоящего стандарта и каталогов. Принятые уточнения: две существующие темы; бронь только в wizard; сохранённая таблица персонала с локальным скроллом; Fold отложен. Основание — чтение текущих `portal.js` и `style.css`; подробные указатели в COMPONENT_CATALOG. Числа и новые семантические переменные пока целевые, а не внедрённые.

Любая новая страница использует существующие компоненты. Новый вариант требует описания причины и состояний в каталоге компонентов, а не ещё одного безымянного CSS override. При миграции удалять старые правила только после доказательства, что их потребители перенесены.

Definition of Done для программной миграции: утверждённый вариант + применимые состояния + роль/точка + клавиатура + реальные desktop снимки + относящиеся проверки кода. Для документального UI-01.1: согласованность правил/карты/каталога, ссылки, evidence из исходников и diff; продуктовые тесты и новая визуальная приёмка не выполняются. После пакета обновляются журнал и перечень исключений; переход к следующему подэтапу требует отдельного задания либо явного разрешения пользователя на автоматическое продолжение, как для UI-04.2 → UI-04.3.
