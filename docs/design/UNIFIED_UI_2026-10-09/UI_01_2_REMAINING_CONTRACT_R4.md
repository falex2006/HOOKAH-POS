S01–S03 — региональные source candidates, F01–F03 — только семантика collection empty. Ни один кандидат не разрешает автоматически изменить весь case row. Whole-row применимость устанавливается после инвентаризации **всех видимых регионов этого state**, отсутствия другого обязательного региона и signoff координатора.

Точные потенциальные recipients S01: CSV predicate `url='/admin#settings' AND role IN(owner,manager) AND state IN(empty,loading,error)` — 36 строк, 12 на state. S02: `url='/admin#help' AND role IN(owner,manager,hookah_master,bartender) AND state IN(empty,loading)` — 48 строк, 24 на state. Это **84 кандидата для обсуждения**, не 84 новых N/A. Read-error topics S02 не исключает 24 help error rows: форма feedback имеет required validation и storage outcome. S03 затрагивает 36 региональных привязок empty/loading/error, но особенно не годится для whole-row исключения из-за открываемого диалога.

Для S01/S02 long-content не исключать по отсутствию удалённых данных: статические карточки имеют конечную композицию, accordion может расширять её. Координатор должен явно определить stress reference: полный фактический текст/раскрытые topics, доступная нижняя форма, отсутствие обрезанных controls при каждом viewport. Не придумывать изменяемые knowledge labels или GET endpoint.

## Исключения, которые аудит не подтверждает

`/admin#company` не stateless: `portal.js:2631,2651,2667–2695` читает venue и reversal policy, есть form, повторная загрузка и связанные поля. Отдельный field без collection не устраняет зависимые списки, read/error или policy. Manager restricted identity не делает всю страницу denied.

`/admin#diagnostics` не stateless: R2 содержит `/api/integrations` и `/api/audit?limit=300`. Empty audit должен оставаться; исходный generic configuration empty candidate нельзя распространять на страницу целиком. `/admin#shift-control` — stateful cash/shift read и действия, closed shift не equal empty collection. `/admin#notifications` — доступный shell/error/Retry, не общая denied поверхность. READ inventory/finance, employee payroll OWN_TODAY и разрешённый finance shell сохраняют собственные состояния даже при запрете вложенного workspace.

Help feedback source `portal.js:2093` пишет `crm_help_feedback` локально и ловит storage exception без сообщения об ошибке, затем показывает успех. Нельзя описывать этот исход как подтверждённую отправку поддержке или успешное сохранение при исключении. Для baseline зафиксировать фактически наблюдаемый success/validation/storage outcome и дефект отдельно; исправление поведения лежит вне этого docs-only пакета.

## Контракт завершённой визуальной базы

`PLAN.md:15–17` определяет UI-01.2 как съёмку исходных экранов; общий повтор системы предусмотрен в UI-09.1 после миграций. При этом фактический `UI_01_2_BASELINE.md:48–55` и R3 acceptance уже включают состояния, keyboard, формы/диалоги и региональную приёмку. Поэтому нельзя задним числом объявить готовой сокращённую базу и снять действующие требования.

Минимальная **завершённая визуальная база** может иметь дефекты исходного продукта, если каждый применимый сценарий достоверно осмотрен, дефект воспроизводим, привязан к current SHA/route/role/state, имеет владельца и не выдаётся за PASS. Она требует:

1. Все 180 role×surface tuples: собственный route gate с session bridge, visible shell/region, итоговый URL/разрешённая normalization, готовность и актуальный bitmap. Baseline всех трёх viewport и двух requested themes — 1 080 slots, со строго ограниченными approved references для public/guard/canonical equivalence.
2. Реальные allowed/READ/OWN_TODAY регионы; источник и подтверждённое отображение empty/loading/error/long states. Уже terminal empty может ссылочно покрывать baseline+empty только той же области с ready/API proof.
3. Keyboard forward/back sequences и focus bitmap у каждого существенно другого template/control context; реально открытые dialog/select/accordion. Common guard reuse требует template×role×viewport и отдельных recipient gates. Baseline/focus denied не становятся N/A.
4. Все 18 component families получают конкретные representatives и recipients по R3 §5–6: source/template/CSS/handler, role/session, theme, geometry, labels, state/action и evidence. Спецификация семейства сама по себе не доказывает runtime equivalence.
5. Каждая из 6 480 строк имеет проверяемый terminal visual-baseline outcome: reviewed own evidence, approved equivalence, region/state N/A либо checked baseline defect. Pending/rejected не terminal. Supported-theme defect может быть документированным исходным дефектом, но не `PASS`/unsupported N/A; ошибочный raster/theme/focus без достоверной пересъёмки остаётся незавершённым.
6. Независимые design/QA/architect подтверждают материал и явно утверждают статус baseline research. Общий функциональный/scenario PASS, persistence и финансовый lifecycle остаются отдельными утверждениями с собственными доказательствами; visual GET samples не подтверждают их.

Это предложение **уточнения типа принятия**, а не разрешение ослабить R3. Если координатор выбирает `BASELINE_COMPLETE_WITH_DOCUMENTED_DEFECTS`, он должен записать decision ID, точный gate, согласование design+QA+architect, обновить связанные acceptance/progress документы согласованно и сохранить matrix case IDs и defects. До такого явного решения действует текущий статус **IN_PROGRESS / NOT ACCEPTED** и текущий R3 gate. Этот аудит решения не принимает.

## Дополнение: независимое решение по предложенной корректировке gate

Координатор отдельно предложил восстановить исходное разграничение `PLAN.md:15–17`: UI-01.2 — visual baseline всех 36 surfaces × 5 roles × 3 viewports × requested themes и representative states; exhaustive 6 480 matrix — сохранённый непройденный regression backlog UI-09.1. Рассмотрено как **явное изменение контракта**, а не как автоматическое разрешение завершить этап.

**Архитектурное решение: GO_CONTRACT_REVISION_WITH_CONDITIONS. NO_GO_STAGE_COMPLETION на основании одного этого решения.** Корректировка обоснована исходным планом: визуальная база нужна перед изменениями дизайна, полная системная приёмка предусмотрена после них. Невыполненные сценарии при этом сохраняются с честными статусами, исходные дефекты остаются основанием следующих пакетов. Существующие 6 480 строки и доказательства не превращаются в PASS и не удаляются.

### Обязательные условия новой минимальной приёмки

1. **Явное решение и согласованные документы.** Записать в `docs/ai-team/DECISIONS.md` decision ID, мотив, исходный и новый gate, точный перечень переносимых обязательств, UI-09.1 как следующего владельца; согласовать architect/design/QA. Новый acceptance документ должен прямо объявить, какие gate-положения R3 он заменяет, а какие сохраняет. Затем согласованно обновить baseline/progress/work log. Пользовательская просьба продолжить UI-01.2 не является доказательством выполнения gate.
2. **Полная карта базовых экранов.** Все 180 role×surface tuples и все 1 080 requested baseline slots должны иметь визуально проверенный актуальный исход: allowed content, partial READ/OWN_TODAY, real deny либо документированный exception. У каждой роли и requested route сохраняется own session/account/tenant/permissions bridge и собственный route JSON. Представитель public login/identical guard/canonical stock допускается только с approved reference и доказанным exact template/geometry/theme context; он сокращает изображения, а не tuples.
3. **Источник и bitmap не противоречат друг другу.** Для обязательных baseline slots нет rejected raster/focus/theme, незакрытых gaps, previous-route capture, pending вместо ready или неподтверждённого target region. Source/product theme defect можно принять как осмотренный исходный дефект; неверная заявленная тема capture требует пересъёмки или честной переклассификации actual context с отдельным доказательством requested context. Ни EX-07, ни одинаковый denied guard не исключают requested theme автоматически.
4. **Репрезентативные состояния по действительным реализациям.** Создать конечный ledger `template/region implementation × role-context × state`, покрывающий применимые empty/loading/error/long/keyboard. Каждая запись ссылается на собственный visually reviewed representative, точный source selector/template/handler и case IDs. Роли фиксируются отдельно; cross-role appearance reuse не подтверждает чужие права/поведение. Все существенные различия responsive layout, light/dark state CSS, visible labels, error handler, dialog composition или permissions разбивают классы. Для shared template достаточно представителей этих реально разных классов; не нужно повторно прогонять все 36 recipient routes в каждом состоянии.
5. **Настоящие поведенческие примеры.** Keyboard включает Tab/ShiftTab и видимый focus, dialog/select/accordion реально открываются. Long reference показывает фактическую расширенную область и scroll/overflow в существенно разных geometry, а не длинную шапку. Empty/loading/error относится к точному list/form/config region и подтверждённому исходу. Существующий defect допустим как baseline finding с воспроизведением, current SHA и владельцем; static/denied N/A допускается по региону с GO_NA. Отсутствующий необходимый representative нельзя заменить задачей UI-09.1.
6. **Backlog принят как непройденный.** UI-09.1 получает все exhaustive route/state/action/persistence сценарии с прежними pending/rejected/defect outcomes и привязкой к baseline representatives. Перенос обязанности не равен component equivalence acceptance и не означает N/A. До изменения общего компонента переиспользуются исходные эталоны; после изменения проверяется зависимый scope, как требует PLAN. Финансовые synthetic GET samples могут быть только visual references с provenance; они не подтверждают реальные операции или lifecycle.
7. **Итоговый независимый signoff.** Design подтверждает просмотр требуемых current-hash baseline и state representatives, QA — фактические sessions/gates/actions/evidence, architect — route/role/region и границы equivalence. Координатор фиксирует residual defects и честный тип приёмки `VISUAL_BASELINE_ACCEPTED_WITH_DOCUMENTED_DEFECTS` либо эквивалентное явно определённое имя. Это не product PASS, не release gate и не deployment approval.

Для нового gate **не требуется terminal outcome у всех 6 480 case rows**. Пункт 5 предыдущего раздела этого отчёта описывал сохранение строгого R3-подхода; он заменяется только после вступления явного решения выше в силу. Terminal visual-baseline outcome требуется у 1 080 baseline slots и каждого обязательного representative ledger entry; остальные exhaustive rows сохраняются непройденными для UI-09.1. Пункты R3 о действительной роли, own-route, current SHA, корректности bitmap, узких N/A и доказанной equivalence сохраняют силу.

Решение становится NO-GO, если новый gate исключает хотя бы роль/маршрут/геометрию/theme slot без доказанного exception, принимает фиктивные access/keyboard outcomes, объявляет недоснятый обязательный state representative «backlog» либо скрывает существующий дефект. На момент этого дополнения фактическая приёмка не выполнена и CSV не изменён. Следующее действие — координатор оформляет decision и независимые signoffs, затем закрывает доказательные gaps по новому gate.
