# Рабочий зал: проверка рабочих состояний

Локальная итерация 13.10.2026. Пользователь запросил проверить и довести перечисленные состояния всей страницы. Работа в изолированном `pos-employee-workspace`; исходный checkout и более ранние изменения сохранены. Нет публикации, изменений схемы или финансовых записей.

## Область проверки

| Сценарий | Требование |
|---|---|
| Свободный стол | Нет суммы/таймера/гостей прошлого заказа |
| Бронь | Реальное время, существующие права и действия; разрешение посадки не выводится из одного времени |
| Недоступный стол | Замок, нейтральная карточка, инспекция без операций; причина не выдумывается |
| Частичная оплата | Отличать общую сумму заказа от остатка, использовать серверный расчёт |
| Смешанная готовность | Видно, какая часть и какое направление готовы; нет ложного статуса готовности всего заказа |
| Выбор | Тонкий акцент не скрывает рабочий статус |
| Обновление | Сохранение выбранного стола, прокрутки и раскрытых подробностей того же заказа |
| Потеря связи | Явное устаревание/ошибка, повтор чтения, запрет записи offline и защита повторных действий |
| Длинные данные | Названия, суммы, время, ТВ/PS и статусы не перекрываются |
| Недоступные действия | Причина видима, включая отсутствие смены, блокировку и неподтверждённые данные |
| Пустота/загрузка/ошибка | Разные состояния и понятный повтор |
| Работа нескольких сотрудников | Обновлённый ответ сервера меняет данные и действия без возврата устаревшего выбора |

## Контракт

`GET /api/floor` — фактические состояния столов и время брони. `GET /api/orders?withPricing=1` — открытые заказы и общая сумма. На карточке написано «Заказ … ₽»: это не остаток к оплате. Выбранный заказ получает авторитетные итоги из существующих `/summary` и `/payments`; дополнительных запросов платежей для каждого стола нет.

Причина блокировки не хранится в текущем контракте API. Вместо выдуманной причины показывается недоступность и обращение к управляющему. Backend уже отклоняет блокировку при активном заказе/броне, создание/перенос на недоступный стол; это проверено чтением существующих обработчиков, без изменения сервера.

Проверка обновлений второго сотрудника в браузере моделирует изменившиеся GET-ответы. Это проверка поведения клиента, а не новый двухпользовательский производственный E2E. Проверки кассовой идемпотентности выполняются отдельно существующими runtime-контрактами.

## Проверки и ограничения

Браузерная проверка `scripts/pos-floor-nuances-browser-qa.cjs`: PASS, 13 групп. Четыре сочетания 320/1366 px и светлой/тёмной темы покрывают свободный/недоступный стол, бронь, смешанную готовность, длинные названия и суммы, частичную оплату и геометрию. Остальные группы: обновление коллегой, ошибки чтения заказов/зала, offline и восстановление, потерянный ответ записи, закрытие заказа коллегой, пустота, начальная ошибка с повтором и загрузка. Ошибок JavaScript и записей API — 0. Мутация в сценарии потерянного ответа перехвачена и прервана тестом до сервера.

Исправлены два подтверждённых регрессионных сценария: прокрутка после обновления цен/заказа теперь сохраняется (90 → 90 px), а ошибка фонового чтения зала запрещает операции с устаревшими данными. При неопределённом результате добавления позиции клиент перечитывает заказ, не повторяя запись автоматически; при неуспешном перечитывании операции заблокированы.

Целевые проверки подготовки, отправки, расчёта и частичной оплаты, навигации, дизайн-токенов/примитивов, синтаксиса и diff выполнены. Старые тестовые mock дополнены отсутствующими browser API и текущим контекстом стола; ожидание суммы обновлено до явной подписи «Заказ». Общий исторический suite не объявляется полностью зелёным.

Снимки и структурированный результат: `evidence/qa.json`, `states-*`, `blocked-*`, `partial-*`; `edge-final.png` — реальная локальная страница в Edge. Экстремальные данные в автоматических снимках моделируются GET-ответами. Универсальная серверная идемпотентность всех операций этим изменением не добавляется.
