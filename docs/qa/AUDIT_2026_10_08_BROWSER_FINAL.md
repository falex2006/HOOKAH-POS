## D02 — устаревшая цена каталога: воспроизведено

1. Кальянщик вошёл, каталог QA Услуга загружен с ценой200.
2. В независимой авторизованной API-сессии владельца PATCH /api/products/{id} сменил цену на275.
3. Кальянщик открыл каталог: кнопка всё ещё «QA Услуга200 ₽».
4. Нажатие добавило новую строку275 ₽. Прежняя строка200 сохранила историческую цену; заказ стал475.
5. Цена справочника восстановлена200. После reload каталог показывает200.

Дефект — несогласованная отображаемая и применяемая цена, не изменение исторической цены. Владелец менял цену через API; отдельный браузерный редактор меню в этом сценарии не использовался. Скриншоты: tmp/audit-20261008/catalog-stale-200.png и order-actual-275.png. Подтверждение строк и цен — GET /api/orders.

## D08 — неверная подпись долга после частичного платежа

После200 из475 основной экран продолжает показывать «К оплате475 ₽», а повторно открытое окно оплаты правильно показывает275 и «Уже оплачено200 из475». Скриншот partial-payment-remainder.png. Архитектор независимо подтвердил: app.js:216 подставляет pricing.due (полную цену) в подпись «К оплате», handler697–705 не обновляет эту строку после частичного платежа. Основное «Итого475» корректно; ошибка относится к подписи долга. Финансовая переплата/двойное списание не доказаны.

Исправление: отдельно «Итого / Оплачено / Осталось», платёжный баланс с сервера, обновление после платежа/reopen/reload с защитой от смены заказа/точки.

## D09 — дублирование и оформление диалога возвратов

У кальянщика в режиме чтения дважды выведен одинаковый раздел «Исходные оплаты». Screenshot refund-staff-duplicate.png визуально подтверждает два блока, белый нативный диалог на тёмном экране и слипшиеся подписи строк. Архитектор независимо подтвердил двойную вставку paymentRowsSection в portal.js:5027 при refundFormAvailable=false (условие5015); у владельца закрытого заказа форма доступна, блок один. Диалог создаётся с классом order-refund-dialog, специальных CSS селекторов для него нет. Дублирования платежей в БД не обнаружено.

Полный browser lost-response/retry с потерей ответа здесь не моделировался; идемпотентность API проверена отдельным PostgreSQL сценарием. Скриншот сохранённой истории: refund-owner-saved.png.

## D10 — передача заказа: исходники и API, без браузерного подтверждения кнопки

Перед повторным входом кальянщика подключение Edge стало недоступным. Этот последний сценарий проверен отдельно авторизованными запросами, а не кликом в браузере. app.js:613–617 формирует status=in_progress для «бар» и ready для «кальянщику». Реальный токен кальянщика на синтетическом открытом заказе110: POST ready →409/invalid_order_transition; POST in_progress →200; затем ready →200; GET orders подтверждает ready всего заказа. Состояние восстановлено через разрешённые переходы in_progress→open. Назначение исполнителя/станции этими кнопками по исходникам не выполняется. Это P1 для рабочего процесса персонала; подробности STRUCTURE.
