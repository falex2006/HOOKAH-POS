# Итоговый диагностический аудит HOOKAH CRM

**Дата:** 08.10.2026. **Основание:** checkout 802d5e63, локальная изолированная среда, исходники, автоматические проверки, реальные API/PostgreSQL и Edge. Три профильных субагента и координатор. Компьютеры/ноутбуки в приоритете; Fold отложен.

## 1. Решение для владельца и управляющего

Диагностический аудит завершён: причины основных расхождений определены, сценарии воспроизведены, составлен план исправлений и матрица покрытия. **Текущая версия ещё не принята для повседневной работы персонала.** Завершение аудита означает готовый диагноз; исправление обнаруженных ошибок и приёмка будут отдельными этапами.

Главная жалоба подтверждена: настройки доступа, предпросмотр сотрудника и фактический интерфейс могут расходиться. Сервер обновляет непустые права в действующих сессиях; причины находятся в правилах приоритета ролей, трактовке пустого списка и разных способах вычисления/отображения прав.

Основа POS работает в проверенных сценариях: заказ сохраняется и виден другой роли; частичная и смешанная оплата закрывают заказ; стол освобождается; сервер блокирует оплату без техкарты и при нехватке сырья. Исправления нужны прежде всего в согласованности прав и информации на рабочем экране.

## 2. Как должна работать единая цепочка

**Владелец задаёт доступ → сотрудник получает эффективные права → интерфейс показывает разрешённое → API проверяет действие → заказ/платёж/склад сохраняются согласованно → другой сотрудник видит тот же результат.**

| Сейчас | Нужно после первого пакета |
|---|---|
| Снятие всех прав системной роли возвращает базовые права | Различать «наследовать» и «явно запретить»; неснимаемые права обозначить отдельно |
| System override перекрывает custom role без понятного объяснения | Явный согласованный приоритет, предпросмотр итоговых прав и источника каждого разрешения |
| Карточка сотрудника и portal используют отличающиеся расчёты | Один серверный источник эффективных прав; одинаковое применение в login/session/profile и интерфейсах |
| Каталог показывает старую цену, сервер добавляет новую | Обновлять каталог без потери заказа; исторические цены строк сохранять |
| Ошибка техкарты выглядит как ошибка суммы | Сообщать причину и доступный следующий шаг, сохраняя серверный отказ |
| После частичной оплаты «К оплате» показывает полную стоимость | Отдельно «Итого / Оплачено / Осталось» по серверному платёжному балансу |

## 4. Что доказано проверками

### Роли и браузер

- Реальные входы owner/admin/manager/bartender/hookah_master; login и session согласованы. Персональные и системные непустые права меняют доступ в уже открытом токене; отзыв/выдача custom scopes также применяется без повторного входа.
- Edge: владелец, управляющий, бармен, кальянщик, ограниченный admin. Рабочий зал, гости, остатки, системный редактор ролей и карточка персонала; выбранные экраны1366×768 и1920×1080. Все формы/состояния каждого маршрута не заявляются проверенными.
- Кальянщик создал тестовый заказ, обновление сохранило его, управляющий увидел тот же заказ. Затем275 добавлены по новой цене;200 наличными +275 картой закрыли заказ475, стол освободился, журнал показывает закрытый заказ.
- Кальянщик может читать историю возврата без формы создания. Владелец создал возврат25 с источником «Карта» и фактической выплатой «Наличные», без возврата товара. Reload и API показывают одну запись; исходные два платежа200/275 сохранены. Все суммы синтетические, внешних транзакций не было.
- При попытке оплатить тестовый товар без техкарты отказ409; payments до/после совпали, paid0, remaining110, closed=false.

Девять baseline FAIL разобраны в COVERAGE_FINAL: четыре несуществующих стола в fixtures, два DOM mock, один lifecycle contract, одна cache revision и один whitelist кассовых полей. Поля текущей кассы документированно добавлены для закрытия смены; их наличие само по себе не доказательство утечки. Тесты нельзя «чинить» отключением защит или assertions.

## 5. Что пока не является готовой функцией

- **Новый официальный расчёт зарплаты:** officialReady:false, writer создаёт blocked run. Прошедшая старая финансовая цепочка не завершает новую интеграцию.
- **Telegram:** planned; реальная отправка уведомлений не подтверждена.
- **Доставка:** просмотренные маршруты ведут журнал суммы/статуса; сквозная связь с позициями POS, платежом и списанием не реализована в них.
- **Цеха/категории:** отдельная записка STRUCTURE сравнивает существующие связи и предлагаемую структуру кальянной/бара; изменения справочников сейчас не выполнялись.

## 6. Последовательность исправлений

Каждый пункт — отдельная задача с номером, статусом, diff, проверками и уведомлением по завершении. Не запускать связанные продуктовые изменения одновременно.

1. **FIX-01, Astra:** единый контракт эффективных прав, пустые/наследуемые значения, приоритеты и profile/session.
2. **FIX-02, Astra:** применение прав во всех интерфейсах, обновление открытой сессии, гости и прямые маршруты. Зависит от FIX-01.
3. **FIX-03, Astra:** сначала исправить передачу работы бармену/кальянщику и договориться о статусах позиций/заказа, затем обновление каталога и согласование отображаемой цены с добавленной строкой. Узкий независимый подэтап каталога после контракта возможен на Luna.
4. **FIX-04, Astra:** понятные складские ошибки оплаты, корректный остаток, окно возврата; проверить деньги/заказ/склад вместе. D06 — отдельный подэтап броней.
5. **FIX-05, Luna для узких fixtures/mocks; Astra для контрактов:** QA-A…F из COVERAGE_FINAL. Можно начать до продукта, в отдельной области файлов.
6. **FIX-06, Astra:** независимая приёмка первого рабочего пакета под всеми ролями. После PASS — пробная работа владельца/управляющего/персонала локально. GitHub и сервер — следующий релизный этап по workflow.

Выбор моделей — рекомендация по сложности; файлы сами модель не переключают. Расход токенов не прогнозируется. Подробные копируемые задания — FIX_TASKS. До приёмки не объявлять первый пакет готовым к работе заведения.

## 7. Границы заключения и остаточная приёмка

Отчёт покрывает основные модули по текущим исходникам/наборам проверок и критические сквозные операции. Он не доказывает отсутствие всех ошибок при любых данных и сетевых условиях. **Не выполнены:** полный lost-response browser retry возврата, HTTP переход через полночь, три настоящих legacy pricing assertions, все комбинации scopes/экранов, полный визуальный CRUD каждого второстепенного модуля, все многофилиальные переходы, реальные внешние интеграции/оборудование/нагрузка. Эти пункты имеют явный статус в COVERAGE_FINAL и приёмке соответствующих исправлений, а не скрытый PASS.

Production, физические устройства и Samsung Fold не проверялись. Продуктовый код, миграции и исходные тесты не изменялись; GitHub/сервер не публиковались. Все дополнительные одноразовые БД удалены. Постоянная синтетическая база сохранена: QA Услуга снова200, заказ475 закрыт, возврат25 сохранён; отрицательный заказ110 без техкарты остаётся открытым и без платежей. Это известные тестовые остатки для воспроизведения.
