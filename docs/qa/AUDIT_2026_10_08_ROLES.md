## ROLE-01 — P1: пустой override восстанавливает базовые права

**Статус: воспроизведено через authenticated API, включая повторный вход.**

`server.js:326–333`: наличие override распознаётся, но `if (!scopes.length) return base` возвращает права базовой роли. Сохранение разрешено в `server.js:3920–3923`.

Шаги: владелец сохраняет бармену `permissionScopes: []` через `/api/staff/system-roles/bartender`; сотрудник запрашивает `/api/session`. Фактически возвращены `floor`, `orders`, `bar_tasks`, `finance_read`; GET `/api/clients` вернул 200. После повторного входа `orders` сохранился. Для администратора исходники предполагают восстановление ещё более широкого базового набора; этот вариант отдельно через HTTP не проверялся.

Приёмка: отличать отсутствие настройки от явно пустой настройки; явно определить неснимаемые служебные права. После снятия направлений их операции запрещены API, соответствующие элементы скрыты; результат одинаков в существующей сессии, после reload и повторного входа. Обязательны бармен и администратор.

## ROLE-02 — P1: custom role игнорируется системным override

**Статус: воспроизведено через authenticated API.**

`server.js:328–329` безусловно выбирает системные scopes раньше custom и персональных. Назначение в `portal.js:2759` / `server.js:4311` успешно сохраняет custom role, не сообщая о подавлении её прав.

Шаги: назначить бармену custom role `[inventory]` — `/api/session` возвращает `inventory`, `inventory_read`, GET `/api/inventory` = 200. Затем сохранить системному бармену `[orders, finance_read]` — `inventory` исчезает, хотя custom role остаётся назначенной.

Приёмка: документированный порядок приоритетов базовых, системных, custom и персональных прав; UI объясняет итоговый доступ. Проверить каждую комбинацию, пустые значения и обновление уже открытой сессии. Это требует решения политики, а не произвольной перестановки условий.

## ROLE-03 — P1: portal восстанавливает базовые права в интерфейсе

**Статус: исходники + браузерное наблюдение координатора под scoped admin. Полная ролевая матрица ещё нужна.**

`portal.js:28–47` строит разрешения объединением базовых и сохранённых прав, игнорируя прямую обработку custom/system scopes. `portal.js:508–512` проверяет маршрут до запроса текущей сессии. Серверная сверка отдельно реализована для финансов/броней (`portal.js:5725–5785`). `app.js:66–70` сохраняет актуальные workspacePermissions, но portal опять объединяет их с базовыми. `login.js:221` сохраняет user без верхнеуровневого permissions.

Координатор в Edge под синтетическим scoped admin `qaprimary_scoped` наблюдал все пункты меню и ошибки на `/admin`, затем кнопки добавления позиции и приёмки на складе при отказе API в доступе. Это подтверждает отображение недоступных функций. Для дальнейшей матрицы: ограничить администратора `[orders]`, сравнить интерфейс с `/api/session`; дать новый scope уже вошедшему сотруднику и открыть соответствующий маршрут. Обратный сценарий скрытия вновь разрешённой функции требует отдельного подтверждения.

Приёмка: единый серверный набор загружается до построения интерфейса на всех маршрутах; отозванные права не добавляются обратно. Проверить выдачу/отзыв, две открытые вкладки, reload, повторный вход, ошибки сессии. Сервер остаётся окончательной проверкой доступа.

## ROLE-04 — P2: «Гости» закрыты сотруднику вопреки API

**Статус: исходники + API + наблюдение координатора в Edge 1366×768.**

`portal.js:293`, `portal.js:508` требуют `staff_view`; `server.js:3587–3588` разрешает чтение гостей также по `orders`. Стандартные бармен/кальянщик имеют orders без staff_view (`server.js:284–285`). В Edge бармен нажимает «Гости» и попадает на `/admin`; API чтения списка возвращает 200.

Приёмка: согласовать ссылку, route guard и сервер; обе рабочие роли открывают разрешённый список гостей напрямую и через меню. Не выдавать кадровые права ради доступа к гостям. Проверить запрет роли без соответствующего права.

## ROLE-05 — P2: profile сообщает неправильный набор прав

**Статус: воспроизведено через authenticated API.**

`server.js:4170–4172`: SQL читает имя и ID custom role, но не её permission scopes; системный override также не загружается. Расчёт workspacePermissions использует отсутствующее поле customRolePermissionScopes.

Фактически при custom role `[inventory]` profile вернул `floor, orders, bar_tasks, finance_read`, а session — `bar_tasks, inventory, inventory_read`. Приёмка: одинаковый effective набор в обоих ответах, вычисленный общим resolver; профиль не раскрывает персональные данные неположенной роли.
