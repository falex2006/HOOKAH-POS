# FIX-03.1 — исходное состояние и критерии QA

Прочитаны профили qa_engineer/code_health_engineer; просмотрены app.js, server.js, db.js и существующие scripts. Это read-only baseline продуктового кода. Изменения FIX-01/02, текущий dirty checkout и посторонние материалы сохраняются. Полный runner не запускался.

## Риски границ

- Существуют три реализации: PostgreSQL, серверный memory и browser static demo. Успех demo не доказывает запись в PostgreSQL. Для production-контракта обязательны HTTP с настоящей PG и повторное чтение вторым сотрудником.
- Текущий order-level status допускает open/in_progress/ready/cancelled; изменение статуса всего заказа нельзя считать готовностью каждой позиции смешанного заказа. Подготовка на станции и финансовое закрытие имеют разные цели.
- `db.js` уже сохраняет station и включает её в pricing facts. Новая отправка не должна переписывать существующую станцию/продавца/цену строки и canonical snapshot после частичной оплаты.
- `bar_tasks`/`hookah_tasks` теперь зависят от эффективных orders; нельзя проверять только название роли или восстанавливать доступ базовым списком. Определить права manager/owner явно.
- Асинхронные ответы app.js должны учитывать текущие order ID, venue и revision. Результат готовности старого заказа после выбора другого не должен менять новый экран.
- Повторная отправка и два сотрудника одновременно не должны сбрасывать ready назад или дублировать задания. Изменение готовности не должно вызывать оплату/списание.
- Финансовые операции блокируют/фиксируют pricing и закрывают заказ транзакционно. Новый обработчик должен сохранять порядок блокировок и запрет изменений closed/cancelled.

## Матрица приёмки

| Сценарий | Ожидаемое доказательство |
| --- | --- |
| Смешанный заказ:2 барные позиции и1 кальян | После отправки каждая станция видит свои позиции, общий заказ сохраняет все3 |
| Готова1 из2 барных | Вторая и кальян не готовы; заказ в целом не ready |
| Все барные готовы, кальян в работе | Бар завершён; весь заказ ещё не ready |
| Последняя кальянная позиция готова | Заказ ready только при выполнении утверждённого правила всех активных позиций |
| Повтор send/status, double-click, replay | Нет дублей и отката статуса; HTTP результат и повторный GET согласованы |
| Два сотрудника завершают разные позиции одновременно | Оба изменения сохранены, конечный aggregate вычислен из актуальных строк |
| Бармен меняет кальянную позицию и наоборот | Сервер отклоняет; UI не предлагает действие; manager/owner по утверждённому контракту |
| Отозваны orders при открытой вкладке | Ни старая кнопка, ни прямой HTTP не дают mutation |
| Чужая точка/заказ, неизвестная строка | Отказ без чтения/изменения чужих данных |
| Добавлена новая строка после отправки/готовности | Явно согласованный переход; готовые старые строки сохраняются, новая требует отправки/готовности |
| Reload и вторая сессия | PostgreSQL статус совпадает с обеими UI без localStorage подмены |
| Частичная оплата, затем готовность | Платёж, цена, продавец и snapshot не меняются |
| Финальная оплата | Ровно одно списание рецепта/движение; готовность сама не списывает склад |
| Нехватка ингредиентов | Платёж/закрытие/движения откатываются по прежнему контракту |
| Closed/cancelled заказ | Отправка/готовность отклонены; финансовая история не меняется |

## Узкий набор проверок

После реализации: `node --check` изменённых JS/MJS/CJS, `git diff --check`, новый focused dispatch/item-status HTTP/PG suite и чистая unit/VM проверка агрегирования. Для нового PG suite сначала зарегистрировать точный безопасный wrapper/owned database, не передавать production URL.

Существующие подходящие команды:

- `node scripts/order-item-close-guard-qa.mjs` — граница финального заказа.
- `node scripts/order-attention-qa.mjs` — совместимость признаков внимания/статуса.
- `node scripts/local-full-pg-regression.cjs acceptance-47-pos-journey-postgres-qa.mjs` — сквозная непрерывность POS.
- `node scripts/local-full-pg-regression.cjs recipe-depletion-pg-runtime-qa.mjs` — финансово-складские guards, если затронута соответствующая ветка.
- `node scripts/staff-effective-permissions-qa.mjs` и `node scripts/portal-effective-permissions-qa.mjs` — если меняются рабочие handler/navigation.

`order-item-sales-attribution-*` подходят для сверки seller/soldAt; PG вариант не следует запускать вслепую: сначала проверить поддержку wrapper и target. Browser suites запускает координатор через CUA; наличие Playwright в старом тесте не является разрешением обходить этот путь.

## Требования к новой проверке

Создавать собственные реальные столы/смену/товары, чтобы не повторить известные ошибки fixtures с выдуманным tableId. Проверять HTTP статус и тело, повторный GET, SQL persisted state, отсутствие дополнительных payments/stock movements. Не ограничиваться regex наличия endpoint. Отличать функциональный PASS от успешной очистки; удалять только runner-owned DB, сохранять первичную ошибку при cleanup failure.
