# Как организовать кальянное направление и бар

Предложение управляющему · 08.10.2026 · по текущему коду CRM. Настройки и данные сейчас не изменены.

## Что уже есть в системе

**Склад:** цех → необязательный подцех → категория → складская позиция. Категория относится к цеху и может быть привязана к подцеху; складская позиция хранит цех, подцех, название категории и её ID. **Меню — отдельный список продаваемых позиций.** Техкарта связывает позицию меню с конкретными складскими ингредиентами и количеством расхода. При окончательной оплате/закрытии заказа списываются ингредиенты; заранее изготовленный премикс поддерживается как отдельная складская заготовка.

```text
СКЛАД                                  ПРОДАЖА ГОСТЮ
Бар → Крепкий алкоголь → Ром ───┐
Бар → Соки → Ананасовый сок ────┼─ Техкарта → Авторский коктейль
Бар → Сиропы/пюре → Сироп ──────┘

Кальяны → Табак и смеси → Вкус ─┬─ Техкарта → Кальян
Кальяны → Уголь → Уголь ────────┘
```

## Рекомендуемый старт без усложнения

| Цех | Категории складских позиций |
|---|---|
| **Кальяны** | Табак и смеси; уголь; расходники; принадлежности/оборудование |
| **Бар** | Крепкий алкоголь; пиво; вино/игристое; безалкогольные аналоги алкоголя; энергетики; вода; соки; газированные напитки; чай/кофе; сиропы/пюре/прочие ингредиенты; заготовки |
| **Хозяйственный** — при необходимости | Уборка и общие хозяйственные расходники |

Подцеха на старте оставить пустыми. Марка, вкус, объём бутылки — свойства/названия конкретных позиций, а не дополнительные уровни дерева. Категории можно объединить, если управляющему удобнее один список «Вода, соки и газировка». Категории принадлежностей сами по себе не означают расход при каждом кальяне: в техкарту включать только фактически расходуемое сырьё.

В **меню для сотрудника** нужны понятные группы: «Кальяны», «Алкогольные коктейли», «Безалкогольные коктейли», «Крепкий алкоголь», «Пиво», «Чай», «Вода и напитки». Авторский коктейль — позиция меню с техкартой. Чай — тоже по рецепту, если учитываются заварка и добавки. Для проданной бутылки напитка — техкарта на одну единицу. Реальное сырьё не следует переводить в режим «без складского учёта» ради обхода отсутствующей техкарты.

## Где требуется доработка, а где достаточно настройки

Складское дерево и рецептурная связь уже поддерживаются. **Но единое дерево меню и склада пока отсутствует:** товар меню хранит текстовую `category`; API использует её также как `station`, и она копируется в строку заказа как станция. У товара меню нет той же прямой связи с ID складского цеха/подцеха/категории. Поэтому сейчас нельзя обещать, что категории «Чай» и «Коктейли» автоматически направят работу именно бармену. Будущая доработка должна отдельно связать товар с направлением приготовления «Бар/Кальяны» и сохранить независимую удобную группировку меню.

**Подцех сейчас — группировка, а не доказанный отдельный остаток «стойка/запас».** Остаток рассчитывается по складской позиции в заведении. До реализации отдельных мест хранения не предлагать подцеха как систему перемещений между складом и стойкой.

Для согласования достаточно подтвердить список категорий, состав продаваемого меню и реальные нормы расхода. Сначала привести справочники/техкарты к этой схеме; отдельным пакетом связать рабочие направления, меню и роли. Новые миграции в рамках этого предложения не выполняются.

## Уточнение фактической отправки сотрудникам

Проверка обработчика показала более конкретную проблему, чем отсутствие связи категорий. **Категория «Чаи» или «Авторские коктейли» сама ничего не отправляет в бар.** Обе кнопки `app.js:613–617` вызывают один endpoint `/api/orders/:id/status`, передавая только статус всего заказа: кнопка с текстом «бар» — `in_progress`, другая — `ready`. `station`, категория, роль получателя, назначенный сотрудник и отдельные строки заказа в запрос не передаются. В обработчике сервера (`server.js:5993–6011`) обновляется статус orders; задача персоналу этим действием не создаётся.

**D10 — P1, блокер рабочего сценария сотрудников:** для нового заказа open кнопка отправки кальянщику посылает ready, но `server.js:824–825/:6003` разрешает open→in_progress и запрещает open→ready. Результат —409 `invalid_order_transition`, UI показывает «Не удалось передать заказ». После предварительной отправки «на бар» эта же кнопка переводит весь заказ в «Готово», хотя уведомление говорит «Задача отправлена кальянщику». Это расхождение операции и подписи. Координатор подтвердил через helper `dispatch-check` и реальный API под кальянщиком: open→ready возвращает409 `invalid_order_transition`; open→in_progress→ready возвращает200, повторный GET показывает ready всего заказа. Тестовый заказ восстановлен в open. Само нажатие кнопки в браузере не проверено: Edge стал недоступен; связь кнопки с запросом подтверждена исходником.

Очередь `app.js:579` фильтрует только общий статус заказа; фильтрации строк по station или роли бармен/кальянщик здесь нет. `/api/orders` (`server.js:5831–5838`) отдаёт заказы заведения по разрешению orders без такой фильтрации. Пункт «Задачи» (`app.js:586`) открывает отдельный `/admin#tasks`; это не результат нажатия описанных кнопок.

Для первого пакета рабочего места нужен краткий сквозной контракт: отдельное направление работы (Бар/Кальяны), его связь с `order_items.station`, допустимые статусы строк и всего заказа, права на передачу и готовность. Настройка категорий сама не создаёт отдельную очередь. Минимальный пакет должен согласовать подписи кнопок, запросы API и переходы статусов; объём последующего разделения работ определяется этим контрактом.
