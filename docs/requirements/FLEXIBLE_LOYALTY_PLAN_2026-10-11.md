# План создания гибкой системы лояльности

Дата: 11 октября 2026. Статус: реализация начата по прямой команде владельца «поставь себе цель и начинай». Активная цель и реестр FLEXIBLE_LOYALTY_ROADMAP.json определяют текущий прогресс. Этот документ не подтверждает готовность перечисленных возможностей в приложении.

## 1 Цель и границы

Владелец может использовать один шаблон, несколько программ одновременно или собрать собственную программу из блоков разных шаблонов. Участие гостя в нескольких программах и применение нескольких выгод к чеку — разные решения. Все финансовые условия выбирает владелец; примеры не включаются автоматически.

Разработка выполняется этапами в изолированной среде, а пользователю передаётся один согласованный локальный пакет с миграциями, интерфейсом, серверной логикой и проверками. Обещание «всё заработает» подтверждается приёмкой, а не количеством написанных форм. GitHub и VPS — отдельный выпуск по актуальному разрешению, не следствие слова «начинаем».

Разрешены локальная реализация и проверки по этапам в выделенном worktree. Пользовательские базы и чужие контейнеры сохраняются; PostgreSQL QA использует отдельные базы, созданные самим прогоном, с удалением только этих баз. Активация рабочего приложения — после приёмки согласованного пакета. GitHub/VPS, реальные рассылки и ранее обсуждавшийся ночной аудит не запускаются по историческим сообщениям.

Новое заведение получает пустые рабочие данные и выключенные программы. Библиотека шаблонов не создаёт гостей, цеха, категории, продукты, техкарты, комнаты или цены. Очистка существующего заведения — отдельная классификация данных; не удалять данные финансов и зарплаты ради пустого экрана.

## 2 Точки интеграции проекта

При подготовке прочитаны SITE_TREE.md, роли архитектора и дизайнера, проектный workflow и LOYALTY_POLICY_CONTRACT.md. В текущем локальном коде найдены loyalty-pricing.js, серверные /api/loyalty/settings, /api/loyalty/promotions, /api/discount-groups, карточки /clients и настройка /admin#loyalty. portal.js содержит редакторы групп и акций. Это точки для повторного исследования на старте, не доказательство текущего runtime или VPS.

Рабочее дерево содержит многочисленные посторонние изменения. На старте сверить опубликованную базу, текущие ветки, работу по финансам/зарплате и UI. Не применять stage-all, reset, clean, массовое копирование или выпуск всей локальной папки. Выделить релевантные изменения в согласованный изолированный worktree. Старый LOYALTY_ROADMAP.json описывает прежнюю систему; не переносить его проценты готовности в новую.

## 3 Модель конструктора

Иерархия: заведение → программа → неизменяемая опубликованная версия → блоки правил. Шаблон копируется в черновик и больше не меняет его скрыто при обновлении библиотеки. «Добавить блок из программы» создаёт независимую копию с происхождением, без скрытых связей и переноса гостей/балансов. Глобальные ограничения заведения применяются поверх блоков.

Каждый блок содержит:

- аудиторию: все, выбранные гости, несколько групп, динамический сегмент, исключения;
- событие: просмотр чека, оплаченный заказ, завершённый визит, достижение, личная дата, приглашение, наступление срока;
- условия: все/любое из условий; ограниченная глубина групп; сумма, товары, категории, количество, филиал, канал, время;
- действие: скидка, цена, бонусы, подарок, выбор награды, привилегия, уведомление или задача;
- период действия и срок полученной награды;
- совместимость, приоритет, лимиты и бюджет;
- режим выдачи: автоматически, выбор гостя, подтверждение сотрудником с правом;
- понятное описание результата и причины отказа.

Типы условий и действий — расширяемый реестр с валидируемой схемой. Произвольный исполняемый код в правилах владельцу не предоставляется. Удалённый товар не заменяется другим молча: блок показывает проблему и требует перенастройки.

## 4 Функциональные блоки полного пакета

| Блок | Требуемые настройки |
|---|---|
| Скидки и цены | Процент, сумма, специальная цена; чек/строки/категории; исключения; минимум чека; предел выгоды |
| Бонусы | База начисления после выбранных корректировок, ставка/множитель, лимиты списания, начисление при списании, доступность и срок партий |
| Уровни | Сумма, визиты, количество оплаченных позиций; календарный/скользящий/весь период; сохранение/снижение уровня; уведомления |
| Персональные группы | Родственники, друзья, сотрудники, партнёры и произвольные группы; несколько членств; сроки и права назначения |
| Расписание | Дни недели, несколько окон, переход полуночи, даты, исключения, часовой пояс заведения |
| Даты | День рождения, личная дата, годовщина первого визита, праздник, событие заведения; окна до/после, повторение, раз в год |
| Достижения | Пороги 20/50/200/500 или любые; оплаченные позиции/визиты/сумма; один раз или каждые N; все пересечённые пороги либо старший |
| Серии и карточки | N посещений за период, последовательные периоды; максимум одного зачётного визита за заданное окно; прогресс и сброс |
| Первый и повторный визит | Цепочка предложений, срок следующего шага, завершение/выход, недопущение повторного welcome |
| Возвращение | Пауза с последнего визита либо отклонение от обычной частоты; частотный предел, исключения активных гостей |
| Приглашения | Код/ссылка, вознаграждение одной или обеим сторонам, первая оплаченная покупка, порог, лимиты, защита от самоприглашения |
| Награды на выбор | Каталог вариантов, наличие, один выбор из набора, срок, история выдачи/погашения |
| Привилегии | Приоритет бронирования, мероприятия, доступ к предложениям; вместимость, запись и подтверждение |
| Комплимент | Разовая персональная выдача с причиной, лимитом полномочий и аудитом |
| Клуб и абонемент | Срок членства, количество услуг, лимиты по периоду, перенос/заморозка по правилам; ручное продление базово |
| Компания и сеть | Членство, локальные исключения, допустимые филиалы; раздельный учёт начисления и использования между заведениями |
| Уведомления | Администратор, кассир, гость; событие, канал, срок, частота, согласие и статус доставки |
| Аналитика | Выдачи, списания, остатки обязательств, стоимость подарков, использование, визиты, отмены, результат по программам |

Подарочные сертификаты, денежный депозит, предоплата брони и оплаченный пакет услуг имеют отдельные типы обязательств. Бонус не становится деньгами гостя. Для онлайн-автосписания подписки нужен подключённый платёжный провайдер и отдельное разрешение; без него доступно явное ручное продление, а интерфейс не обещает автоплатёж.

Количество «выкуренных» означает оплаченные позиции заказа, а не сведения о фактическом потреблении. Для общего стола владелец выбирает главного гостя либо распределение строк между гостями; двойной зачёт запрещён. Подарки, возвраты и частичная оплата учитываются явно. Программы табачных и иных ограниченных категорий требуют отдельной проверки применимости до активации; наличие настройки не означает допустимость любой акции.

## 5 Расчёт и совместимость

1. Сервер получает заведение, гостя, корзину, время и версии правил. Клиент не является источником суммы выгоды.
2. Отбирает действующие программы по аудитории, расписанию и условиям, формирует причины допуска/отказа.
3. Строит допустимые сочетания по матрице совместимости: вместе, взаимоисключение, выбор гостя, приоритет.
4. Раздельно решает скидки/цены, начисление, списание и подарки. «Наиболее выгодно» по умолчанию сравнивает денежную скидку текущего чека; несопоставимые будущие бонусы и привилегии предлагает выбрать, не выдаёт за автоматически лучший вариант.
5. Применяет общий предел и пределы строк, проверяет неотрицательный итог, ограничения минимума заказа. Спеццена не повышает цену по умолчанию. Фиксированная скидка не превышает допустимую базу.
6. Использует целые денежные единицы минимальной точности, детерминированное распределение округления по строкам. Для совместных процентов задаётся порядок и база; по умолчанию каждый следующий процент от остатка, с показом фактической итоговой скидки.
7. При равенстве — стабильные приоритет, идентификатор правила и версии. Ограничивает сложность расчёта; превышение не приводит к случайному выбору или тихому отказу от выгод.
8. При оплате атомарно проверяет лимиты/баланс/бюджет и фиксирует подробный снимок применённых компонентов. Повтор запроса не дублирует списание или награду.

Новый контур должен иметь явную политику фиксации условий: проектный default — серверная переоценка до первой успешной оплаты и заморозка при ней. Если условия изменились после показа кассиру, показать новый итог до подтверждения. Для старых заказов сохранять действовавший контракт; текущий снимок настроек при создании заказа нельзя скрыто заменить новой семантикой. Разделение/объединение заказов, добавление позиций после частичной оплаты и перенос гостя требуют отдельных контрактов с финансами; до их поддержки запрещать несовместимое действие с объяснением.

Возврат использует исходные строки, версии, распределения и тендеры, не сегодняшнюю программу. Уже потраченные начисления корректируются через аудируемую политику удержания будущих бонусов/долга, не переписыванием истории. Денежный возврат и возврат стоимости товаров не смешиваются.

Расписание использует IANA timezone, интервалы [начало, конец), ночное окно относится ко дню его начала. Политика для повторяющихся/несуществующих часов DST фиксируется в контракте и тестах. Для 29 февраля владелец выбирает 28 февраля/1 марта/только високосный год. Название праздника не определяет пол гостя. Год рождения необязателен, если не нужен функции.

## 6 Экраны и расположение элементов

Сохранить существующий вход «Лояльность» /admin#loyalty и карточки /clients. Не добавлять второй похожий раздел. Новые вкладки и URL состояния согласует system_architect с общим каркасом; прямые ссылки и возврат браузером должны сохранять контекст заведения.

### 6.1 Главная страница лояльности

В общей шапке остаются штатные элементы приложения. Под заголовком — локальная панель: слева поиск, статус и тип; справа основная кнопка «Создать программу» и вторичная «Проверить на примере». Пять вкладок: «Программы», «Аудитории», «Награды», «Результаты», «Настройки». Библиотека шаблонов доступна из создания и пустого экрана; общие правила и конфигурация уведомлений — в настройках. На узком экране вкладки прокручиваются, фильтры открываются одной кнопкой. Журнал управленческих уведомлений использует существующий /admin#notifications, не второй центр.

Список программ показывает название, аудиторию, короткое описание выгоды, расписание, статус, предупреждения и активную версию. Действия строки: «Открыть», переключатель работы и меню «Копировать / История / Архивировать». Архив скрыт штатным фильтром. Пустой экран объясняет отсутствие программ и предлагает «Выбрать шаблон» / «Создать свою».

### 6.2 Создание и редактирование

Первый выбор: «Из шаблона» или «Собрать свою». Мастер: 1 название → 2 кому → 3 когда и за что → 4 награды → 5 совместимость и лимиты → 6 проверка. Можно вернуться к любому шагу. Справа на desktop — постоянно обновляемое описание человеческим языком; на mobile оно раскрывается кнопкой «Как это работает».

Внутри программы — список блоков с названием, кратким правилом, переключателем и кнопкой «Настроить». Над ним «Добавить блок» и «Взять из другой программы». Порядок имеет значение только там, где это явно указано; кроме drag-and-drop доступны кнопки перемещения. Расширенные поля свернуты, финансовые ограничения не спрятаны в подсказке.

Нижняя панель редактора: «Отмена», «Сохранить черновик», «Проверить», «Включить» для прошедшего проверку проекта. При редактировании активной программы кнопка называется «Опубликовать изменения»: сохранение черновика не меняет действующую версию. Несохранённый выход требует выбора сохранить/отбросить/остаться. Ошибки около поля и краткий список сверху с переходом к полю.

### 6.3 Включение и выключение

Жизненный цикл: черновик → запланирована/активна → приостановлена → завершена → архив. Запланирована/завершена могут быть вычисляемыми состояниями опубликованной версии. Переключатель «Включена» управляет разрешением работы опубликованной версии, рядом отдельно видны «Работает сейчас» или «Вне расписания». В черновике вместо тумблера «Проверить и включить», в архиве тумблера нет. Переключатель не удаляет программу; запрос pending блокирует повтор, ошибка возвращает прежнее состояние. Включение объясняет число блоков и ограничения, не включает соседние программы.

Пауза прекращает новые выдачи и применение новых скидок. Уже выданные награды и замороженные оплаты сохраняют условия; их отзыв — отдельное действие с причиной и последствиями. Отключение блока действует только на будущие операции новой версии. Аварийная остановка новых выдач доступна уполномоченному владельцу с аудитом; возвраты и учёт обязательств продолжают работать.

### 6.4 Симулятор

Поля: реальный гость в доступном контексте либо синтетический пример без создания записи, корзина, дата/время, филиал. Результат: исходная сумма → каждая скидка → итог; бонусы к начислению/списанию; награды; выбранные и отклонённые блоки с причинами; пересечения и лимиты. Сценарий можно сохранить как пример программы. Симулятор использует тот же движок, не изменяет деньги, квоты и счётчики. Реальная оплата повторно проверяет условия и может отличаться при изменении остатков — это явно показывается.

### 6.5 Карточка гостя

Вкладка «Лояльность»: несколько программ, группы, уровень, прогресс, доступные награды, личные даты и согласия. Кнопки по правам: «Назначить программу», «Выдать награду», «Изменить участие». Денежный счёт и бонусы показываются раздельно и только при соответствующем праве. Текущая оперативная /clients по SITE_TREE не раскрывает bonus/deposit поля: расширение требует явного серверного permission-контракта, одного права orders недостаточно. История содержит время, причину, программу/версию, сотрудника, заказ, отмену. Группы и служебные пометки не раскрываются в гостевом уведомлении. Объединение дубликатов гостей сохраняет происхождение событий и не выдаёт welcome/достижения повторно.

### 6.6 Касса и бронирование

В карточке заказа рядом с гостем — компактный блок «Лояльность»: применённая выгода, доступный выбор и «Почему так». Автоматическое правило не требует повторного нажатия при каждом заказе. Кнопка «Выбрать награду» доступна при альтернативе, «Использовать бонусы» показывает баланс и доступный максимум. Ручное изменение требует права и причины. До привязки гостя видны только общедоступные предложения; при его смене пересчитываются права, не переносятся чужие награды.

В бронировании — доступные привилегии и даты без обещания награды до выполнения условий. Для ограниченного мероприятия нужна атомарная резервация места. Денежную предоплату показывать отдельно.

### 6.7 Уведомления и доступность

У кассира — неблокирующее сообщение и индикатор в карточке; администратору — центр уведомлений/задача. Попап на каждый визит запрещён. События: доступная награда, достижение, скорое истечение, конфликт программы, исчерпание бюджета, ошибка доставки. Владелец выбирает адресатов и пороги; повторные события объединяются.

Гостевые каналы только при подключении и соответствующем согласии: тихие часы, часовой пояс, лимит сообщений, отписка, минимизация данных. Статусы: ожидает/отправлено/доставлено при подтверждении провайдера/ошибка/отменено. Внутреннее создание уведомления не равно доставке гостю. Без провайдера внешняя отправка недоступна с понятным объяснением, внутренние уведомления работают.

Все экраны: loading/empty/error/retry/forbidden/stale-venue/stale-version/offline. Финансовое действие при неизвестном серверном результате проверяет статус операции по ключу, не повторяет с новым ключом. Сеть не превращает неизвестный баланс в ноль. Подписи переключателей, клавиатура, видимый фокус, возврат фокуса, экранный диктор, touch targets, светлая/тёмная тема; tooltip не единственный носитель важных условий. Проверять desktop, планшет, phone и Fold по проектным правилам.

## 7 Данные и API будущей реализации

Это целевой контракт; точные имена и расширение существующих маршрутов утверждаются на этапе 2, до кода.

Сущности: программы; неизменяемые версии; блоки; шаблоны; членства; динамические сегменты; накопительные события/счётчики; выдачи наград и погашения; бонусные партии и распределения; резервы бюджета; подписки/пакеты; согласия; outbox; журнал аудита. У каждой записи tenant/venue и ссылки на исходные события. Сетевой доступ только внутри явно разрешённого объединения; соседний tenant никогда не является «филиалом» по совпадению имени.

| UI действие | Предлагаемый API | Права и сохранение |
|---|---|---|
| Список/редактор | GET/POST /api/loyalty/programs; GET/PATCH /:id | Чтение по permission, запись owner/admin; серверный tenant, expectedVenueId/version |
| Включить/пауза | POST /api/loyalty/programs/:id/transitions | Проверка конфигурации, новая версия/событие, аудит атомарно |
| Симулятор | POST /api/loyalty/preview | Ограниченное чтение гостей; один evaluator, без записей |
| Членства | GET/POST /api/clients/:id/loyalty-memberships | Роль/область, сроки, optimistic concurrency, аудит |
| Выдать/погасить | POST /api/loyalty/rewards; POST /:id/redemptions | Право, причина, idempotency, баланс/квота/аудит одной транзакцией |
| Расчёт заказа | Расширить существующий контракт orders/payments | Компонентный снимок, итог от сервера, сохранение старого формата чтения |
| Возврат | Расширить текущий маршрут возврата | Исходная аллокация, тендер, сторно наград; не новый параллельный возврат |
| Отчёт/доставка | GET /api/loyalty/reports; GET /api/loyalty/notifications | Область данных, пагинация, минимизация персональных данных |

Каждый endpoint описывается в API.md: payload, response, auth, ошибки, повторное чтение. Коды 400 — поля/несовместимые правила, 403 — право, 409 — версия/баланс/квота/контекст, 428 — отсутствующая предусловие, 503 — недоступность; UI показывает понятный русский текст. Все мутации проверяются сервером независимо от скрытых кнопок.

Истечение бонусов списывает партии по ближайшему сроку, сохраняет распределение и сторно. Переменный курс нельзя просто добавить полем: текущий контракт фиксирует 1 бонус = 1 ₽; сначала нужны независимые единицы баллов и денег, исторический курс и новый формат платежа. Полный пакет предусматривает эту миграцию, но default сохраняет 1:1.

Уведомления и достижение порога обрабатываются outbox/идемпотентным consumer после commit, с уникальным ключом события и контролируемым retry. Расчёт оплаты и проверка денежных лимитов остаются транзакционными. Полный пересчёт истории для каждого чека запрещён; индексы и агрегаты с восстанавливаемым происхождением. Исторические данные импортируются только явным действием, не ретроактивно раздают награды при включении.

## 8 Финансы склад и зарплата

Согласовать единый расчёт для предпросмотра, POS, отложенных заказов, отчётов и зарплатной базы; отдельно найти SQL/legacy-калькуляторы. Не допускать двух трактовок скидки в server.js и loyalty-pricing.js. Текущий evaluator выбирает одну скидку; композиция требует новой версии снимка, а не маскировки суммы под старый selectedDiscount. Снимок содержит версии каждого компонента, строковую gross/discount/net аллокацию, основания, курс и начисления. Расширить promotionTermsEqual, allowlists, DTO и сохранение/повторное чтение согласованно; неизвестный тип блока запрещает публикацию вместо тихого пропуска.

Подарок — реальная позиция с учётом себестоимости/списания склада и нулевой либо скорректированной ценой. Выдача обещания подарка сама по себе не списывает товар. Бонусы, деньги, сертификаты, подписки и предоплаты сверяются раздельно.

Привязка продаж сотрудникам, распределение скидок и влияние возвратов на зарплату остаются настройками владельца. Не назначать скрыто комиссию от gross/net и не пересчитывать закрытый зарплатный период. Исправления отражать принятой моделью корректировок. Проверить отсутствие двойного начисления выручки при внесении/расходовании депозита и использовании подарочного сертификата.

## 10 Матрица приёмки

- Одна программа, три одновременно, собственная смесь; разные правила для одного гостя; отключённый блок не влияет на расчёт.
- Наиболее выгодная скидка, приоритет, ручной выбор, последовательное сложение, общий предел; фиксированная сумма больше базы, цена ниже нуля, разные eligible строки.
- Полночь, конец интервала, timezone, DST, 29 февраля, праздник вместе с днём рождения; изменение даты гостя не выдаёт повторный подарок.
- Каждый порог один раз, пересечение нескольких порогов, каждый N; общий стол, возврат, подарок, частично оплаченный заказ, разделение чека.
- Два кассира одновременно списывают последний бонус/подарок/бюджет; повтор запроса, timeout после commit, ошибка аудита, откат транзакции.
- Начисление/списание/истечение партий/сторно/изменение курса; деньги и баллы сходятся независимо.
- Изменение/пауза программы во время оплаты; прежние чеки не меняются, имеющиеся награды не пропадают.
- Роли owner/admin/manager/staff и реально существующие permission bundles; прямой API обход; подмена venue/guest/program ID; недоступность приватных групп.
- Уведомление без согласия, отписка, quiet hours, повтор consumer, сбой провайдера; отправлено не считается доставлено.
- Пустое заведение, legacy-данные, недоступный каталог, пустая аудитория, архивный товар; реальные пользовательские данные не используются как расходные тестовые фикстуры.
- Создание/изменение/включение после refresh; back/forward/deep link; клавиатура и экраны mobile/Fold/desktop, темы и ошибки.
- Подарок списывает склад один раз; возврат восстанавливает по выбранной модели; финансы и зарплата используют одни аллокации; закрытые периоды защищены.
- Нагрузочные замеры на согласованном наборе программ/гостей/строк; численные бюджеты latency/размера правил фиксируются в FL02 и проверяются в FL10.

Для каждого результата хранить среду, commit, сценарий, фактический результат и артефакт. Программный код проверяет code_health_engineer до и после изменений, навигацию принимает system_architect. Тесты из этого раздела запланированы на будущую реализацию; при сохранении плана не запускались.
