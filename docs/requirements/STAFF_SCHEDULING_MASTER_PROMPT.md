# Единый промпт: универсальное планирование смен

## Порядок запуска и границы

Этот документ объединяет согласованные требования к шаблонам времени, составам сотрудников и расширенному планированию. На момент создания подготовлен только план. Реализацию начать после команды пользователя продолжить работу после переключения модели. Настройки модели пользователь меняет самостоятельно.

Цель: довести основной объём ниже до работающего и проверенного локального результата на отдельной тестовой PostgreSQL. GitHub и VPS — последующий выпуск по отдельной команде пользователя. Не считать прежние разрешения на публикацию других изменений разрешением на этот выпуск.

Перед работой прочитай AGENTS.md, docs/AI_ORCHESTRATOR.md, docs/AI_TEAM.md, docs/AI_TEAM_WORKFLOW.md и необходимые профили .codex/team/roles. Координатор выбирает роли: product_analyst, system_architect, design_lead, backend_engineer, frontend_engineer, data_engineer, security, QA и code_health_engineer по фактическим ID team.json. Если нативное делегирование доступно, до трёх независимых агентов; иначе выполнить проверки последовательно, не изображая независимые ревью. Code health участвует до изменения кода и при итоговом diff.

Работай небольшими законченными этапами. Перед каждым этапом сверяй предыдущий результат, затем реализуй, проверь и обнови журнал. Не проси пользователя принимать обычные технические решения. Не выдумывай бизнес-правила оплаты или юридические нормы.

## Основной объём и последующее расширение

Обязательный локальный выпуск: шаблоны времени и составов; назначение рабочих функций; индивидуальные и ролевые значения по умолчанию; доступность; циклы; свободные смены; потребность в персонале и проверка покрытия; массовое применение и корректировки; полноценный календарь; права; история; печать и CSV; проверка на реальной тестовой БД.

Следующий выпуск, сейчас только документированные границы интеграции: заявки сотрудников на отсутствие, обмены и замены с согласованием, подтверждение ознакомления, доставка уведомлений, личные календарные подписки, прогноз расходов и автоматический подбор состава. Не показывать неработающие кнопки этих возможностей. Не называть их реализованными. Если соответствующая функция уже существует, использовать её совместимо после аудита.

## Сквозные правила

- Роль доступа, рабочая функция и шаблон времени — самостоятельные понятия. Бармен или кальянный мастер в смене не получают новые разрешения CRM автоматически.
- Названия, часы и имена не зашивать в код. Роман, Виктория, Борис — синтетические тестовые сотрудники.
- Один человек может выполнять несколько функций, но время не удваивается. По умолчанию одна единица его доступной мощности не покрывает два одновременно требуемых отдельных рабочих места. Совмещение допускается только по явно заданной модели потребности заведения; не складывать автоматически число функций.
- План не создаёт отработанное время, кассовую смену, начисление или выплату. Сохранить существующие границы payroll.
- Все сущности принадлежат заведению; проверки прав и принадлежности выполняются сервером.
- Пустая дата, выходной, отпуск, больничный и другая недоступность различаются.
- Ночной интервал проверяется целиком, включая следующий день. Даты трактуются в часовом поясе заведения.
- Изменение шаблона не переписывает созданные смены. Шаблон и исходные значения сохраняют проверяемую связь с применением.
- Сохранить существующий процесс черновик → предпросмотр → публикация и доступный ручной сценарий; не создавать второй независимый движок планирования.

## Этап 01. Аудит и изолированная среда

Промпт: выясни текущий опубликованный main и состояние подходящих worktree. Не переноси несвязанные изменения общего каталога. Выбери или создай изолированный worktree от актуальной основы, отдельно учти неопубликованную работу графика. Не сбрасывай её и не объявляй устаревший код актуальным без проверки. Найди реальные модули графика, шаблоны, черновики, миграции, права и API. Документы и прошлые сообщения — ориентиры, факты проверяй по коду.

Создай отдельную тестовую БД с синтетическими данными, отдельный локальный запуск и явный env. Перед любой записью проверяй идентичность тестового сервера и базы; отсутствие проверки блокирует запись. Исключи production env и копирование реальных персональных данных.

Результат: карта «уже есть / требуется расширение / пробел», абсолютный путь worktree, branch и commit, способ запуска, описание тестовой базы без секретов. Создай рядом с этим документом STAFF_SCHEDULING_PROGRESS.md и обновляй его дальше.

## Этап 02. Контракт данных, прав и сценариев

Промпт: архитектор фиксирует для каждого сценария UI → метод/API → DTO → права → транзакция → повторное чтение → ошибка → проверка. Разработай минимальное совместимое расширение существующих сущностей. Предусмотри версии, requestKey, аудит, архивирование, связь с серией, шаблоном и применением. Миграции должны учитывать существующие данные; подготовь восстановление на тестовой базе.

Владелец выдаёт admin/manager права. Согласуй с существующими grants просмотр, управление графиком, управление общими шаблонами/правилами и публикацию. Право чтения не разрешает запись; делегат не может выдавать себе права. Отзыв действует на сервере и в уже открытой сессии. Не раздавай новые права всем действующим менеджерам молча.

Результат: единый контракт и таблица миграционной совместимости; никакой параллельной несогласованной схемы шаблонов.

## Этап 03. Навигация и дизайн

Промпт: основная точка настройки — «График сотрудников → Настройки», внутри «Шаблоны», «Повторения», «Потребность», «Правила». Из общих настроек персонала сделай ссылку в тот же модуль. В карточке сотрудника размести функции, доступность и значения по умолчанию. Архитектор согласует фактические маршруты с SITE_TREE и общей оболочкой; не добавляй новый верхнеуровневый пункт для каждого подраздела.

Сохрани дизайн-систему, обе темы, единые формы и диалоги. Простой сценарий требует названия и времени; расширенные поля раскрываются по необходимости. Покажи название, часы, состав и архивный статус шаблона. Для каждого экрана предусмотрены загрузка, пустое состояние, ошибка, повтор, отсутствие прав, несохранённые изменения и конфликт версии. Телефон: карточки вместо широких таблиц; клавиатура, подписи, фокус, доступные размеры кнопок. Цвет дополняет текст, не заменяет его.

Результат: описанные состояния и согласованная структура интерфейса до крупных UI-правок.

## Этап 04. Рабочие функции и шаблоны

Промпт: реализуй справочник рабочих функций и допустимые функции сотрудника с повторным использованием существующей модели, где возможно. Пользовательская роль «Утренний сотрудник» продолжает работать. Системный код hookah_master отображай как «Кальянный мастер»; не переименовывай произвольные пользовательские должности и данные сервера массово.

Поддержи шаблон времени без сотрудников и шаблон состава с одним или несколькими людьми. Поля: название, начало, окончание и смещение дня, перерывы, функция/функции, необязательное примечание. У участников группы свои часы. Разреши дублирование и архивирование, поиск и временное исключение участников при применении.

Приоритет подстановки: явный выбор → персональное значение → единственный подходящий ролевой шаблон. При нескольких вариантах запроси выбор в форме; без вариантов оставь ручной ввод. Не затирай уже введённое вручную время при асинхронной загрузке или смене сотрудника без понятного действия пользователя.

Результат: создание/изменение/чтение шаблона через UI и БД; изменение шаблона не меняет прошлые применения.

## Этап 05. Доступность и ограничения

Промпт: реализуй повторяющиеся окна доступности по дням недели и разовые исключения с периодом действия. Отдели предпочтение от недоступности; утверждённые отсутствия учитывай через существующую модель. Для ночной смены проверяй обе даты. Для каждого запрета показывай причину и интервал.

Правила заведения: предупреждения о максимальной плановой нагрузке, минимальном промежутке отдыха, числе последовательных дней, работе вне часов заведения. Значения задаёт владелец; не называй их юридически корректными нормами без отдельного анализа. Жёсткие конфликты пересечения и принадлежности нельзя обойти. Допустимые предупреждения можно подтвердить с причиной и аудитом согласно правам.

Результат: планировщик видит доступных людей и объяснение конфликтов. Самообслуживание сотрудника с заявками пока остаётся будущим расширением.

## Этап 06. Повторения и серии

Промпт: поддержи дни недели, циклы 2/2, 3/3, 5/2 и пользовательскую последовательность рабочих дней/выходных. У серии есть дата начала, конец/ограниченный горизонт, персональное смещение цикла и исключения. Не генерируй бесконечные записи. Существующие ограничения диапазона API учитывай явно.

Применение к месяцу или диапазону сначала показывает даты, людей, число смен, часы и конфликты. Редактирование серии позволяет выбрать одну смену, выбранные даты либо будущую часть серии; прошлое и персональные исключения не перезаписываются незаметно. Повтор применения защищён от дублей; изменение цикла не сдвигает уже подтверждённые исключения без предпросмотра.

Результат: построение текущего и следующего месяца, включая переход месяца/года и корректировку серии.

## Этап 07. Потребность, свободные смены и покрытие

Промпт: настрой интервалы потребности по рабочим функциям, количеству людей, дням недели и разовым датам; учитывай часы работы, подготовку до открытия и завершение после закрытия. Создай свободную смену без сотрудника, которую можно назначить позднее. Не создавай фиктивного пользователя для свободной смены и не включай её в персональные часы.

Покажи нехватку по интервалам, незакрытые смены и лишний состав. Учитывай перерывы и совместимость функций. Один человек с двумя навыками не закрывает автоматически две отдельные требуемые позиции. Для замены предложи подходящих людей с объяснением доступности, функции и нагрузки; окончательное назначение делает уполномоченный пользователь. Автоматический оптимизатор не требуется.

Результат: сценарий «нужны два мастера и бармен» выявляет дефицит и позволяет закрыть свободное место без двойного подсчёта Романа.

## Этап 08. Календарь и массовые действия

Промпт: сохрани представления месяц/неделя/день/список. Неделя — люди и даты; день — шкала с функциями и покрытием; месяц — смены, отсутствия и часы; телефон — список дней и карточки. Добавь быстрый выбор даты, следующего месяца, фильтры людей/функций и индикацию черновика.

Сценарий «Добавить по шаблону»: дата/диапазон → шаблон → редактируемый состав и часы → предпросмотр конфликтов → явное применение. У группового шаблона можно снять галочку с человека без создания нового шаблона. Массовые операции: копирование периода, изменение времени выбранных смен, отмена с причиной. При конфликте не сохраняй незаметно часть группы: исправление или явное исключение строк, новый предпросмотр и атомарное применение.

Сохраняй пользовательский ввод при сетевых ошибках. Проверяй актуальность preview при применении; устаревший preview, архивирование сотрудника и изменение графика параллельным редактором требуют повторного просмотра. Защити повторы после таймаута.

Результат: календарь → действие → API → тестовая БД → обновление страницы, без дублей и потерянных правок.

## Этап 09. Публикация, история и вывод графика

Промпт: интегрируй новый функционал в существующие черновики и публикацию. До подтверждения покажи, что будет добавлено/изменено/отменено и кого затронет. Сохраняй историю автора, времени, причины и версии; для массового действия сохраняй связь записей с пакетом.

Добавь печатный график и CSV с читаемыми датами, часовым поясом, периодом, статусом и временем формирования; защищай CSV от выполнения формул из пользовательских полей. Экспорт соблюдает права и не включает лишние персональные данные. Не называй CSV полноценным XLSX.

Опиши точки интеграции для будущих уведомлений и подтверждений ознакомления: событие публикации/изменения, адресаты, дедупликация и версия графика. Не отправляй сообщения внешним получателям и не добавляй фиктивную отметку «уведомлён».

Результат: доступный только уполномоченным пользователям опубликованный график, проверяемая история и пригодная для печати/выгрузки версия.

## Этап 10. Приёмка на тестовой PostgreSQL

Промпт: создай два синтетических заведения, владельца, admin/manager с разными grants, сотрудника без управления, пользовательскую роль и Романа/Викторию/Бориса. Создай шаблоны: Роман 10–17; вечерняя команда Виктория 17–23 и Борис 18–02; персональные варианты и шаблон времени без состава.

Проверь реальным UI и API с чтением из БД:

1. CRUD/архивирование/копия шаблонов, ручное время и неоднозначная подстановка.
2. Группа и один участник, персональные часы, функция без изменения прав.
3. Цикл со смещением, выходные, исключения, следующий месяц, граница года, ночной интервал.
4. Доступность, отсутствие, перерывы, дефицит и свободная смена, отсутствие двойного покрытия/часов.
5. Черновик и публикация, повтор запроса, таймаут после успешной записи, атомарный отказ группы.
6. Параллельное редактирование, устаревший preview, архивирование сотрудника между preview/apply.
7. Изоляция заведений, подмена ID, отзыв прав в открытой сессии, запрет выдачи себе grants.
8. Редактирование одной смены и будущей части серии, сохранение прошлых записей и исключений.
9. Reload и перезапуск приложения; печать/CSV и приватность данных.
10. Совместимость старого ручного графика и сохранение границ факта/payroll/кассы.

Проверь миграцию существующей тестовой схемы и повторный запуск, восстановление тестового backup. Проверки должны выявлять реальные ошибки, а не повторять реализацию. Каждое PASS подкрепи результатом; не заменяй E2E статическим анализом. Запускай релевантные проверки и обязательные контракты проекта, расширяй набор при обнаружении регрессий.

Результат: матрица PASS/FAIL/BLOCKED, доказательства основных путей, все дефекты основного объёма устранены либо честно оставлены незавершёнными.

## Этап 11. Визуальная проверка и локальная передача

Промпт: проверь обе темы и ширины 375/768/1440, длинные имена, много сотрудников, большое число смен, пустые/ошибочные состояния, мобильный редактор, фокус и клавиатуру. Сохрани снимки и проверь их визуально. Выполни code-health review итогового diff, исключи секреты, случайные файлы и несвязанные изменения, синхронизируй только относящиеся published assets по правилам проекта.

Подготовь инструкцию владельцу и отчёт: что реализовано, точные проверки, путь/команда запуска, ветка/commit, миграции, остаточные ограничения. Отдельно подготовь план будущего выпуска с backup, восстановлением, совместимостью старого приложения с новой схемой и production-проверками после выпуска. Сам выпуск сейчас не выполнять.

Результат: пользователь может открыть локальную систему и пройти все основные сценарии. Цель завершена только после выполнения этапов 01–11; будущие функции не считать недоделками основного объёма.

## Этап 12. Последующий выпуск — отдельная команда

После команды на публикацию обнови основу main, разреши конфликты с сохранением чужой работы, повтори затронутые проверки, выполни GitHub workflow и прикрепи PR. Для VPS пройди действующий release workflow, backup/restore rehearsal, миграционные проверки и контроль после выпуска. Не удаляй контейнеры, тома или данные вне релиза. Этот этап не является разрешением на публикацию сейчас.

## Формат журнала и продолжения между моделями

В STAFF_SCHEDULING_PROGRESS.md храни этапы 01–12 со статусами NOT_STARTED/IN_PROGRESS/PASS/BLOCKED/DEFERRED. Для каждого: результат, файлы, проверки, артефакты, нерешённые вопросы.
