# POS item sale attribution contract

## Scope

This POS package records who added each order item and when it was added. It does not calculate payroll, allocate discounts, or model refunds.

## Write rules

- The seller is the authenticated employee in the request session. The client cannot set or override `salesEmployeeId` or `soldAt`.
- A new item write requires an active employee session and a seller eligible for the order venue under the existing venue/organization membership rules.
- `sold_at` is generated by the server/database in UTC at the time the item is added.
- Each add action creates its own order item row, including repeated additions of the same product and price. It must not merge into an older row because that would lose the event's seller and time.
- Reducing quantity or deleting an existing row preserves its original seller and time. An increase is not permitted through `PATCH`: it returns `409 quantity_increase_requires_new_line`. Adding another portion uses a new `POST` add action and row, attributed to the authenticated seller and server/database time.
- New rows store seller and time together. Historical rows can keep both fields NULL; the POS must present those rows as unattributed and must not infer an employee from the order opener.

## Read contract

Order item responses include `salesEmployeeId`, `salesEmployeeName`, and `soldAt`. `soldAt` is an ISO timestamp representing UTC. Existing un-attributed rows return null attribution fields.

## Storage

Fresh installations receive the columns and validation trigger from `schema.sql`. Existing installations receive them from migration `084_order_item_sales_attribution.sql`. The nullable pair check preserves historical data; the trigger validates active employee and venue/organization eligibility for attributed rows.

## Payroll handoff

Payroll coverage must treat legacy rows with NULL attribution as unknown and exclude them from employee-specific credited sales until a separately approved remediation policy exists. Payroll calculations, official run blocking, discounts, and refunds are outside this POS package.

## Demo-only attribution

The static local POS adapter may create `salesAttributionStatus: "demo_unverified"` records using the employee in local browser storage and a browser clock. The floor UI labels those seller and time values as demo/unconfirmed and local. They are not authenticated POS events, are not written to PostgreSQL, and must never enter payroll or finance source coverage. Only the authenticated PostgreSQL write path above is canonical.

## Payroll source limits

The order-item API exposes the line `id`, `productId`, `salesEmployeeId`, `salesEmployeeName`, and database `soldAt`; `orderId` is the parent order key and must be joined from the order context. The current item record does not provide a stable department ID, immutable net cents allocated after discounts, a line-linked refund/reversal ledger, or a versioned net cost snapshot. Payroll must not derive these from `station`, catalog labels, current order totals, or browser demo metadata. Official runs remain blocked until the responsible POS/loyalty/finance sources provide reconciled line-level values and lineage.
