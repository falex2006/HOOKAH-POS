# Дымовой фон входа и PIN

## Принятое решение — 2026-10-01

Пользователь явно разрешил: «Использовать выбранный ролик с водяным знаком». Выбранный Magic Hour MP4 включён в итоговый пакет без изменения ролика или удаления знака. Прежнее ограничение local-only preview и ожидание другого чистого/8-секундного клипа для этого выпуска отменены данным решением.

- Источник: выбранная локальная проба `login-smoke-preview-watermarked.mp4`.
- Канонический ресурс: `/assets/login-smoke-ambient.mp4`.
- H.264, 854×480, 24fps, 3.041667 секунды, 73 кадра, без аудио, 251421 байт.
- SHA256 MP4: `11504365180f86adea29ce4e5517938bf62e61e644274fa3e618f7f5d83bc75c`.
- PNG fallback SHA256: `facb22e95581b26f43f0ddf6d9cda0a54a7fa7ea9645070e46421c7bf42461e1`.

## Контракт

Вход по паролю, доверенный PIN и блокировка рабочего места используют одинаковый backdrop и единый контроллер. Видео декоративное, muted/loop/playsInline, poster сохранён; фон не принимает клики. Форма находится поверх дыма и остаётся читаемой. Login центрируется; на низком экране доступна вертикальная прокрутка. PIN-клавиатура и выход доступны на узком экране.

Видео создаётся только для видимого экрана при обычном motion preference. Первоначальный reduced motion не создаёт video и не запрашивает MP4; остаётся статичный PNG. Скрытый PIN и скрытая вкладка ставят playback на паузу. Ошибка медиа или отказ autoplay сохраняют неподвижный PNG без drift-анимации. Изменение предпочтения учитывается; повторная загрузка контроллера не создаёт дубликатов или бесконечных MutationObserver callbacks.

Ресурсы доступны обычному runtime по закрытому allowlist, включены в assets/dist/Docker. MP4 поддерживает HEAD, полный GET, одиночный byte Range206; ошибочные диапазоны дают416. tmp, env и git не попадают в Docker build context.

## Сессии и cookie в локальном и HTTPS окружении — 2026-10-05

Сервер выдаёт `crm_session` и `crm_device_id` как host-only cookie с `Path=/`, `HttpOnly` и `SameSite=Lax`. Атрибут `Secure` задаётся только явной настройкой `COOKIE_SECURE=true`; сервер не определяет HTTPS по `X-Forwarded-Proto`. Поэтому TLS reverse proxy должен работать с `COOKIE_SECURE=true`. Пример Nginx перенаправляет HTTP на HTTPS и передаёт `X-Forwarded-Proto https`; это полезно для приложения, но само по себе не включает Secure-cookie.

| Окружение | Настройки | Ожидаемое поведение |
|---|---|---|
| Локальный loopback HTTP в memory-only QA | `COOKIE_SECURE=false`; тестовые `AUTH_REQUIRED`/учётные записи задаются самим QA runner | Cookie остаются HttpOnly/SameSite=Lax/Path=/, атрибут Secure отсутствует, чтобы браузер мог отправлять их по локальному HTTP. Этот режим не является настройкой обычного HTTPS-развёртывания. |
| Приложение за TLS Nginx reverse proxy | `AUTH_REQUIRED=true`, `COOKIE_SECURE=true` (значение по умолчанию в `.env.example` и Compose) | HTTP перенаправляется на HTTPS; обе cookie имеют Secure. Путь и host-only область не меняются; приложение не публикует сессию на соседние поддомены. |
| Явно разрешённое HTTP-only развёртывание | `COOKIE_SECURE=false` и одноразовый `ALLOW_HTTP_DEPLOY_ONCE=true` только при запуске deploy-скрипта | Preflight печатает предупреждение; без одноразового opt-in deployment блокируется. Это исключение не следует использовать за TLS proxy. |

Обычная сессия и сессия сотрудника живут 12 часов. Флаг доверенного устройства разрешён ролям owner/admin/developer, продлевает их сессию до 30 дней и сохраняет требование PIN при возврате на заблокированный экран; отправленный сотруднику trust-флаг не продлевает его сессию. `crm_device_id` живёт один год и связывает сессии браузера с устройством, но не является credential. Logout отзывает серверную сессию и истекает `crm_session`; cookie идентификатора устройства остаётся. `SameSite=Lax` описывает same-site web-сценарий; межсайтовое встраивание CRM и shared-cookie между поддоменами в поддерживаемый контракт не входят.

Локальный memory-only runtime сравнил оба значения `COOKIE_SECURE` и проверил атрибуты login/logout cookies; `local-deploy-contract.mjs` проверяет HTTPS-шаблон и запрет небезопасного deploy без одноразового opt-in. Фактический внешний TLS endpoint здесь не проверялся.

## Проверки

- CUA browser: readyState4, paused=false, muted/loop, 854×480; наблюдался переход времени 2.980723 → 0.061045, то есть реальный повтор.
- Login/PIN desktop1280×800, mobile375×667 и низкий login320×480: без горизонтального переполнения. PIN-клавиатура разблокирует; после скрытия video paused=true. Неверный PIN показывает ошибку, доверенный PIN возвращает правильного пользователя.
- Browser fixture с MP4404: video-fallback, display:none, PNG animationName:none; поля доступны. Отдельный fixture с reduced-motion preference до загрузки контроллера: video отсутствует; смена preference создаёт video, readyState4; обратная смена ставит на паузу. Это QA-моделирование matchMedia, а не изменение системной настройки устройства.
- Lifecycle VM QA дополнительно выполняет начальный скрытый PIN, pause/resume, media error, play rejection, detach/reconnect, двойную загрузку и сходимость observer.
- source/dist byte parity и HTTP Range QA пройдены на локальном сервере и запущенном Docker runtime.

Первый и последний кадр не идентичны: средняя абсолютная разница RGB2.607/255 (средняя соседних кадров0.984). Композиция сохраняется; математически идеальный бесшовный цикл и качество выше выбранных480p не заявляются. Водяной знак виден на desktop и частично обрезается object-fit на узком экране. Замена клипа остаётся отдельной возможной задачей, а не блокером одобренного выпуска.
