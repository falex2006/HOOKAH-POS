# API предварительного просмотра зарплаты по данным системы

**Статус:** локальный owner-only HTTP-маршрут подключён; candidate-only API проходит локальную проверку. Полная payroll E2E и официальный расчёт остаются отдельными этапами. Это не разрешение создавать начисления.

## История допуска сотрудников

`GET /api/payroll/employment-eligibility` возвращает текущую owner-attested ревизию с датированными интервалами и до 30 последних заголовков ревизий. `POST /api/payroll/employment-eligibility` принимает только `{ "reason", "idempotencyKey", "periods" }`, где каждый период содержит `employeeId`, `effectiveFrom` и nullable `effectiveTo`. Точные повторы возвращают исходную ревизию; повтор ключа с изменённым содержимым получает `409`. Пересекающиеся периоды одного сотрудника запрещены, раздельные интервалы повторного найма сохраняются. Изменение создаёт полную новую ревизию; история неизменяема.

Оба маршрута доступны только владельцу аутентифицированного заведения; GET не принимает tenant/query override, POST требует same-origin/CSRF boundary. Employee и actor связи tenant-scoped. Новый источник подтверждает только допуск к зарплатной области, а `payroll_role_assignments` остаются версионируемыми ролями/ставками. Никакие предыдущие даты из текущего статуса пользователя не выводятся. API не создаёт payroll run, entry, expense или выплату. Пока UI редактирования источника и калькуляторной поддержки исторических интервалов не готовы, источник нельзя считать завершённой зарплатной функцией.

## Контракт

`POST /api/payroll/versions/:id/preview/sourced`

Тело запроса допускает только два поля:

```json
{"periodFrom":"2026-10-01","periodTo":"2026-10-31"}
```

Обе даты должны быть реальными датами одного календарного месяца; `periodFrom` — первое число месяца. Клиент не передаёт сотрудников, продажи, DTO источников, валюту, площадку, source policy, watermark, сценарий или суммы. Версия схемы и площадка разрешаются сервером по аутентифицированной owner-сессии.

Версия, timezone, readiness и recognition manifest читаются в одной `REPEATABLE READ READ ONLY` транзакции. В ответ включаются доступные подтверждённые source observations, отдельная кандидатная проекция признанных строк продаж/возвратов и явное состояние всех семи режимов расчёта. `status`/`sourceStatus` агрегирует статусы компонентов readiness; `projectionStatus` описывает только признанную проекцию. Watermark имеет `watermarkScope: "sourced_payroll_candidate_input_fingerprint"`: он фиксирует согласованные входы, но сам по себе не удостоверяет полноту источников.

В `sources.orderRevenueReconciliation` находится owner-only диагностика закрытых заказов за период по локальной дате закрытия. Она связывает canonical pricing snapshot с признанными payroll sale lines и отдельно показывает общую сумму заказа, чистую стоимость строк, минимальную корректировку и остаток. Если снимок, sale event или строки отсутствуют либо не сходятся, статус становится `incomplete`, агрегатные итоги `null`, а закрытый заказ остаётся в знаменателе. Legacy сумма без canonical snapshot не выдаётся как сверенная. Поле candidate-only, `officialReady:false`, `persistence:'none'`; оно не передаётся в калькулятор, не атрибутирует минимальную корректировку сотрудникам и не открывает личный лимит. Возвраты остаются отдельными событиями признания и не вычитаются из закрытого чека.

`modes[mode].calculationStatus` остаётся `unavailable`, а `modes[mode].amount` — `null`: официального запуска по зарплатным периодам ещё нет. Отдельный `candidateCalculation` выполняет owner-only in-memory preview для выбранной сохранённой версии, если полный source bundle прошёл строгую проверку. Готовый расчёт сопровождается `candidateSnapshot`: source-bound DTO с полными typed line details и отдельными SHA-256 результата/снимка. Он существует только в памяти ответа, `persistence:none`; заблокированный расчёт или возврат дают `candidateSnapshot:null`. Отдельный `POST /api/payroll/compare/sourced` выполняет сравнение candidate-расчётов на общем серверном source snapshot и включает per-version snapshot только при совпадении общего raw-source watermark. Это не сценарный JSON endpoint `POST /api/payroll/compare` и не official run. Candidate путь допускает только период без возвратов: manifest должен быть доступен, список сырых refund events и пересчитанных refund adjustments — пустым, а projection/readiness watermarks — совпадать. Любой возврат закрывает wage calculation, потому что правила применения подписанных корректировок ещё не утверждены.

Сценарий использует тот же детерминированный `calculatePayrollScheme`, но его результат отдельно помечен `candidateOnly`, `nonPayable`, `nonAccrual`, `payoutEligible:false`, `officialReady:false`. При недостатке любого обязательного источника `candidateCalculation.status="blocked"` и `amountCents:null`; иначе `status="scenario_ready"` содержит временную сумму и детализацию сотрудник/день/строка. Если у схемы есть item rules, каждая строка продажи обязана иметь UUID товара из immutable source facts, иначе расчёт блокируется вместо применения базовой ставки. UI явно показывает, что сумма не начислена и не к выплате. Верхний уровень сохраняет `calculationStatus:"unavailable"`, `amount:null` и `officialReady:false`.

`modes[mode].inputStatus`, `requiredFacts` и `facts` дают матрицу источников; `configurationStatus` отдельно показывает owner acknowledgment. Общие факты — продажи, политики, признанные возвраты, подтверждённый допуск сотрудников и покрытие их ролей. Табель требуется режимам со сменной оплатой, attendance-зависимыми milestone и распределением фонда по минутам; процентный режим без таких зависимостей может пройти входной gate без attendance. Личная net-выручка требуется, когда сохранённое owner-подтверждение включает абсолютный предел выплаты личной выручкой. Department attribution требуется режимам/ограничениям, которые используют цех. Venue daily turnover требуется progressive/final-month режимам и любой конфигурации с venue-day cap или включёнными milestone. Final-month отдельно требует закрытый полный месяц; team-fund и margin — свои факты цеха/распределения и cost snapshots. Конфигурация роли и личные mode/cap/milestone overrides учитываются при выявлении этих зависимостей. Исторический допуск сотрудника читается из owner-attested ревизии и fail closed при её отсутствии или нарушении целостности; employee/role coverage, immutable department attribution, margin costs и refund-consumer расчётов пока не подключены как authoritative факты для расчётов. Venue daily turnover подключён только как отдельный candidate-only источник для зависимых режимов; он не подтверждает официальную готовность. Полная чистая стоимость товаров по сотрудникам доступна как отдельная candidate-only серия, но не входит во вход payroll calculator. Неполные и неподдержанные источники сохраняют причины и статусы; неизвестное значение не становится нулём. Отдельные валидированные строки и события можно показать как evidence, но их частичные суммы не называются итогами сотрудника за месяц и в envelope остаются `null`, пока не подтверждена полная coverage. Endpoint не создаёт calculation run, snapshots, adjustments, `payroll_entries`, expenses, payouts и не изменяет POS/payment/loyalty/shift журналы.

`calculationInputContract` — read-only gate между этими источниками и калькулятором. Он принимает только внутренний server-owned bundle, связанный с tenant/version/currency/period и fingerprint readiness; каждый компонент обязан иметь свой watermark и scope. Employee roster и интервалы сверяются с точной ID owner-attested ревизии. Движок поддерживает подтверждённые непересекающиеся интервалы повторного найма (`historicalEmploymentIntervals:true`). Для scenario preview проверенная серия full employee net может быть прочитана как отдельное evidence, но не передаётся калькулятору; официальный purpose сохраняет `fullEmployeeNetRevenue:false` и `signedRefundAdjustments:false` blockers. Candidate input возвращается только для доказанного периода без возвратов; этот исключительный preview не меняет official readiness.

Отдельная `sources.fullEmployeeNetRevenue` показывает кандидатную серию **«Чистая стоимость товаров по сотрудникам»**: сумма строк товаров после распределённых скидок на дату признания продажи и минус стоимость возвращённого товара на дату признания возврата, зачисленная продавцу исходной строки. Для периода с полностью подтверждённым manifest серия содержит sparse employee/day строки и построчную lineage; отсутствие event-day для сотрудника, уже представленного в серии, означает ноль только для этого товарного показателя. Источник не содержит roster и не перечисляет сотрудников без товарных событий, поэтому отсутствие сотрудника в `daily` ничего не говорит о трудоустройстве, выходе, комиссии или праве на выплату. Полное отсутствие событий даёт `amount: 0` лишь когда manifest доказывает покрытие периода. При неполной/неподдержанной проекции `amount` остаётся `null`, `daily` пустой. Это не база комиссии, сумма зарплаты или бухгалтерская прибыль; серия не попадает в `calculatorInput`, не включает зарплатные ограничения и не создаёт run/entry/expense либо ledger-записи. Watermark серии повторно вычисляется из manifest, выбранной политики и lineage.

`sources.refundReview` отдельно показывает владельцу signed стоимость подтверждённых товарных возвратов: строки возвратов и сводку по исходному сотруднику и дате признания, с ID исходной строки и датой исходной продажи, включая продажи до выбранного периода. Для доступной сводки `impactStatus` обязан быть `not_applied`; суммы не применяются к зарплате. Интерфейс проверяет сверку сводки с исходными строками до отображения и ограничивает DOM 500 сводочными строками, сохраняя полный периодный итог. Это справка об изменении стоимости товара, не зарплатное удержание. Возвраты не применяются к candidate calculation; не создаются долг, перенос остатка, корректировка, run, payroll entry или расход. Если полное покрытие источника не подтверждено, `rows` и сводка пусты, а `totalMerchandiseNetRevenueDeltaCents` равен `null`. SHA-256 watermark этого обзора включён в fingerprint sourced preview.

## Локальная проверка и границы готовности

### Кандидатный источник дневного оборота

Если выбранный режим/owner-конфигурация требует venue/day turnover, сервер в той же owner `REPEATABLE READ READ ONLY` транзакции добавляет в `sources.venueDailyTurnover` отдельную серию из закрытых заказов. Порядок суммы: canonical pricing snapshot → сохранённый `final_total_snapshot` → помеченный Finance-safe legacy fallback. Неизвестные суммы и несогласованные canonical snapshots блокируют серию. Покрытие дат для дневного оборота проверяется независимо от покрытия построчных продаж; timezone, валюта, период и source watermark связываются отдельно. Watermark SHA-256 — candidate evidence, не доказательство полноты. `refundsIncluded:false`: это pre-refund venue turnover, не чистая товарная выручка сотрудника. Источник не входит в readiness как всеобщий POS факт, не открывает calculator input и не разрешает официальный run.

- Контракт сервиса и границы с финансовыми данными сверены с MASTER и финансовым координатором; системный архитектор одобрил owner-only маршрут.
- Повторно сверены границы source-input пакета с MASTER, Finance и system architect. Поздний возврат остаётся товарной стоимостью по `recognized_event_date`; без замороженной payroll policy и исходной credited run-line он не становится зарплатной корректировкой. `original_sale_period_correction` остаётся недоступен без immutable correction lineage.
- Mode availability matrix — только gate по readiness, не calculator input и не расчёт. Даже если все required facts отмечены available, сумма остаётся `null`, пока отдельная интеграция калькулятора не принята.
- `payroll-calculation-input-contract.js` описывает/проверяет source bundle и возвращает `calculatorInput:null` при отсутствующем, несогласованном или неподдерживаемом evidence. Его текущий contract проверяется `scripts/payroll-calculation-input-contract.mjs`.
- Route contract проверяет дополнительные поля, неподходящий метод, owner/CSRF guards и поведение ошибок до создания ответа.
- `payroll-scheme-browser-postgres-qa.mjs` прошёл через guarded local runner: реальная owner-сессия, PostgreSQL, tenant/role isolation, readiness, sourced preview, стабильный watermark и неизменность runs, `payroll_entries` и expenses.
- Тот же browser сценарий проверяет сохранение/перезагрузку/активацию owner-конфигурации и UI на ширинах 320, 375, 768 и 1440 px. Он работает на синтетической временной схеме БД.
- Это только промежуточный preview. Готовность к официальному запуску требует отдельного end-to-end калькулятора, полных source contracts всех сотрудников/дней, immutable snapshots, сравнения режимов на одном снимке и run→entry→expense lifecycle.
# Сравнение версий на серверных источниках

Owner-only `POST /api/payroll/compare/sourced` принимает строго четыре поля: `versionIds` (2–8 уникальных UUID), `baselineVersionId` (UUID из списка), `periodFrom`, `periodTo`. Клиентские продажи, табель, предварительные расчёты и JSON-сценарий не принимаются. Версии читаются сервером в одной транзакции `REPEATABLE READ READ ONLY`; каждая проекция рассчитывается последовательно на одном MVCC-срезе.

Для запроса только из legacy v1 версий ответ имеет `comparisonKind: sourced_candidate`, `candidateOnly: true`, `officialReady: false`, `persistence: none`. Для доступных сравнимых версий возвращаются кандидатная сумма и разница с явно выбранной базовой версией; для заблокированной или несопоставимой версии сумма и разница равны `null`. Отсутствующие значения не трактуются как ноль. Общий `sharedSourceWatermark` строится по объединению raw-фактов, требуемых режимами сравниваемых версий. Факт, не нужный конкретной версии, может быть прочитан только другой версией, но чтение всё равно происходит в том же `REPEATABLE READ` снимке; все фактические watermark одного типа должны совпасть, а у каждого нужного raw-факта должен быть хотя бы один корректный SHA-256. Если общий набор не подтверждён, watermark и расчётные суммы не выдаются. Policy-derived projection/input watermarks остаются отдельными и могут различаться между версиями.

Сценарное `POST /api/payroll/compare` остаётся отдельным пользовательским JSON-сценарием. UI использует отдельную кнопку и не передаёт JSON в sourced endpoint.

### Сверка личной товарной выручки в candidate snapshot

Перед выдачей `candidateSnapshot` сервер заново строит `fullEmployeeNetRevenue` по immutable recognition manifest и сохранённой политике схемы, сверяет весь объект и watermark компонента. Затем суммы `calculatorInput.sales.turnoverCents` сверяются с источником и с `daily.employees.personalRevenueCents` по сотруднику и дню. Отсутствующий источник, расхождение, небезопасное целое или пропущенный день сотрудника с исходными строками не допускают построения снимка. Отсутствующая строка дневной выручки означает ноль только при подтверждённой полной серии источника и сверке всех продаж.

`candidateSnapshot.personalRevenueReconciliation` содержит `status: matched`, `scope: no_refund_merchandise_net_only`, `sourceWatermark`, `amountCents` и `employeeDayCount`. Поле входит в `snapshotWatermark`. Оно подтверждает согласованность товарной выручки в текущем сценарии без возвратов. Оно не объявляет эту сумму полной базой абсолютного потолка зарплаты и не включает official calculation или запись начисления.

## 2026-10-19 — Margin candidate source binding

For a saved configuration requiring `marginCosts`, the existing owner-authorized repeatable-read/read-only source transaction verifies migration187 capability, reads each recognized order through `readSaleCostEvidence`, and passes verified results to `buildPayrollMarginCostSource`. Other configurations do not query the cost producer. Missing schema yields unsupported; incomplete, unknown or refund-linked sources do not become zero cost.

Internal source bundle fields: `marginCostEvidenceByOrder` (verified producer reader results) and `marginCostSource` (exact recognition/product/quantity/order-total binding). They are included in the input hash and independently rebuilt/compared by the calculation input contract. `components.marginCosts` must match readiness and rebuilt source. `calculatorInput.sales[].costSnapshot.costCents` is full line cost, not unit cost.

A margin `candidateSnapshot.lines[]` includes `costSnapshot`, `signedMarginCents`, `costSourceWatermark` and `producerWatermark`; the calculated line must match source cost exactly and its signed margin must equal commission base minus cost. Role-specific non-margin lines do not expose cost as part of their calculation. The existing candidate snapshot hash includes these fields. Official input remains explicitly blocked with `payroll_margin_cost_candidate_evidence_not_official`; no run, entry, expense or payout is created by preview.

Pure integration proves12500 net minus2500 cost at10%=1000, replace/additive revenue commissions, non-margin role override, cost/hash/product tampering and linked-refund rejection. Real PostgreSQL acceptance is recorded separately in WORK_LOG; pure evidence alone is not HTTP-chain acceptance.


## Сравнение с учётом возвратов: DTO v2 (2026-10-23)

Если хотя бы одна сохранённая версия использует sourcePolicies.schemaVersion=2, тот же endpoint возвращает schemaVersion=2, comparisonKind=sourced_candidate_v2 и results. Тело запроса, owner/tenant/same-origin проверки и лимит 2–8 версий сохраняются. Настройки берутся только из сохранённых версий.

Одна fenced REPEATABLE READ READ ONLY транзакция собирает общий recognition manifest, экономику возвратов, eligibility и объединение необходимых attendance/department/frozen-cost источников. Каждый raw источник читается однократно; индивидуальные расчёты используют одну исходную выборку. Отсутствие необязательного для другой схемы источника блокирует только зависимые схемы.

Возвраты уменьшают товарную базу исходной продажи по явно выбранной v2 policy. Legacy v1 после возврата остаётся заблокированным. Для смешанных policy family разница равна null; при заблокированной базе собственная доступная сумма другой схемы остаётся видимой, разница null. Отсутствующий сотрудник означает неизвестное значение, а не ноль. Margin использует замороженную себестоимость исходной продажи только для зарплатной мотивации, refundAdjustedReady=false.

Результат — прогноз до входящих корректировок: candidateOnly/nonPayable/nonAccrual=true, officialReady/payoutEligible=false, persistence=none. Не создаёт run, начисление, расход, выплату, claim или settlement. UI показывает сотрудников, суммы, различия и причины блокировок.

Полный интегрированный PostgreSQL/UI прогон78201 прошёл: семь режимов, исходные/частично/полностью возвращённые продажи, mixed v1/v2, source hashes и неизменность денежных записей. Дополнительная foreign-owner HTTP проверка фиксируется отдельным итогом в payroll-current-integration-acceptance.json.
