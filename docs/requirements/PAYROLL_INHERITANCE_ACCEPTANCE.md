# Payroll: матрица наследования параметров

Сверка 2026-10-03 по исходному ТЗ: каждый параметр независимо назначается по роли или персонально; явный ноль отличается от наследования. Официальные источники и выплаты этим документом не принимаются.

Для каждого поддержанного параметра требуется доказать: наследование, личное значение, изменение роли, личный ноль/false, возврат к роли, включительные даты, сохранение/перезагрузку и расчёт. Наличие общего helper само по себе не доказывает всю матрицу.

Дополнительные доказательства: `payroll-parameter-inheritance-contract.mjs` — 23 случая фактического calculator во всех семи режимах с независимо ожидаемыми суммами, датами, inherit и сменой роли. Расширенный `payroll-personal-threshold-postgres-contract.mjs` — 15 типов путей через create/read/edit/read/new-version/activate/read, точные нули/boolean/string, даты, сохранение параметров роли и отсутствие posting. PG-проверка не доказывает математику каждого режима; её проверяет отдельная pure матрица. Browser-матрица сохранения 15 поддержанных путей принята в указанной ниже области; расчёт на официальных источниках остаётся незавершённым.

## Независимость режима и премий

Личный override `mode` меняет только режим. `applyMilestones` отдельно наследует явное значение роли, затем схемы, затем default исходного режима роли. Поэтому progressive → личный stable сохраняет включённые премии, а stable → личный progressive сохраняет выключенные, если личный флаг не задан. Это следует требованию ТЗ о независимом назначении каждого параметра; автоматический сброс премий при личной смене режима нарушил бы эту независимость. Порядок личных mode/apply overrides не меняет результат.

Подпись личного параметра исправлена в UI rev14: показывает наследуемое значение и источник на дату начала настройки, учитывает role/scheme/mode default и несохранённые поля роли. Для пробела/пересечения назначений значение не выдумывается. Личный режим не переключает премии автоматически. Подпись не заявляет одно значение на весь период, если роль меняется внутри него. Ошибка постороннего поля не скрывает независимо определимое значение; общая валидация таблицы сохраняется при Apply. `payroll-inherited-caption-contract.mjs` проверяет фактические helpers, false/zero, дату, ambiguous/gap и отсутствие мутаций.

## Browser → HTTP → PostgreSQL → reload: принятая область

`scripts/payroll-parameter-browser-postgres-qa.mjs`: фактический локальный прогон завершился PASS, exit 0. Проверены 15 путей: mode, perShiftCents, stableRateBps, targetCents, baseRateBps, bonusRateBps, excessRatePolicy, lossPolicy, itemRuleBasis, teamWeight, cap.rateBps, cap.basis, applyMilestones, bracketRatesBps.40000000, milestoneBonusesCents.40000000.

Настройка владельцем через карточки сохраняет точные числовые/boolean/string значения, включая ноль и false, денежные единицы и проценты, даты 2026-11-03…2026-11-20. Проверены ответ API, значения PostgreSQL и повторное отображение; личный mode сохранён в трёх вариантах. Для каждого пути возврат к роли сохраняет inherit, NULL в PG и пустое личное поле после reload. Активация делает карточки и JSON недоступными для редактирования; исходные параметры роли не изменяются. Проверены ширины 1440/1024/768/375/320 без переполнения панели; снимок 375 дополнительно просмотрен координатором.

Изолированная схема использует существующие миграции до 088 включительно. Это устранило ошибку загрузки финансов тестовой базы; GET finance/summary и analytics проверены на HTTP 200. Новых DDL и изменений продукта нет, UI остаётся rev14. В finally закрываются браузер/сервер и удаляется только собственная временная схема с проверкой удаления. Количество payroll_entries, expenses и runs не меняется.

Область доказательства — сохранение и отображение поддержанных личных параметров. Этот прогон не доказывает расчёт на официальных источниках, математику всех режимов, полную финансовую регрессию или отдельную матрицу RBAC. Отсутствующие scalar/cap/team параметры и персональный цех остаются открытыми требованиями.

## Исправленный дефект пересечения дат

Missing-parameter preflight проверял каждое личное значение против каждой роли сотрудника, даже вне периода этого значения. При переходе stable → personal_target личный targetCents=0 на второй день ошибочно блокировал первый день, где параметра targetCents нет.

Проверка перенесена в существующий обход фактического дня назначения: личный путь проверяется только если employee, override mode и обе даты применимы; исторические назначения и будущие override окна не участвуют. `scripts/payroll-dated-override-role-contract.mjs` воспроизводил RED до правки, после правки PASS, включая явный ноль. Последующий scalar пакет разрешает явный target leaf и до перехода на target роль; он не меняет математику исходного stable дня. Отсутствующие cap/team листья этим не разрешены, их blocker отдельно сохраняется в threshold contract.

## Принятый контракт новых личных порогов

Два семейства `bracketRatesBps.<threshold>` и `milestoneBonusesCents.<threshold>` допускают новые листья. Порог ставки — безопасное целое от нуля; премии — положительное безопасное целое. Новый ключ пишется без ведущих нулей. Точное существующее legacy написание остаётся совместимым; новый числовой alias не создаётся и не нормализуется. Наследование возвращает лист роли либо отсутствие личного листа, если такого порога у роли нет. Остальные листья роли сохраняются; значение ноль — явное личное значение.

Общий validator calculator/service проверяет пересечения дат и конфликт конкретного личного порога с базовой/личной таблицей. Неизменённые старые bracket aliases не получают новых ограничений от этого этапа. Новая личная премия при включённом начислении и cap требует явной `milestoneCapPolicy` уже при сохранении/активации, а не только в preview. Ранее пройденный порог не начисляется догоняющей премией.

Проверки: `payroll-personal-threshold-contract.mjs`, `payroll-personal-threshold-postgres-contract.mjs`, browser QA rev13 через личные карточки → API → PG → reload, прежние inheritance/calculation contracts. OfficialReady этим не меняется.

Проверка последовательных окон ускорена обработкой событий начала/окончания. `payroll-personal-threshold-sweep-contract.mjs` сравнивает новый helper с сохранённым прежним алгоритмом: 400 детерминированных случаев, смена роли, исходный порядок override, включительные даты, годы 0001/9999 и отсутствие мутаций. На 15 000 последовательных окнах в прогоне координатора прежний helper занял 10 858 мс, новый — 526 мс; независимый прогон code-health дал 5 223/238 мс. Оба измерения относятся только к этому helper и сценарию, а не скорости полного сохранения или начисления. Время не является жёстким тестовым порогом. Массовые одновременно активные листья и остальные validators требуют отдельного измерения.
