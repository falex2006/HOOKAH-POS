**Статус:** проектный контракт, кодовую реализацию не разрешает и не описывает как уже выполненную.  
**Источник продукта:** `C:\Users\ADMIN\Downloads\Telegram Desktop\ТЗ_Гибкий_модуль_расчёта_зарплаты_CRM.md`.
**Финансовый источник:** `docs/requirements/FINANCE_MODEL.md` и актуальные сообщения чата MASTER.

## 1. Цели и границы

Модуль расширяет существующий зарплатный жизненный цикл `payroll_rules` → `payroll_entries` → `expenses`. Он добавляет настраиваемые версии схем и воспроизводимый расчёт, но не создаёт второй реестр начислений или платежей.

Только владелец площадки может создавать/изменять payroll-конфигурацию: версии схем, ставки по ролям и персональные overrides, пороги, бонусы, caps и item commission rules. Перерасчёт утверждённого периода и запуск нового расчёта для закрытого периода требуют явной аудируемой owner-only операции. Просмотр зарплатных сумм, создание/утверждение черновиков, фактическая выплата и отмена — отдельные permissions: сохранять текущие права payroll lifecycle до отдельного продуктового решения, не расширяя их через finance-read и не смешивая с правом менять конфигурацию. Сейчас UI/API опираются на permission `finance`; для будущих owner-only изменений потребуется серверная проверка фактического venue owner, а не роль manager/admin или platform owner. UI скрытие само по себе не является границей безопасности.

Не входит в зарплатный модуль: изменение order/payment/loyalty ledgers, редактирование сменной кассы, изменение цены закрытого заказа, повторное признание связанного payroll expense, и автоматическое изменение финансовых записей при пересчёте.

## 2. Фактическая отправная точка

- `migrations/021_staff_time_payroll.sql` создаёт `staff_schedules`, `staff_work_logs`, `payroll_rules` (hourly/monthly/percent_revenue/per_shift) и `payroll_entries`.
- `migrations/040_payroll_lifecycle.sql` добавляет audit-поля и состояния draft/approved/paid/cancelled.
- `server.js` реализует API правил, создание начисления по правилу и рабочим часам, состояния записи и связывание выплаты с расходом; `payroll.js` содержит текущий calculation helper, а payroll UI находится внутри финансового раздела `portal.js`.
- Роль `owner` существует в `user_role`, но текущие finance/HR права шире и payroll endpoints должны получить отдельную серверную owner-only проверку для конфигурационных операций.
- В `order_items` есть `id`, `order_id`, `product_id`, quantity, unit price, station/status и guest number; migration 084 добавила nullable-пару автора добавления `sales_employee_id` и UTC-времени `sold_at` для новых строк. Legacy-строки могут остаться без attribution. Эти поля не определяют payroll-credit policy/correction, а распределения скидки и ссылки на возврат по строкам всё ещё нет. `orders.opened_by` не является line attribution. `products.category` и `order_items.station` существуют, но не закрепляют payroll department contract.
- MASTER подтвердил, что в аналитике linked payroll expense уже учитывается ровно один раз; смены, заказы и лояльность остаются отдельными источниками истины.
- Migrations 077–079 already add versioned schemes, role assignments, employee overrides, item rules, revisions, calculation runs and snapshot tables. The pure calculator and owner-only scheme API/UI support scenario preview and version comparison. They do not yet create `ready` runs or source-backed snapshots; the current run service writes only blocked headers.
- `payroll_entries` has no calculation-run link. Its legacy `UNIQUE (venue_id,user_id,period_from,period_to,rule_id)` does not deduplicate rows when nullable `rule_id` is `NULL` and does not prove source provenance. New run-derived entries require a nullable tenant-scoped run link plus a unique run/employee constraint and overlap protection against all live legacy entries.

Это контракт целевого расширения, а не аудит текущего diff. Перед каждой кодовой итерацией повторно проверить HEAD, `git status`, активные сообщения MASTER и затронутые пути.

## 3. Термины и денежные инварианты

- **Схема** — именованная конфигурация расчётной формулы/режима.
- **Версия схемы** — неизменяемая конфигурация с `effective_from` и, при закрытии, `effective_to`; новая ставка создаёт новую версию.
- **Назначение** — применение схемы на период к роли или сотруднику площадки.
- **Calculation snapshot** — неизменяемый результат по площадке, локальному дню и сотруднику с версией правил и детализацией исходных строк.
- **Начисление** — payroll entry существующего жизненного цикла, созданное из утверждаемого набора расчётных снимков.
- Все новые сущности площадочные (`venue_id`); организации и сотрудники не пересекают tenant boundary.
- Расчёт хранит денежные значения в decimal/numeric, без binary floating-point в доменной логике.
- Для 10.1 диапазон определяется по cumulative turnover площадки на конец venue-local дня и применяется к комиссионной базе атрибутированных строк. Venue turnover — самостоятельный дневной агрегат закрытых заказов по `final_total_snapshot`; он не выводится из суммы сотруднических строк. Порядок строк внутри дня остаётся детерминированным по timestamp/ID для snapshot detail.
- Полная личная выручка для абсолютного ограничения выплаты — самостоятельная normalized source series: все продажи, приписанные сотруднику, после скидок и возвратов по Finance semantics, независимо от комиссии и категории позиции. Ни `commissionBaseCents`, ни `turnoverCents` не являются доказанной заменой. Пока POS/Finance не предоставляет эту величину с line lineage и coverage, калькулятор может только показать сценарную проверку по attributed turnover и не подтверждает право на официальный run.
- Пороговый бонус выплачивается однократно при первом пересечении установленного cumulative venue turnover в месяце, всем сотрудникам, которым версия правила назначает бонус, даже если у них нет смены в день пересечения.
- Смена для модели 10.1 подтверждается фактической продажей сотрудника в день (требование ТЗ), а не `staff_schedules`. Данные `staff_work_logs` пригодны для почасовых исторических правил, но не заменяют sales-based presence.
- Caps в калькуляторе v1 применяются на сотрудника и локальный день: `venue_day` использует полную дневную выручку площадки из отдельной серии закрытых order snapshots (эталон 35% для утреннего универсала), `employee_department_day` — turnover attributed этому сотруднику и department по строкам за день (эталон 30% для вечерних ролей). Сумма строк может отличаться от venue total из-за minimum-price adjustment и unattributed lines; ни одно значение не подставляется в другую базу. `commissionBaseCents` остаётся отдельной комиссионной базой. Общий лимит расходов цеха/смены не реализуется до появления проверенного shift + department turnover источника и детерминированного правила распределения общего лимита. Суммы до и после cap видны в расчёте.
- Позиционный commission rule имеет режим `replace` или `additive`; область и приоритет правил разрешаются детерминированно и входят в snapshot.
- Изменение правил не переписывает утверждённые или оплаченные снимки. Ретроактивный пересчёт — отдельная owner-only операция с обязательной причиной, автором, временем, исходным snapshot и ссылкой на заменяющий результат.
- Начисление и выплата продолжают существующий lifecycle. В начисленном P&L approved/paid payroll entries распределяются по периоду ровно один раз; связанный `source='payroll'` expense не суммируется повторно в этом P&L. Денежный поток отражает expense по дате фактической выплаты, создаваемый только существующим pay lifecycle; расчётная запись и snapshot сами не создают expense.
- Выплаченный период заблокирован от редактирования и повторной выплаты. Сторнирование/корректировка — отдельная аудируемая финансовая операция по согласованному финансовому контракту, а не мутация старого snapshot.

## 4. Концептуальная схема данных

Имена предварительные: перед миграцией проверить существующие объекты `schema.sql`, `db.js`, миграции и naming conventions.

1. `payroll_schemes`: `id`, `venue_id`, `name`, `description`, `active`, `created_by`, timestamps. Идентичность схемы не содержит изменяемых ставок.
2. `payroll_scheme_versions`: `id`, `venue_id`, `scheme_id`, monotonic `version_no`, `mode` (`progressive_daily`, `stable_percent`, `percent_only`, `final_month_threshold`, `personal_target`, `team_fund`, `margin_target`), `effective_from`, `effective_to`, `currency`, `config_json` либо нормализованные дочерние правила, `status` (`draft`, `active`, `retired`), author/audit columns. Уникальность версии по площадке/схеме/номеру; запрет пересекающихся active effective windows для одного назначения.
3. Нормализованные дочерние правила версии: для роли — default department, mode, per-shift cents, stable rate basis points, `bracketRatesBps` keyed by cumulative turnover cents, milestone bonus cents keyed by threshold cents, cap rate/scope/department and milestone-cap policy. Role defaults can be overridden independently for an employee by explicit `inherit|override` parameter rows, including zero and mode. JSON допустим только для versioned parameters, validated by server schema and snapshotted; tables preferred for thresholds and rates.
4. `payroll_role_assignments`: `venue_id`, `role_key`/существующий role FK, версия схемы или набор версионных правил, effective dates. Не вводить дублирующий справочник ролей, если доменная роль уже существует.
5. `payroll_employee_overrides`: площадка, сотрудник, ключ параметра, режим (`inherit`/`override`), значение, effective window, автор. Каждый параметр независим: mode, base, stable rate, каждая bracket rate, cap, milestone bonus, ориентир/план. Значение override=0 допустимо и отличается от наследования.
6. `payroll_item_commission_rules`: площадка, menu item/category selector, role или employee scope, rate, `replace|additive`, effective dates, priority, author. Персональное правило имеет приоритет над ролевым правилом того же селектора; неоднозначные ties отклоняются при сохранении.
7. `payroll_calculation_runs`: площадка, период, scheme version, явный input watermark, author/created time, `supersedes_run_id`, причина пересчёта, итоговый checksum. Run append-only; изменения создают новую run.
8. `payroll_daily_snapshots`: run, площадка, локальная дата, employee ID plus name/role snapshot (без каскадного удаления истории), валюта, eligible shift count, turnover/cumulative turnover, base pay, percent pay, milestone bonus, item adjustments, cap, final amount, source version IDs, explanation. Уникальность `(run_id, local_date, employee_id)`.
9. `payroll_daily_snapshot_lines`: snapshot, order ID + order item/line ID, sales author/employee ID snapshot, menu item/category/department snapshot, quantity, gross/net commission base, cost/margin if available, applied rule IDs, rate, amount. Уникальность исходной order-line в одном snapshot run. FK включает venue/order boundary; строки не должны исчезать при archive/delete пользователя или заказа. Нулевая/возвращённая/сторнированная продажа обрабатывается согласованно с фин. источником.
10. `payroll_adjustments`: append-only корректировки со ссылкой на первоначальный run/snapshot/строку, исходный refund/void ID, сотрудника, знаковую сумму, дату признания, целевой run и idempotency key. Одна исходная refund allocation применяется к зарплате не более одного раза. Непогашенный остаток переменной корректировки переносится явно; это не отдельный платёж и не `expense`.
11. `payroll_entries` расширяется nullable tenant-scoped FK на расчётный run. Один `ready` run агрегирует дневные snapshots и adjustments до одной существующей `payroll_entry` на сотрудника, не по отдельной строке заказа/компоненту; period boundary не может пересекать несовместимые версии схемы. Добавить partial unique index по `(venue_id, calculation_run_id, user_id)` для непустого run link: существующий `rule_id` nullable, поэтому legacy unique key не обеспечивает идемпотентность для `NULL`. Атомарно сверять run status, точный период, версию и присутствие employee snapshot; сумма entry обязана совпадать с суммой его snapshots и применённых adjustments. Сериализовать проверку пересекающихся периодов на сотрудника и отклонять конфликт со всеми live legacy entries — совпадение дат и суммы само по себе не доказывает происхождение. Существующий `rule_id`, status, `expense_id` и approve/pay transitions сохраняются без повторного жизненного цикла; expense создаётся только подтверждённым `pay`, как сейчас требует финансовый контракт. Legacy rows не backfill-ятся выдуманной связью.
12. Audit log фиксирует старое/новое значение конфигурации, scope, время действия, actor, причину, approved/paid transitions и пересчёты. Для владельца показывается diff версии и список сотрудников, затронутых или оставшихся на персональном override.

### Проверенная граница текущей реализации (2026-10-03)

Миграция 077 создаёт таблицы расчётных runs и snapshots, но существующие routes и UI не создают официальный run и не заполняют snapshots. Payroll-owned `payroll-calculation-run-service.js` умеет сохранить только owner-authorized `blocked` attempt header с `source_coverage='unknown'`, `commission_basis='unknown'`, неизменяемыми timezone/currency, причиной отсутствующих первичных источников и идемпотентным ключом. Отдельный `payroll-venue-turnover-source.js` строит только read-only tenant-scoped venue-дневную серию по закрытым заказам: использует `final_total_snapshot`, а для legacy заказов без него — тот же fallback из сохранённых строк и одобренных скидок, что Finance. `payroll-scheme-service.js` использует её только в `previewWithVenueDailyTurnover` внутри owner read-only repeatable-read transaction. Этот preview-source method доступен владельцу через `POST /api/payroll/versions/:id/preview/venue-turnover` и отдельное действие на панели payroll-схем. Заказы без `closed_at` блокируют ряд. Отдельный payroll-owned `previewWithApprovedAttendance` в том же read-only repeatable-read scope использует актуальный immutable attendance approval; источник, неполнота и stale watermark проверяются на том же соединении до расчёта, а caller-provided attendance заменяется snapshot-строками. UI раскрывает ID ревизии. Этот preview-source method доступен через `POST /api/payroll/versions/:id/preview/approved-attendance`. Оба sourced previews остаются независимыми сценарными этапами: оборотный preview не подтверждает строкового автора/net базы комиссии/табель, attendance preview не подтверждает продажи, автора, скидку/возврат или Finance revenue coverage. Ни один helper не имеет операции `ready`, не пишет calculation snapshots, adjustments, `payroll_entries` или `expenses`; ответы `official:false`/`persistence:none`. Source-backed API для `ready` run по-прежнему отсутствует; нельзя создавать начисления из preview JSON или показывать сценарий как сверенный с начислениями.

Закрытый schema gap перед этим API: `payroll_calculation_runs` 077 первоначально хранил диапазон дат без snapshots `venue_timezone` и `currency`; timezone может позже измениться, а валюта иначе читалась бы только через изменяемый контекст. Payroll migration 081 (`migrations/081_payroll_run_metadata.sql`) добавляет nullable IANA `venue_timezone` и ISO `currency` без DEFAULT и backfill; DB guard требует оба значения для каждого нового run, сверяет timezone с площадкой, валюту с версией схемы и удерживает исходные строки под `FOR SHARE`. Старые runs остаются с `NULL`, явно обозначающим недоступную историческую конфигурацию. Replay, legacy preservation и metadata guard проверены изолированным PostgreSQL-контрактом. Не принимать `ready` при неподдерживаемой валюте или неподтверждённых POS/attendance источниках.

В существующем payroll lifecycle строки по сотруднику и точному периоду могут повторяться с разными `rule_id`, поэтому совпадение сотрудника, периода и суммы — только диагностический кандидат, не доказательство происхождения начисления. Пока нет tenant-scoped устойчивой связи run→entry, модуль не должен объявлять сверку расчётного snapshot с начислением точной или использовать snapshot для создания/утверждения/выплаты `payroll_entry`.

Реализацию вести в зависимом порядке, не объявляя следующий этап готовым до прохождения предыдущего:

1. **Approved attendance manifest (migration 082).** В payroll-owned таблицах сохранить отдельную неизменяемую owner-approved ревизию полного табеля: снимки расписания и закрытых work intervals, локальная дата/таймзона, сотрудник, автор и время утверждения, причина, source watermark/checksum и idempotency. Источник читается tenant-scoped из `staff_schedules`/`staff_work_logs`; эти HR-таблицы не меняются. Пересечения объединяются детерминированно только в рамках однозначно сопоставленной плановой смены; открытые/несопоставленные интервалы и неизвестная полнота блокируют approval. Изменение исходных строк делает текущую ревизию stale и требует нового утверждения, не изменяя старый снимок. Это отдельное owner-only действие: только владелец из серверной сессии, без caller-supplied `approved`/actor; не закрывает POS-смену и не создаёт run, payroll entry или expense.
2. **Официальный run из первичных источников.** Реализовать source-backed API, который читает закрытые заказы, source line author (`sales_employee_id`, если разрешён выбранной owner policy), immutable line net после скидок и возвратов, approved attendance manifest из migration 082, активную версию схемы и venue-local календарь из одного согласованного DB snapshot/transaction. Он фиксирует timezone/currency, неизменяемые дневные и построчные snapshots, input watermark/checksum и создаёт `ready` только при полной проверяемой coverage. Attribution уже хранится для новых строк миграцией 084; official run остаётся `blocked` из-за неподтверждённой legacy/credit coverage, отсутствия immutable per-line discount allocation и того, что migration 088 refund остаётся order-level unattributed для payroll lineage, а также до подтверждения остальных Finance источников. Эвристики не подменяют недостающие факты.
3. **Run-to-entry lifecycle.** Только после появления официальных `ready` runs спроектировать отдельную additive migration для nullable tenant-safe `(venue_id, calculation_run_id)` link новых entries и unique `(venue_id, calculation_run_id, user_id)`; номер назначается после перепроверки миграций, поскольку migration 082 выделена под attendance. Существующую expense-связь отдельно проверить на tenant provenance: сейчас FK ссылается только на `expenses.id`, а `expense_id` nullable и не уникален. Атомарное создание одного draft на employee проверяет ready run, площадку/версию/точный период, snapshot membership и совпадение суммы; транзакционно сериализует поиск конфликтов с любыми live legacy entries того же сотрудника. Не backfill-ить выдуманную связь для старых строк. Использовать существующие approve/pay transitions; только подтверждённый `pay` создаёт или связывает один `source='payroll'` expense и отражает cash flow. Исходный run/snapshots после создания не менять.

Оба этапа требуют явного согласования файловых границ с MASTER и финансового контракта; особенно `server.js`, которым уже владеет payroll entry/expense lifecycle. До их реализации допустима только явно помеченная owner-only диагностическая выборка существующих связей `payroll_entries.expense_id` с расходами. Она не подтверждает связь с расчётным snapshot и не меняет отчёты либо ledgers.

### Подтверждённые POS точки фиксации attribution

Текущий PostgreSQL путь добавления строки расположен в `POST /api/orders/:id/items` (`server.js`); пользовательский клиент отправляет только `productId` и `quantity` (`app.js`). Endpoint получает автора только из аутентифицированного `req.user`, не из тела запроса и не из `orders.opened_by`; migration 084 хранит автора добавления и UTC-время на строке. Каждое добавление создаёт отдельную строку, поэтому смешанные авторы не объединяются. Эти факты не выбирают payroll-credit policy и не фиксируют исполнение/коррекцию. `PATCH` количества сохраняет исходные автора и время; контракт 084 требует отдельную строку для новой порции, поэтому увеличение существующей строки остаётся конкретным несоответствием для POS-владельца. Перед включением payroll credit нужно решить policy атрибуции и отдельно проверить/согласовать семантику quantity edit. Любое изменение POS write paths должно оставаться транзакционным и tenant-scoped.

Текущие `PATCH/DELETE /api/orders/:orderId/items/:itemId` разрешены только пока заказ не закрыт и цена не зафиксирована; `POST /api/orders/:id/payments` закрывает заказ и блокирует ценообразование. Перенос стола меняет table/order placement, а перенос отдельных позиций между заказами сохраняет `order_items.id`; attribution должна следовать за проданной позицией и стать неизменяемой на момент закрытия, независимо от стола и текущего пользователя. Старые строки остаются unattributed. Миграция `order_items` и изменение этих write paths относятся к POS/MASTER границе и требуют отдельного file-level согласования плюс regression для смешанных авторов, количества, transfer/move, tenant isolation и закрытой строки.

Сырые HR записи сами по себе не являются утверждённым payroll-фактом: `staff_schedules` — план, `staff_work_logs` содержит `source`/интервалы. Уже реализованный payroll-owned manifest 082 сохраняет отдельный owner-approved снимок с автором, периодом и watermark без редактирования HR источников. Verified loader повторно проверяет полноту и актуальность источника в одной RR транзакции; незакрытый интервал и неполная coverage блокируют approval. Его sourced preview не делает продажи подтверждёнными и не создаёт официальный run. Стол/заказ показывает место обслуживания, но сам по себе не подтверждает attendance и не определяет исполнителя.

## 5. Расчётное ядро и режимы

Ядро должно быть чистой детерминированной функцией над нормализованными строками продаж, отдельной `venueDailyTurnover` серией, role assignments, versioned rules и venue-local датами. Суммы передаются целыми копейками, ставки — basis points, комиссии округляются half-up отдельно по каждой строке исходного чека. Для сотрудника/роли режим выбирается из `progressive_daily`, `stable_percent`, `percent_only`, `final_month_threshold`, `personal_target`, `team_fund`, `margin_target`; override режима валидируется вместе со ставками этого режима. Ядро не выполняет записи в orders, payments, loyalty, shifts, expenses или `payroll_entries`. Preview не сохраняет расчётные snapshots; при фиксации run source values копируются в snapshot-lines внутри транзакции. Pure calculator принимает coverage manifest (`kind`, from/to local dates, complete flag, nonempty opaque watermark); если `venueDailyTurnover` передан, он обязан содержать по одной строке на каждую покрытую venue-local дату, включая нули. Scenario-only preview без этой серии сохраняет legacy-derived line-sum поведение и помечает его в результате; official run обязан требовать полный источник дневного turnover. Это attestation входного слоя, а не доказательство полноты само по себе: production API обязан получать source rows в согласованном DB snapshot/transaction и формировать watermark по версиям/ID закрытых orders, order lines, pricing snapshots, discount/refund adjustments, attribution, attendance, payroll config и timezone. Изменение любого исходника создаёт новый run. База данных должна запрещать update/delete финализированных run/snapshots (например append-only API + trigger/permissions), а не полагаться только на frontend.

- **10.1 `progressive_daily`:** оклад за фактическую смену + commission с продаж дня по диапазону cumulative venue turnover на конец дня + milestones при первом пересечении + cap. Ставки и строки item-specific вычисляются в целых копейках/basis points; сумма округляется отдельно на каждой order line. Role department задаётся явным стабильным mapping, а не эвристикой по тексту названия; первоначальная миграционная классификация названий с «кальян» допустима как одноразовый проверяемый импорт, не как постоянная бизнес-логика. `venueDailyTurnover` задаёт сверенный venue-level turnover по `final_total_snapshot`/согласованному legacy fallback; `sales[].turnoverCents` задаёт attributed line/department turnover для персональных caps; `commissionBaseCents` задаёт нормализованную комиссионную базу строки после discounts/refunds. Эти базы не выводятся друг из друга.
- **`stable_percent`:** оклад за подтверждённую смену + стабильный %, применимый к определённой сотруднику выручке.
- **`percent_only`:** только commission; никаких shift wages.
- **`final_month_threshold`:** ставка выбирается по итоговому месячному обороту и применяется ко всей квалифицируемой выручке месяца. Ввиду выплаты раз в две недели такой режим несовместим с окончательным закрытием/выплатой первой половины до конца месяца: calculator принимает его только для полного закрытого месяца. Для применения к двум payroll entries понадобится отдельно согласованный provisional advance/true-up contract; он здесь не реализуется.
- **Исторические схемы 1–9:** обеспечить выразительность параметров без обещания поставки каждого как отдельного preset. До поддержки командного фонда, личного плана, маржи и дневного ориентира должны быть доступны соответствующие данные и формулы; схема не может ссылаться на отсутствующую себестоимость/план. Это отдельное решение о фазах после MVP, а не повод использовать недокументированную формулу.
- Формулы, bracket boundary convention (`lower inclusive, upper exclusive`, последний диапазон unbounded), округление, refunds/voids, скидочная база, taxes/gratuity и распределение shared lines фиксируются как часть версии и объяснения результата.

## 6. Атрибуция и источники данных

Обязательная гранулярность commission — строка заказа: каждая строка приписывается сотруднику, фактически совершившему/пробившему эту конкретную позицию. Ни общий `orders.opened_by`, ни смена, ни равное деление заказа не заменяют line attribution.

Migration 084 уже сохраняет автора добавления `sales_employee_id` и UTC `sold_at` для новых POS-строк; legacy строки без пары остаются unattributed. `orders.opened_by` и текущая смена не доказывают исполнение конкретной позиции. Ещё требуется owner-approved payroll-credit/correction policy; она не должна переписывать исходную POS-атрибуцию. Проверки полноты должны включать legacy unknown rows без эвристического назначения.

Кассовая сверка сопоставляет line-sales totals и cash/payment tender по площадке/дню/способу оплаты. Разница является диагностикой, не изменяет commission base автоматически. `order_items` сейчас не содержит строки распределения скидки или возврата, поэтому net commission base требует отдельного согласованного price/refund contract и безопасного источника line-level amounts. Loyalty redemption/deposit/prepayment/refunds остаются их собственными движениями и не прибавляются к выручке повторно.

Финансовый контракт признаёт закрытую выручку по `orders.final_total_snapshot`; при его отсутствии допускается только тот же одобренный Finance fallback, с явным legacy marker. Payroll source helper применяет тот же fallback к legacy заказам из сохранённых строк и одобренных скидок; количество таких заказов показывается в сценарии владельцу. Закрытая запись без `closed_at` блокирует серию: для неё нельзя безопасно определить локальный день. Поэтому 10.1 thresholds, cumulative month turnover и `venue_day` cap в snapshot-backed preview получают `venueDailyTurnover: [{ date, turnoverCents }]` из отдельной tenant-scoped выборки закрытых заказов по `closed_at` в venue timezone, суммируя каждую цену один раз. Серия покрывает каждый календарный день от начала месяца до coverage boundary и передаёт нулевые дни явно. Возвращаемый объект явно помечен `official:false`, `persistence:'none'`, `previewOnly:true`; его MD5 watermark включает tenant, timezone, период и идентификаторы/закрытие/формульные inputs исходных заказов, но является только средством обнаружения изменений для preview, не authoritative provenance для ready run. Серия включает minimum-price adjustment и revenue с неатрибутированными позициями, поэтому может не совпадать с суммой employee lines. Эти неразложенные суммы остаются venue-level и не распределяются на employee/department. В этом preview сотрудники, line attribution/net base, commission и attendance остаются caller-supplied сценарием; для `employee_department_day` используется только переданный `sales[].turnoverCents`, а комиссия — только переданный `sales[].commissionBaseCents`. Источник поддерживает реалистичный venue-only preview, но не разрешает считать комиссию, attendance или полный результат сверенными и не может создать `ready` run. Пока POS/Finance не подтверждает все требуемые серии и line bases, official run остаётся blocked.

## 7. API-контракт (предварительный)

Все endpoints tenant-scoped и проверяют авторизацию на сервере. Owner-only endpoints возвращают 403 без раскрытия чужих площадок.

- `GET /api/payroll/schemes`, `GET /api/payroll/schemes/:id/versions`: чтение только тем, кому разрешён просмотр конфигурации; текущий route `/finance` и permission `finance` не следует молча расширять пользователям с `finance_read`.
- `POST /api/payroll/schemes`, `POST /api/payroll/schemes/:id/versions`: создание схемы/черновой версии.
- `POST /api/payroll/versions/:id/activate` и `POST /api/payroll/versions/:id/retire`: валидация effective dates, отсутствия конфликтов и защиты закрытых периодов.
- `PUT /api/payroll/roles/:roleId/assignments`, `PUT /api/payroll/employees/:userId/overrides`: редактирование owner-only; каждый parameter override несёт explicit `inherit|override` и effective date.
- `PUT /api/payroll/item-commission-rules/:ruleId` / `POST ...`: upsert versioned replace/additive rule.
- `POST /api/payroll/calculations/preview`: deterministic read-only preview, breakdown by employee/day/line, caps, milestones, warnings, reconciliation totals; не пишет начисления или расходы. Scope доступа к конфигурационным preview vs личным суммам сотрудника — явное серверное permission.
- `POST /api/payroll/calculation-runs`: создать immutable run/snapshots с idempotency key и input watermark; повтор ключа возвращает тот же run.
- `GET /api/payroll/calculation-runs/:id` и `GET /api/payroll/dashboard`: чтение версий, aggregate и drilldown из того же snapshots source.
- `POST /api/payroll/calculation-runs/:id/recalculate`: owner-only, требует reason, сохраняет supersedes lineage; запрещён для затрагивающего paid period без отдельного финансового reversal workflow.
- Интеграция с `/api/payroll/entries`: утверждение и выплата используют существующие переходы. Выплата создаёт/связывает ровно один payroll expense и фиксирует ссылку на run; повторная оплата идемпотентна.

Названия и формы запросов — проектный proposal; проверять router conventions и RBAC перед кодом. Не добавлять альтернативный lifecycle parallel to existing entries.

## 8. Интерфейс

1. Owner-only настройки: список схем/версий, draft preview, сравнение версий, effective dates и audit history. Сейчас payroll UI встроен в `/finance`, отдельного payroll маршрута нет; оставить его там, если отдельный маршрут не согласован, и не расширять пункт навигации/route доступ для `finance_read` случайно.
2. Настройка ставки по роли с пороговой таблицей и видимым списком затронутых сотрудников; персональные overrides на каждом параметре независимо, включая явный персональный ноль.
3. Каталог позиционных правил: item, роль/сотрудник, ставка, replace/additive, период действия, конфликты.
4. Распределение смен/персонала: добавить подменного сотрудника с ролью без создания новой роли; не создавать смену как доказательство продаж.
5. Расчётный экран: выбрать площадку/период/версию, preview с drilldown до строки чека, cumulative bracket, базой комиссии, bonus threshold, cap и итогом; отдельные alerts о неизвестном авторе строки и несверенной кассе.
6. Сравнение схем: одинаковый snapshot входных данных и период, отдельные суммы по сотруднику/дню и дельта; симуляция ничего не сохраняет в ledger.
7. Dashboard: агрегаты и детализация читают только выбранный неизменяемый run, показывают draft/provisional vs approved/paid, общие начисления, выплаты и расхождение сверки. Нельзя отдельно пересчитывать карточки другой формулой.
8. Закрытие периода и выплата используют существующий lifecycle. UI не предлагает изменение выплаченного периода; исправление ведёт к аудируемому корректирующему workflow.

## 9. Права и аудит

- Owner-only на payroll configuration/activation и ретроактивный пересчёт. Текущие payroll draft/approve/pay/cancel permissions сохраняются до отдельного решения владельца продукта; новый просмотр зарплатных сумм и конфигурации не открывать шире действующих payroll ACL.
- Защита tenant должна быть проверена на каждом API по `venue_id`/membership, включая вложенные item/rule IDs.
- Каждая конфигурационная правка содержит actor и `effective_from`, сохраняет прежнюю версию; не удалять применявшуюся версию физически.
- Аудировать preview не обязательно как финансовое изменение, но сохранять calculation run, approve/pay/cancel и retroactive recalc. Причина обязательна для отмены/перерасчёта и видима в audit trail.
- Персональные данные и зарплатные значения возвращать только ролям, которым разрешён просмотр payroll; точная матрица сверяется с auth implementation перед API.

## 10. План миграции и поставки

**Этап 0 — контракт/инвентаризация (без продуктовых правок):** подтвердить owner role, staff/role model, order line IDs/authorship, category→department, sale/refund basis, currency/timezone, current payroll UI/API and schema; сравнить все активные diffs/HEAD с MASTER. Этот документ фиксирует целевое направление.

**Этап 1 — additive schema:** новые схемы/версии/assignment/overrides/item rules/runs/snapshots; nullable link из payroll_entries на run. Никаких destructive rename/drop и массового переписывания существующих правил. Backfill для старых payroll rows не выдумывает snapshots; маркировать legacy source.

**Этап 2 — attribution/source completion:** actor + add-time UTC attribution already exists for new POS lines via migration 084; legacy rows remain unattributed. Remaining work is quantity-edit lineage contract, approved correction/credit policy, stable department source and immutable line-level net/discount/refund allocation. Historical data is not backfilled by inference; any additive schema/write path requires owner agreement and tenant-scoped QA.

**Этап 3 — shadow calculator:** 10.1 и три обязательных режима считаются параллельно в preview/shadow, сравниваются с контрольными примерами Excel/владельца; никаких автоматических выплат или расходных записей.

Изолированный первый engineering slice — чистый `payroll-schemes.js` и его focused contract QA на нормализованных входах (центовая арифметика, versioned config, per-role/person mode/rate resolution, 10.1 + три обязательных режима). Он требует coverage manifest и role assignment на каждый день активного employment window, блокирует расчёт при отсутствующей attribution или невалидных входах и не выполняет API/DB writes; этим slice не заявляется сквозная payroll-функция. Caller обязан передавать точную basis для sales/commission amount.

**Этап 4 — owner UI и snapshot:** версионируемая конфигурация, preview, audit, immutable run, compare и dashboard. Создание run — отдельно от approval.

**Этап 5 — lifecycle integration:** из `ready` run дневные snapshots и adjustments агрегируются в ровно одну idempotent draft entry на сотрудника/период/run, затем используют существующие approve/pay transitions. Tenant-safe unique run/employee constraint защищает повторный запрос; сериализованный overlap-check конфликтует со всеми live legacy entries, в том числе без `rule_id`. Entry amount и период должны точно сходиться со snapshots/run до вставки. При фактическом `pay` существующая транзакция создаёт/связывает один payroll expense; этот расход не участвует в P&L второй раз и входит в cash flow только по payment date. Проверить повторные запросы, конкурирующие runs, блокировку оплаченных периодов и void/refund. Согласовать с MASTER, когда daily snapshot суммы должны попадать в фин. отчёты: существующая аналитика равномерно раскладывает entry по дням; report не должен одновременно учитывать и entry allocation, и daily snapshots.

**Этап 6 — расширение формул:** исторические варианты, margin/team fund/personal target после подтверждения доступности unit cost, source attribution и определения плана. Версии движка/формул должны быть явны в snapshots, чтобы будущая смена кода не меняла старые суммы.

Rollback — только отключение feature flag и откат использования новых сущностей; после создания snapshots сохранять их для аудита. Схемы rollout/backfill требуют отдельного DB/security review по проектным правилам.

- Этот новый документ: `docs/requirements/PAYROLL_ARCHITECTURE_CONTRACT.md` — зарплатный чат может поддерживать как product contract.
- Предварительно ожидаемые shared zones: `server.js`, `schema.sql`, новые migrations, `db.js`, payroll UI entry points (уточнить фактические файлы), `portal.js`, `dist/portal.js`, API/auth code и финансовые отчёты.

- Рекомендуемый первый кодовой PR после инвентаризации — только additive migrations и узкий API/domain layer с owner tests; `server.js` затрагивать лишь по согласованному списку файлов, не одновременно с MASTER. Не выпускать dist snapshots вручную до установления build/sync contract.

## 12. Риски и вопросы исходного ТЗ

Перечень ниже сохраняет исходную инвентаризацию рисков. Рабочее поведение первой реализации для продуктовых неоднозначностей зафиксировано в разделе 15; эти пункты не требуют повторных рутинных вопросов владельцу. Реальный source gap всё равно блокирует `ready`, пока не будет добавлен проверенный первичный источник.

1. **Решено исходным ТЗ:** commission attribution относится к сотруднику, который пробил конкретную позицию чека. Это не исполнитель услуги, не сотрудник, открывший заказ, и не все сотрудники смены. POS должен сохранять actor на каждой строке продажи; `orders.opened_by` и факт работы за столом этого не заменяют. Если позднее потребуется платить исполнителю услуги отдельно от кассира, это будет отдельная атрибуция и отдельное продуктовое решение, а не автоматическая подмена текущего правила.
2. **Решено владельцем:** commission base — чистая сумма конкретной строки после применённых скидок и возвратов. Источник должен возвращать финальное распределение скидок/возвратов по строкам; payroll не распределяет order-level discount собственной эвристикой и не суммирует loyalty/deposit/prepayment движения повторно. Пока текущая POS-модель не предоставляет подтверждённое line-net значение, production расчёт должен блокироваться для таких источников, а не подменять net суммой до скидки. Отдельно остаётся решить, как отражать возврат, проведённый после закрытия расчётного периода.
3. **Рабочее правило зарплатного контура:** закрытый run и выплаченная запись никогда не мутируются. Возврат, проведённый после snapshot, становится отдельной корректировкой следующего открытого расчёта с ссылкой на исходную строку продажи и возврат. Сумма корректировки не превращается автоматически в отрицательную выплату и не удерживается из фиксированной оплаты; не покрытый будущей переменной частью остаток переносится как видимый долг корректировки и требует отдельного подтверждённого финансового процесса. Для невыплаченного, но уже утверждённого периода также создаётся новая корректирующая версия/run с lineage, прежний snapshot сохраняется. В текущей POS-схеме нет ledger возвратов конкретной строки заказа: будущий API обязан блокировать refund adjustment до появления проверяемого source refund allocation; `source_key` и DB лимит относительно исходной комиссии сами по себе не доказывают реальность возврата.
4. К какому цеху относятся смешанные/переименованные позиции: использовать закреплённую menu category/department; названия не являются надёжной постоянно действующей категоризацией. Сейчас есть `order_items.station` и `products.category`, но нет подтверждённого ownerable department mapping для payroll.
5. Кто получает threshold bonus: пять перечисленных штатных сотрудников, активные назначения схемы или все сотрудники с ролью; даты найма/выхода и подменные нуждаются в явной eligibility.
6. **Временная политика конфликтующих инвариантов:** процентный cap в калькуляторе и абсолютный дневной потолок общей выплаты из исходного ТЗ — разные проверки. Fixed shift pay и milestone остаются видны без автоматического урезания; если сумма выше подтверждённой личной net revenue, официальный run блокируется. До authoritative personal-revenue source калькулятор помечает проверку как preview-only proxy; финансово конфликтующую конфигурацию также нельзя считать owner-approved только потому, что API сохранил черновик.
7. Разбивка оклада за смену, если сотрудник частично отработал/сделал несколько overlapping logs; ТЗ говорит о факте продаж, но не задаёт правило длительности.
8. Семантика персональных ставок для bracket table и персональных overrides при смене роли/схемы; обеспечить snapshot effective config.
9. Для historical schemes: точные формулы и guardrails для margin 48%, excess-plan 65%/40%, командного фонда и дневных ориентиров; не выводить их из описания без согласованной числовой модели.
10. Должен ли owner отдельно подтверждать payroll calculation run перед его преобразованием в черновики текущих payroll entries; существующий `approved` → `paid` workflow при этом сохраняется.
11. Retention: новая payroll history не должна удаляться существующими `ON DELETE CASCADE` через `users` или venue; определить архивирование/ограничения hard-delete и сохранить snapshot employee identity для прошлых периодов.
12. `payroll_entries.expense_id` в текущей схеме допускает `ON DELETE SET NULL`; определить защиту от потери связи и повторного/пропущенного признания выплаченной зарплаты в finance analytics.
13. Кто может видеть точные зарплатные суммы, расчётные строки, ставки и сравнение схем; `finance_read` не должен автоматически давать доступ к чувствительным зарплатным деталям.
14. **Отчётная основа синхронизирована с MASTER.** `FINANCE_MODEL.md` устанавливает, что approved/paid payroll entries учитываются по покрываемому периоду в accrual P&L ровно один раз, связанный `source='payroll'` expense повторно в этот P&L не включается, а cash flow отражает расход только по фактической дате выплаты. До интеграции snapshots/entries в отчёты нужно проверить межпересечённые периоды и сверку paid entries ↔ expenses.

В исходном ТЗ есть несовместимость дневного лимита общей выплаты относительно личной выручки и безусловных milestone/фиксированных начислений сотруднику с нулевыми личными продажами. Сценарный калькулятор сохраняет сумму без автоматического урезания, показывает критическое превышение и запрещает snapshot DTO для такого результата. Это не разрешает сохранить конфигурацию без owner acknowledgement и не делает сценарий официальным. Нынешний `personalRevenueCents` — только сумма приписанного `turnoverCents`, сценарный proxy; контракт не подтверждает, что это полная чистая выручка по Finance после скидок/возвратов. До такого подтверждённого поля любой официальный run остаётся заблокированным.

## 15. Рабочие продуктовые defaults

Чтобы не переносить неявные правила в код и не блокировать проект рутинными вопросами, для первой реализации принимаются следующие defaults. Каждый параметр схемы версионируется; владелец может изменить поведение новой effective-версией. Эти defaults не заменяют отсутствующие первичные данные, проверку владельцем перед run или финансовую проверку MASTER.

1. **Пороговые премии.** Получателями являются сотрудники из явного owner-maintained eligibility roster, назначенные на версию схемы и активные в кадровой записи на локальную дату пересечения порога. Подменный сотрудник не включается автоматически только потому, что он работал или пробивал продажи. Если исходное правило конкретного заведения перечисляет пять штатных работников, roster задаётся этими пятью назначениями. Сценарий начисляет сумму каждому eligible получателю один раз на событие пересечения и не обрезает её автоматически. Если итог дня выше подтверждённой личной выручки, официальный расчёт блокируется до owner-reviewed разрешения конфликта; preview сохраняет сумму и показывает критическое превышение.
2. **Неполный выход и несколько интервалов.** Для фиксированного компонента «за смену» использовать утверждённые фактические интервалы, предварительно объединяя их пересечение для сотрудника. Начислять долю `ставка за смену × подтверждённые минуты / запланированные минуты` по каждой owner-confirmed scheduled shift, суммарно не более одной полной ставки за один плановый shift. Отсутствующий/нулевой planned duration, незакрытый интервал или неутверждённое время блокирует соответствующую часть official run; расписание само по себе не доказывает отработанное время. Комиссия по валидным строкам остаётся независимой от attendance.
3. **Персональные overrides.** Override применяется только к явно указанному параметру и effective window. Нулевое значение является явным override, пустое/отсутствующее значение означает наследование. Изменение ставки не переписывает прежнюю версию, и расчётный snapshot сохраняет окончательно разрешённый набор параметров сотрудника на каждый день.
4. **Категория/цех и исторические режимы.** Категория определяется стабильным ID/menu-department mapping, а не названием товара, свободным текстом или `station` по умолчанию. Если формула/cap требует department и mapping нет — расчёт блокируется. Текущий калькулятор поддерживает семь режимов, включая personal_target, team_fund и margin_target; это промежуточное состояние, а не сокращение полного ТЗ. Для historical margin, excess-plan, team fund и target требуется завершить числовой контракт, сценарную интеграцию и source gates; официальный margin дополнительно требует immutable unit-cost inputs. Владелец поручил самостоятельно выбирать логически и финансово обоснованные решения, поэтому отсутствие дополнительных примеров владельца не блокирует разработку сценарной математики.
5. **Run, деньги и доступ.** Официальный run создаёт только owner после просмотра периода и источников; перевод ready run в черновики — отдельное действие с idempotency и повторно использует существующий payroll lifecycle. Выплата создаёт только существующий единый payroll expense. Пока expenses/финансовая модель не несут подтверждённую валюту, официальные runs принимают только RUB; другая валюта остаётся blocked. Текущие draft/approve/pay/cancel permissions не расширяются, а схемы, точные ставки и run detail доступны только действующему owner-only payroll endpoint и существующим ролям, уже имеющим право видеть соответствующие payroll amounts.
6. **История, возвраты и ошибки источника.** Legacy entries и продажи остаются без выдуманного автора или run link. Подтверждённый после закрытия run возврат создаёт lineage-linked adjustment в следующем open run и не переписывает paid amount. Hard-delete сотрудника/expense с исторической payroll-связью запрещается; применяется архивирование, история сохраняет имя/роль snapshot и связь с выплатой. При неизвестной атрибуции, net amount, refund lineage, неутверждённом табеле или недоступном tenant-scoped источнике run остаётся blocked с перечисленными причинами.
7. **Область cap.** Согласованный с MASTER preview default для `employee_department_day` — turnover строк, атрибутированных конкретному сотруднику в нужном цехе за venue-local день. Выручка между сотрудниками не делится; отдельная смена или общий цеховой фонд не выводятся из даты/стола/заказа. `venue_day` использует полный признанный дневной turnover площадки из `venueDailyTurnover`, а не общий лимит фонда. Официальный run обязан получить и проверить обе независимые базы из подтверждённых POS/Finance источников; сменный/общий cap остаётся недоступен до появления authoritative shift identity, turnover allocation и правила распределения между сотрудниками.

8. **Проверенная база фиксированной сменной оплаты в pure-core калькуляторе.** Вход `attendance` независим от `sales` и содержит ровно одну утверждённую нормализованную строку на owner-confirmed planned shift `{ id, employeeId, date, approved, workedMinutes, plannedMinutes }`; upstream обязан объединить пересекающиеся фактические интервалы сотрудника в пределах запланированной смены. Для каждой строки рассчитывается округление half-up в копейках: `perShiftCents × workedMinutes / plannedMinutes`; каждая утверждённая плановая смена учитывается отдельно. Повторные/неутверждённые строки, неизвестный сотрудник, нулевая плановая длительность, несовпадающие кадровые даты и превышение факта над планом блокируют результат. Payroll owner-only интерфейс сохраняет неизменяемые ревизии полного табеля в migration 082. Новый `/api/payroll/versions/:id/preview/approved-attendance` в одной tenant-scoped repeatable-read транзакции берёт только актуально утверждённые смены; caller не может подменить attendance или manifest watermark. Это всё ещё неофициальный, неперсистентный сценарий: продажи, строковый автор, скидочное распределение, возвраты и revenue coverage остаются входом/ограничением сценария; этот endpoint не создаёт run, начисление или расход и не разрешает `ready` official run.
9. **Регрессии схемы и сотрудника.** Право на milestone проверяется на локальную дату события и границы `activeFrom/activeTo`; одному employee override разрешены соседние непересекающиеся effective windows, включительное пересечение блокирует схему. Любой положительный turnover без автора блокирует период независимо от commission base, чтобы пороги оборота и комиссия не расходились.

Этот default не считает конфликт разрешённым: безусловную премию нельзя совместить с абсолютным потолком выплаты в день без личной выручки. Сценарий сохраняет сумму и показывает конфликт; source-backed run при превышении должен оставаться blocked.

10. **Реализованное подтверждение политики владельцем.** Каждое создание/сохранение payroll-версии требует отдельного `payoutRiskAcknowledgement: { confirmed:true, policyCode:"payroll-own-revenue-ceiling-v1" }`. Это общее подтверждение понимания риска для каждой конфигурации, а не оценка конкретного сценария. Оно не отменяет дневной лимит, не меняет calculator eligibility и не подтверждает полноту источников. Сервер сам фиксирует active venue owner, время PostgreSQL и SHA-256 канонической конфигурации; metadata входит в `config_json` и append-only snapshot ревизии 079. Новое сохранение требует нового явного подтверждения; UI сбрасывает checkbox при правках. Активация блокирует версию, заново читает конфигурацию и сверяет policy/digest. Старый черновик без подтверждения нужно повторно сохранить; активная история не переписывается. Отдельных DB таблиц/миграций и финансовых записей этот механизм не создаёт.

## 13. Критерии готовности будущей реализации

- Любой результат можно воспроизвести из неизменяемой версии формулы, конфигурации, sales line inputs и локального календаря.
- Две позиции одного чека могут начисляться разным сотрудникам; незаданные attribution не присваиваются молча.
- Персональный override независим по параметрам, включая 0, и журнал изменений объясняет область воздействия.
- Повторный preview/run/pay не удваивает суммы или расходы; tenant isolation подтверждён.
- Выплаченный период не пересчитывается молча; correction имеет lineage и аудит.
- Dashboard, сравнение схем, calculation detail и payroll entries строятся из того же snapshot source.
- Financial report учитывает связанный expense один раз; order/payment/loyalty ledgers после salary calculation неизменны.
- Каждая миграция additive/replay-safe и проверена на legacy data и конкурентных изменениях MASTER.

## 14. Внешние отраслевые ориентиры

Эти примеры — проверяемые публичные функции готовых систем, а не автоматическое утверждение их правил для HOOKAH CRM:

- **Сквозная защита зарплатных данных:** Deputy отдельно ограничивает просмотр pay rates, стоимости смен, индивидуальных итогов и истории ставок сразу в Schedule, Timesheets, People и Payroll. Для нашей системы это аргумент проверять permission не только в редакторе схемы, но и на каждом ответе, отчёте и деталях; конкретная матрица доступа остаётся продуктовым решением владельца. [Deputy: Managing access to sensitive pay rate information](https://help.deputy.com/hc/en-au/articles/15900797384975-Managing-access-to-sensitive-pay-rate-information)
- **Расчётный запуск из проверенных первичных данных:** Payroll Dashboard Deputy формирует run из approved timesheets, показывает итоги, сотрудников и разбивку по pay rates; предыдущие runs доступны для повторной проверки и аудита. Для нас это поддерживает отдельные стадии preview → проверка/фиксация → существующие approval/pay, с сохранением расчётной детализации и версии правил. [Deputy: How do I use my Payroll Dashboard?](https://help.deputy.com/hc/en-au/articles/16410101615759-How-do-I-use-my-Payroll-Dashboard-US)
- **Сравнение стоимости с альтернативным правилом:** Deputy Pay Comparison пересчитывает данные периода по выбранной comparison rate и показывает разницу на уровне сотрудника и pay rule. Это подтверждает полезность нашего сравнения схем только при одинаковых входных данных и явном baseline; результат сравнения не должен считаться проведённым начислением. [Deputy: Pay comparison report](https://help.deputy.com/hc/en-au/articles/5337848247567-Pay-comparison-report)
- **Гибкая комиссия и неизменяемая атрибуция:** Square поддерживает персональные ставки, фиксированный процент и пороговые ставки по сумме или количеству проданных позиций; в примере атрибуция фиксируется в момент продажи и не меняется постфактум. В настройке также отдельно выбирается комиссия от исходной цены или цены после пакетной скидки. Для нас это подтверждает необходимость versioned item rules, явной базы комиссии и неизменяемого исполнителя/price snapshot; персональный override и правила скидочного распределения ниже остаются решениями HOOKAH CRM. [Square: Set up and manage commissions](https://squareup.com/help/us/en/article/7145-set-up-commission-tracking)
- **Начисление отделено от реальной выплаты:** Square импортирует комиссии и часы в pay run, позволяет проверить период и построчные суммы перед подтверждением; отдельно различает чаевые, уже выплаченные наличными, и суммы, которые будут перечислены через payroll. Для нас это хороший контрольный образец против двойной выплаты и основание сохранять preview → draft/approval → paid через существующий `payroll_entries`/связанный expense. Продуктовые роли и налоговую часть Square мы не переносим. [Square: Run payroll for W-2 employees](https://squareup.com/help/us/en/article/5855-run-payroll)

Применение этих ориентиров к HOOKAH CRM является архитектурным выводом, а не заявлением о финансовом или юридическом соответствии продукта Deputy. Региональные нормы, налоги, overtime и payroll export остаются вне этого калькулятора до отдельного продуктового решения.

### Personal target scenario contract — 2026-10-03

- `personal_target` — employee/day, независимо от других дней и накопительного turnover. Параметры роли/overrides: `targetCents`, `baseRateBps`, `bonusRateBps`, `excessRatePolicy`, `perShiftCents`. База плана — eligible commissionBaseCents; `employee_day_commission_base_scenario` не доказывает личную Finance-net выручку. Политика component_half_up_v1 сохранена в формуле; ставки сверх плана явные replace_base/add_to_base.
- Replacement item rule исключает строку из attainment/пороговой комиссии и платит её обычным процентом; additive оставляет строку в плане и добавляет построчную комиссию. Дневной порог распределяется пропорционально базам методом наибольших остатков; раздельно округлённые компоненты распределяются по соответствующим below/excess weights. Сумма line commissions совпадает с дневной employee commission до caps.
- Owner create/edit → existing payroll routes → typed validation → PostgreSQL version+child rows → revision/digest → reload/activation → scenario preview подтверждены изолированным PG roundtrip. Migration 083 расширяет лишь named mode/path CHECK, replay дважды; исходная 077 неизменна. До schema upgrade новый mode/path CHECK отвечает 409 с rollback, не частичной записью.
- UI показывает дневной план, базу, превышение, обе части комиссии и распределение по строкам. JSON editor остаётся промежуточным; редактируемая сетка/карточка сотрудника полного ТЗ ещё не закрыты.
- Пороговая строка имеет `appliedRateBps:null`: единственного достоверного scalar rate нет. Serializer явно отказывает `payroll_snapshot_incentive_schema_required` (включая mixed role modes), пока typed incentive snapshot contract не реализован. Official run остаётся blocked.
