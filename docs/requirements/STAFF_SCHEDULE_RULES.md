# График сотрудников: правила и приёмочные сценарии

Статус14.10: локальная runtime-приёмка расширения выполнена.27 suites PASS, включая recovery101–103, calendar и keyboard; отчёт acceptance-1791962120575.json. Доказательства и ограничения в STAFF_SCHEDULE_HANDOFF.md и WORK_LOG.md. Production не публиковался.

## Правила

### Согласованное расширение 14.10

- Неделя, сетка месяца Пн–Вс, почасовой день и список используют одни записи. Ночные продолжения загружаются по пересечению интервала, ссылаются на исходный ID и не прибавляются к итогам по дате начала. Ровно 00:00 не занимает следующий день. Дневная шкала строится по реальной длительности суток; в редкий день с неоднозначной полуночью используется явный карточный вид вместо неверного масштаба.
- Черновик — отдельный набор до 200 явных операций на период до 93 дней и до 100 сотрудников. Он не меняет live-график, фактические часы или утверждённую зарплату. Пропуск строки не означает отмену. Доступ к черновикам и шаблонам требует manage.
- Публикация требует отдельного canPublish: owner автоматически, admin/manager только по выдаче владельцем. **Совместимость:** manage сохраняет непосредственное редактирование live-графика и копирование недели. Это необязательный процесс планирования, не запрет прямой правки и не обязательное согласование каждого изменения. UI обозначает это явно.
- Публикация проверяет неизменность исходной области, версию, часовой пояс, активность назначаемых сотрудников и конечный план целиком; применяет строки/историю/закрытие атомарно. Разрешены корректные перестановки смен. Конфликт требует нового черновика на свежей основе, автоматического rebase нет. Опубликованный/закрытый черновик остаётся читаемым и неизменяемым.
- Шаблон — именованная версионируемая комбинация интервалов и дней недели либо цикла с датой-якорем. Цикл 2/2: четыре дня, рабочие смещения 0 и 1. Неуказанные дни остаются незапланированными. Изменение/архивирование шаблона не меняет существующие графики. Массовые отсутствия задаются диапазоном и нужными днями повторения.
- Предпросмотр не пишет данные. Применение диапазона атомарно добавляет предложения в черновик, не делает неявный upsert/замену. Конфликтный набор целиком отклоняется; отдельные предложения можно корректировать в редакторе. DST gap/fold не нормализуются молча.
- Закрытие редактора с изменёнными полями требует подтверждения. После успешной записи и ошибки чтения родитель показывает сохранение с недоступным readback и повтором загрузки, не оставляя устаревшие действия.
- Обеспеченность по должностям/часам, обязательное согласование всех прямых изменений, уведомления и запросы сотрудников не входят в этот пакет; автоматические юридические нормы не вводятся.

1. График — план работы, не кассовая смена и не фактически отработанные часы. Никаких автоматических начислений, выплат или открытия кассы.
2. Владелец имеет доступ. Администратор и управляющий по умолчанию доступа не имеют. Владелец выдаёт конкретному пользователю просмотр либо управление (включает просмотр), может отозвать. Широкое staff_manage не даёт доступ к графику. Получатель не может делегировать права или менять их себе.
3. Все чтения, изменения, селекторы, история, итоги и копирование ограничены текущим заведением. Выбранный сотрудник должен принадлежать ему. Селектор возвращает только id, имя, должность и активность, без login, контактов, кадровых данных или permission scopes.
4. Основной вид — неделя, строки сотрудников, столбцы дат. Месяц — обзор загрузки. На узком экране — список дней/смен. Отсутствие записи означает «Не запланировано», а не выходной.
5. Тип записи: смена либо отсутствие (выходной, отпуск, больничный, другое). Отсутствие занимает календарный день заведения и запрещает пересекающую этот день смену. Оно не считается оплачиваемым фактом. Причину показывать кратко без медицинских подробностей.
6. Несколько смен за один день разрешены без пересечений. Интервалы полуоткрытые [начало, конец): окончание одной в 18:00 и начало следующей в 18:00 допустимы. Перерыв внутри смены не разрешает другую пересекающую смену.
7. Начало/конец задаются в часовом поясе заведения; сохраняются как абсолютные моменты. Дата смены — местная дата начала. Конец выбирается явно, включая следующий день. Длительность >0 и не более 24 часов, как предел существующего payroll snapshot, а не утверждение о трудовых нормах. Неоднозначное или несуществующее местное время нельзя молча нормализовать.
8. Перерыв — целое количество неоплачиваемых минут, 0 <= перерыв < длительность смены. Плановые минуты = длительность − перерыв. UI подписывает именно неоплачиваемый перерыв. Настройка юридических норм и расчёт оплаты больничных в модуль не входят.
9. Перенос и замена сотрудника — обновление одной записи с новой версией и историей до/после. Проверяются новый сотрудник, даты и пересечения. Архивного сотрудника нельзя назначить, но его история остаётся видимой; отмена исторической записи разрешена с причиной.
10. Отмена сохраняет запись и историю, требует причины, исключает её из действующего плана. Физического удаления в UI/API нет. Коррекция прошлого периода требует явного предупреждения и причины, не переписывает утверждённую зарплату.
11. Оптимистическая версия защищает от потерянного редактирования. При 409 введённые данные остаются в форме; пользователь сравнивает с актуальной записью. Сохранение, история и защита пересечений выполняются атомарно. Повтор запроса с тем же ключом не создаёт дубль.
12. Копирование недели: источник, целевая неделя, выбранные сотрудники, preview и отдельное подтверждение. Переносится местное время, а не фиксированные 168 часов UTC. Конфликтный пакет не сохраняется частично. Пользователь снимает конфликтующие строки либо исправляет цель и повторяет preview. Отмена preview не меняет БД.
13. Итоги показывают план смен, чистые часы и фактические часы раздельно. Ночная смена принадлежит дате начала; период явно подписан «по дате начала». Дополнительные отображения продолжения на следующий день не увеличивают число смен/часов повторно.
14. Payroll читает только действующие смены, учитывает неоплачиваемый перерыв, не читает отсутствие как смену. Утверждённые attendance snapshots неизменяемы. Новая версия плана должна обнаруживаться проверкой актуальности источника; требуется отдельное переутверждение, не скрытая корректировка начисления.
15. Загрузка, пустой период, отсутствие сотрудников, ошибка чтения, запрет, сохранение и конфликт имеют разные состояния. Ошибка не стирает форму. Ответ от старого периода/заведения не заменяет текущие данные. Успех показывается после сохранения и подтверждается повторным чтением.

## Матрица обязательной приёмки

| Сценарий | Доказательство |
|---|---|
| Owner выдаёт admin/manager просмотр/управление, затем отзывает | HTTP + браузер после reload; сервер запрещает запись после отзыва |
| Admin без выдачи и сотрудник другого заведения | 403; отсутствует чужая информация в ответе |
| Создание, правка, перенос, замена, отмена | UI → API → PostgreSQL → reload; история содержит автора и версии |
| Две соседние смены, пересекающиеся смены, ночная смена | соседние принимаются, пересечение отклоняется, ночь не удваивается |
| Отсутствие, неоплачиваемый перерыв, пустой день | корректные подписи и итоги, отсутствие не создаёт оплату |
| Архивирование сотрудника во время редактирования | сохранение отклоняется без потери ввода; история остаётся доступной |
| Два параллельных редактора и двойной клик | нет lost update, дубля, частичной истории |
| Копирование недели с конфликтом и без | preview без записи; атомарный apply; идемпотентность |
| Смена месяца/года, часовой пояс и переход времени | дата начала и длительность правильны; неоднозначное время явно разрешается |
| План до/после payroll approval | snapshot не изменён; stale источник обнаружен; факт не подменён планом |
| Desktop/tablet/mobile/Fold, обе темы | отрендеренные скриншоты; фокус, контраст, длинные имена, плотные данные |

## Решения по независимому аудиту

Приняты: отдельный hash, узкие права, история/версия, сохранение payroll snapshots. Не принят вариант фильтрации полного /api/staff только во frontend: это не защита данных. Не принят временный доступ через staff_manage: противоречит owner-controlled выдаче. Старые snake_case ответы должны сохраняться либо иметь явно проверенный адаптер; молчаливое изменение контракта запрещено. Legacy upsert нельзя применять к неоднозначному дню с несколькими сменами: требуется явная ошибка, а не выбор произвольной записи.
