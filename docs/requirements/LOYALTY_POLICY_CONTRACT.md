# Контракт правил лояльности для L11

**Статус:** implementation contract для локальной системы. Совместимые значения по умолчанию сохраняют текущую математику; менять финансовые параметры можно только явным действием владельца/администратора и с новой версией правил. Рыночное сравнение — ориентир, не утверждённая политика заведения.

## Текущие источники правил

| Правило | Где сейчас живёт | Область действия | Состояние |
|---|---|---|---|
| Скидка группы | `guest_discount_groups.discount_percent`; `/api/discount-groups` | Группа гостя в одной площадке | В заказе фиксируется при привязке гостя |
| Начисление бонусов | `guest_discount_groups.bonus_percent` | Группа гостя, заказ при полном закрытии | Снимок ставки/базы/суммы на заказе; целые баллы, округление вниз |
| Минимум VIP-заказа | Группа/поля VIP заказа | Конкретный заказ/место | Ограничивает итог снизу, не становится eligible базой бонусов |
| Курс списания | Константа в POS/server | 1 бонус = 1 ₽ | Временная техническая политика |
| Максимум списания | `loyalty_program_settings.max_redemption_percent`; `/api/loyalty/settings` | Версионируется по площадке; снимок cap фиксируется при создании заказа | Совместимый default — 100%; owner/admin может задать cap для новых списаний |
| Срок бонусов | Не хранится и не вычисляется | — | Автоматического сгорания нет |
| Денежный счёт гостя | `deposit_balance` и денежный ledger | Обязательство гостя в валюте площадки | Не бонусы и не предоплата брони |

Группа — сегмент гостя, а не единая программа. Редактор `/admin#loyalty` и API `/api/discount-groups` управляют группами. В L11.3 добавлено отдельное пространство настроек `/api/loyalty/settings` и блок общих правил на `/admin#loyalty`; версионированная таблица `loyalty_program_settings` хранит лимит и минимум первой операции; новый заказ получает снимок активной версии. Курс остаётся фиксированным 1 бонус = 1 ₽: payment tender сейчас хранит целую сумму бонусов одновременно как денежную сумму, поэтому переменный курс пока скрыт/недоступен. Истечение не включено.

## Реализованный контракт настроек (L11.3)

| Элемент | Контракт |
|---|---|
| Чтение | `GET /api/loyalty/settings`; venue берётся из аутентифицированного контекста, `expectedVenueId` может проверить его актуальность. Чтение доступно сотрудникам с `orders`, `loyalty` или `staff_view`. Пустая конфигурация возвращает legacy defaults: version 0, курс 1, cap 100%, минимум 1, expiry null. |
| Изменение | `PATCH /api/loyalty/settings` только для ролей owner/admin. Требуются `expectedVenueId`, `expectedVersion`, `bonusRublesPerPoint:1`, `maxRedemptionPercent:0..100`, `minimumRedemptionPoints:1..1000000`. Срок и неизвестные поля сервер отклоняет. |
| Конкуренция и аудит | Версия неизменяема: PATCH добавляет новую запись, блокирует строку venue, проверяет версию и вставляет venue-scoped audit event в той же транзакции. Ошибка аудита откатывает изменение. |
| Применение | Заказ фиксирует версию, курс, cap и минимум при создании. Денежная база фиксируется при первой бонусной оплате; последующие оплаты используют её. Старые заказы без снимка сохраняют legacy defaults (version 0, cap 100%, минимум 1), а изменение правил не пересчитывает уже открытые/закрытые заказы. Разделение заказа переносит его исходную версию. |
| Ошибки | `403 loyalty_settings_owner_admin_required`; `428 venue_precondition_required`; `409 venue_context_changed` или `loyalty_settings_version_conflict`; `400 invalid_loyalty_settings`/`unknown_loyalty_setting`; `503 loyalty_settings_save_failed`/`loyalty_settings_unavailable`. |
| POS | `GET /api/orders/:id/payments` возвращает `bonusRedemptionRemaining` и `bonusRedemptionPolicy`; клиент ограничивает поле по остатку долга, балансу и cap, сервер повторно проверяет их при POST. Минимум обязателен для первой операции списания; последующая операция может быть меньше, чтобы использовать остаток cap/баланса. |

L11.3 регрессия подтвердила memory и PostgreSQL defaults, создание и повторное чтение версии, stale venue/version, отказ PATCH роли manager, sibling-venue isolation, minimum/cap, rollback при ошибке аудита и сохранение политики, захваченной при создании заказа, после следующего изменения настроек. Курс нельзя разрешить менять, пока тендер не будет хранить независимые единицы «баллы» и «рубли» и начисление/списание не пересчитают их через курс.

## Ограничения текущей конфигурации и следующие подэтапы

Базовое хранилище и версионирование настроек списания реализованы. Сейчас поддерживаются cap списания и минимум первой бонусной операции. Курс временно закреплён 1:1, expiry выключен. Для курса нужен тендер с отдельным количеством баллов и рублёвой суммой; для срока нужны партии начислений, распределение списаний и безопасное сторно.

### Реализовано в L11.5: управление кампаниями

`loyalty_promotions` — отдельная от групп гостей venue-scoped сущность; каждая новая редакция создаёт неизменяемую версию и scopes. Настраиваются название/описание, период, IANA timezone, percent/fixed выгода, приоритет и включённые/исключённые активные товары и категории. Категории — значения `products.category`; включение требует хотя бы одного товара или категории, исключения перекрывают включение. Период хранится в UTC; административный интерфейс переводит локальные дату/время через выбранный IANA timezone, расчётный интервал полуоткрытый `[startsAt, endsAt)`.

`GET /api/loyalty/promotions` читает кампании в текущем venue контексте и принимает `expectedVenueId`; `includeArchived=true` возвращает архивные последние версии. POST/PATCH доступны только owner/admin, требуют площадку и версию для изменения, проверяют каталог той же площадки, ведут атомарный аудит в PostgreSQL. Архивирование добавляет версию, история защищена от UPDATE/DELETE триггером. Новая запись всегда черновик. Активация создаёт новую активную версию и влияет на новые ещё не зафиксированные заказы; первая принятая оплата фиксирует цену и snapshot акции, поэтому последующие правки кампании не переоценивают такой заказ. Активная кампания может менять сумму оплаты и pending revenue, но не бонусы, депозит или предоплату.

Ограничения первой конфигурационной версии: нет расписания по дням/часам, промокодов, лимитов частоты/бюджета, аудитории гостя, минимальной суммы заказа и приоритета «ручное подтверждение». Они не включены скрыто; добавить можно отдельными требованиями. Реализованный L11.6 применяет eligibility/выбор и объясняет POS причины; визуальная приёмка desktop/mobile пройдена в L13.3.

### Контракт L11.6 — реализован

Для одной и той же товарной суммы сервер должен:

1. Отсеять неактивные/просроченные акции и строки, не проходящие площадку, время и товарно-категорийные условия.
2. Рассчитать каждое автоматическое предложение отдельно и показать причины включения/исключения.
3. Не суммировать group/manual/promo discounts; сравнивать фактическую скидку после округления. Равенство разрешать стабильно: среди промо — больший priority, затем меньший promotionId; между типами — promotion > guest_group > manual. Это сохраняет прежнее преимущество группы перед ручной скидкой и задаёт явное место промо.
4. Считать ручную скидку отдельным согласованным предложением; сохранить действующее правило, что group/manual не складываются.
5. Применить VIP minimum после выбранной скидки как floor. Он не меняет товарную базу начисления бонусов.
6. Применять bonus tender после цены/скидок к остатку, не изменяя скидочную цену и не начисляя бонусы на часть чека, закрытую бонусным tender.
7. Не суммировать бонусы, деньги гостевого счёта и предоплату брони со скидкой: это способы оплаты уже рассчитанной суммы.

Заказ хранит выбранные условия и offers; migration 090 дополнительно сохраняет immutable eligible item IDs и gross/discount/net minor units каждой строки. Зафиксированная первая оплата не переоценивается после изменения или архива кампании. Единый evaluator выбирает best-only цену; при равной выгоде порядок типов — promotion > guest_group > manual, внутри promotion больший priority, затем меньший promotionId. Pending revenue использует тот же расчёт. Активация и первая оплата сериализуются venue-level lock. PostgreSQL/browser QA проверяет quote, частичную оплату, последующую активацию версии, неизменность зафиксированной цены, историческое чтение, fractional-cent allocation и гонку активации с первой оплатой.

Срез по публичным правилам заведений, проверен 2 октября 2026 года. Он показывает варианты рынка, а не отраслевую норму и не готовые числа для HOOKAH POS.

В этой небольшой выборке лимит в опубликованных программах — 20% (Grizzly, HookahPlace, Shishka и Камин), но существуют разные источники/сроки бонусов и разные eligible товары. Практическая рекомендация для обсуждения владельцем: оставить 1 бонус = 1 ₽ как легко объяснимую единицу, добавить настраиваемый процентный cap с временным совместимым значением 100% либо согласовать снижение примерно до 20%; не вводить сгорание старого баланса при включении срока на будущие начисления; поддержать исключение позиций и правило, что один и тот же товар не получает одновременно скидку/бонусное начисление, когда бонусом оплачена его часть. Сравнение не доказывает прибыльность ни одного значения — для выбора нужно проверить валовую маржу и средний чек конкретного заведения.

## Тестовая матрица для L11.3–L11.4 и будущих кампаний

| Слой | Обязательные проверки |
|---|---|
| Модель акции | Percent/fixed округление денег; ограничение скидки товарной базой; пустое/пересекающееся included/excluded scope; архив; начало/конец периода и локальный часовой пояс; дни/время через полночь; неактивный/удалённый товар; минимальная сумма до и после исключённых строк |
| Выбор предложения | Best-only по максимальной сумме; при равенстве promotion > guest_group > manual, внутри акций priority по убыванию и стабильный promotionId; ручная скидка с причиной/согласованием; без скрытого stack; VIP minimum floor после скидки |
| Цена/оплата | Bonus/deposit/prepayment не меняют discount price; bonus tender caps eligible remaining amount; смешанные tender не превышают due; бонусы не начисляются на часть, покрытую bonus tender; возврат не меняет цену закрытого заказа |
| Настройки и конкурентность | Venue isolation; unauthorized GET/PATCH; отдельное management permission; version conflict; повтор с тем же idempotency key; изменение правил между созданием заказа, оплатой и закрытием; закрытый заказ остаётся с неизменным snapshot |
| Журнал/отчёты | Каждый candidate имеет eligible/excluded reason; выбранная акция, правила и округление воспроизводимы; audit before/after; earned/redeemed/refunded/expired (если появится lot model) сверяются с гостевым балансом и сменой |
| UI и перезагрузка | Loading/empty/error/success; сотрудник может понять выгоду и причину; настройки перечитываются после reload; страница не показывает неподтверждённые числа как утверждённые; narrow POS не переполняется |

Знаки acceptance: чистая миграция и upgrade replay; memory + PostgreSQL; tenant/RBAC; idempotency и гонки; UI action → live API → DB → reload; source/dist asset parity; локальный smoke. Написание отдельного статического контрактного теста может начаться до принятия бизнес-чисел, но release/roadmap step нельзя считать завершённым без рабочих API/UI сценариев и их QA.

## Открытые подтверждения владельца

1. Сколько рублей даёт один бонус и можно ли изменить курс для будущих начислений/списаний?
2. Каков максимум бонусной части заказа; допустимо ли полностью закрывать eligible остаток бонусами?
3. Есть ли срок сгорания, как уведомлять гостя, с какой даты правило действует и как разбираются возвраты?
4. Какие товары/категории исключены из скидок и начисления; какая база начисления применяется при смешанной оплате?
5. Разрешено ли акции суммироваться с уровнем гостя; требуется ли предварительный ручной override и какие лимиты авторизации?
6. Общие ли группа/бонусы для сети заведений или у каждого venue независимые правила и баланс?

Настройки программы можно реализовать с совместимыми defaults и доступным owner/admin явным сохранением новой версии; это не меняет действующие значения само по себе. Новые акции до уточнения механик остаются выключенными. Необратимое сгорание остаётся недоступным до lot-based ledger.

## Сквозной стык POS → Loyalty → Finance → Payroll: скидка и частичный возврат по строкам

**Статус на 4 октября 2026: локальный ценовой снимок по строкам и возврат товарной стоимости реализованы через миграции 090–092 и сквозные проверки. 092 удостоверяет только порядок новых событий после миграции; существующие 091 события остаются без sequence и не перестраиваются. Это подтверждает факты цены/товарного возврата, но не включает официальный зарплатный расчёт и не реконструирует старые строки без снимка.**

| Область | Фактический источник сейчас | Чего он пока не доказывает |
|---|---|---|
| Проданная строка | POS-снимок 090 хранит `order_item_id`, исходные seller/time, количество, цену и суммы в RUB minor units. | Legacy locked/closed orders без снимка остаются unknown; исторические факты не восстанавливаются из текущего каталога. |
| Выбор скидки | `loyalty-pricing.js` возвращает best-only winner, offers с `eligibleItemIds` и line allocations gross/discount/net minor units. POS 090 атомарно сохраняет их при первой принятой оплате или прямом закрытии; eligible set берётся из результата evaluator, не выводится позже из каталога. | Снимок доказывает источник и денежное распределение, но сам по себе не разрешает зарплатное начисление или attribution неполных/чужих сотрудников. |
| Денежная выплата и товарный возврат | 088 сохраняет внешний payout по tender, 091 — товарные строки/количество/value по 090, а 092 добавляет per-source `producer_sequence` и immutable previous/cumulative facts. | Внешний payout не равен автоматически товарной стоимости; строки без исходного 090 snapshot остаются unattributed. Старые 091 события остаются unsequenced без вывода порядка из timestamp/UUID; первый post-092 baseline может содержать их агрегат без полной исторической хронологии. |
| Payroll | Payroll может читать подтверждённые исходные seller и frozen line price/return evidence как отдельные источники. | Официальный расчёт остаётся fail-closed при неполном seller, discount, refund, department, cost или coverage; миграции 090–092 сами не подтверждают payroll readiness. |

### Выбранная политика для line-level реализации

1. **Распределение единственной выбранной скидки по строкам — выбрано.** Групповая/ручная скидка распределяется по всем товарным строкам заказа; promo — только по фактически выбранным evaluator eligible lines. Итог скидки хранится в копейках, распределяется пропорционально gross с методом largest remainder, равенство решается по возрастанию `order_item_id`. Сначала gross line cents согласуются с исходным order subtotal: точные PostgreSQL numeric `quantity * unit_price` округляются до копейки на уровне заказа; недостающие копейки распределяются по остаткам дробной части с тем же стабильным ключом. Это сохраняет сумму чека при дробных количествах и не опирается на JS float. Winner, версия/источник правил и eligible item IDs фиксируются вместе с line gross/discount/net атомарно при первой принятой оплате. Изменения каталога, акции, категории и seller позже ничего не пересчитывают.
2. **Частичный возврат товарной стоимости — выбрано.** Для каждой строки value возвращённого количества вычисляется из исходного immutable net snapshot. Для cumulative quantity: `round_half_up(original_line_net_cents * cumulative_returned_qty / original_qty) - previously_returned_item_value_cents`, PostgreSQL `numeric`, исходная шкала количества `numeric(12,3)`. Полное количество возвращает ровно исходный line net; сумма/количество не могут превысить остаток. Фактический payout и tender остаются отдельными фактами Finance. Возвраты без связанной строки или исторического snapshot остаются `unattributed`; employee inference запрещён.
3. **Разделение складских и payroll effects — выбрано.** VIP minimum adjustment остаётся заказной суммой вне seller/item lines. Возврат сам по себе не создаёт stock movement: складская пригодность товара требует отдельного подтверждённого действия приёмки. Возвратная дата, clawback/offset и распределение эффекта по сотрудникам задаются versioned payroll policy; обязательный исходный seller строки из ТЗ не заменяется заказчиком или cashier.

### Критерии после решения

- **Реализовано локально:** winner, eligible IDs, reconciled gross cents, discount cents и line net сохраняются неизменно при первой принятой оплате/прямом закрытии; PostgreSQL сверяет состав и deterministic largest-remainder allocation. Focused QA проверяет две строки `0.5 × 0.01 ₽`, 100% promotion, стабильный tie по `order_item_id` и round-trip сохранения.
- **Реализовано отдельно в Finance:** частичные/полные item returns ограничены исходными количеством и line-net cents с учётом уже возвращённого; повтор, конфликт ключа, гонка, rollback и общий payout report покрыты PostgreSQL/browser QA. Исходный closed order/payment не переписывается.
- Cash/card/QR payout остаётся отдельной append-only записью Finance; bonus/deposit/reservation reversals идут в соответствующих liability ledgers; legacy возвраты без доказуемого 090 line link явно остаются unattributed.
- UI → API → PostgreSQL → reload, tenant/RBAC и расчёт line allocation покрыты тестами 090/091; 092 добавляет тест последовательности при совпадающих transaction timestamps и сохранения unsequenced legacy baseline. Payroll потребляет только подтверждённые line facts, а не пересчитывает их; official readiness отдельно остаётся неподтверждённой.
