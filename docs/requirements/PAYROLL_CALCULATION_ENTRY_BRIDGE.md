# Связь сохранённого расчёта и начисления

## Продуктовый контракт

Гибкая схема рассчитывает совокупную зарплату сотрудника за период: оклад, процент, премии и ограничения являются компонентами одной суммы. Владелец выбирает сотрудника сохранённого расчёта и создаёт одно начисление в `payroll_entries`. Сумма, период и исходный расчёт не вводятся повторно.

Старые записи по разным правилам могут быть отдельными компонентами. MASTER подтвердил 23.10.2026: их существующие пересечения сохраняются; новый совокупный расчёт не может пересекаться ни с другим совокупным расчётом, ни с активной старой записью. Поэтому ранее подготовленный всеобщий exclusion не устанавливается. Миграция202 реализует две GiST exclusion: mixed legacy/run и run/run, для `draft/approved/paid`, с включительными границами дат. Отменённые записи освобождают период, но сохраняют исходную связь run/employee навсегда. Ошибочная историческая дата блокирует upgrade без исправления данных.

## API и права

- `GET /api/payroll/calculation-runs/:runId/entries`: owner, список связанных начислений в своей площадке.
- `POST` на тот же маршрут: owner, ровно `employeeId`, `financeCategoryId` (UUID или null), `idempotencyKey`. Сервер получает сумму и период из сохранённых доказательств; caller не передаёт сумму или разрешение на запись.
- Существующие GET/PATCH начислений сохраняют финансовые права. Настройка схем и создание начисления из расчёта принадлежат только владельцу.
- POST возвращает `{schemaVersion,entry,replayed,existing}`. Повтор исходного ключа возвращает исторический результат и отдельный `currentEntry`, чтобы отмена была видна без переписывания исходного ответа.
- Новый ключ для существующей связи возвращает ту же запись; другую категорию не подставляет. Отмена не позволяет восстановить или заново создать начисление по тому же run/employee.

## Транзакция

Exclusive source session fence берётся до BEGIN REPEATABLE READ READ WRITE. Затем повторно проверяется действующий owner, ключ запроса, saved evidence, воспроизводимость движка, точная сумма сотрудника в daily snapshots и свежесть всех источников. Запись начисления и неизменяемого ответа запроса коммитятся вместе. Потеря ответа, конкуренция и rollback не создают второй draft. GiST проверяет конфликт с одновременными legacy writes независимо от snapshot isolation.

В БД сохраняются run, provenance SHA, gross cents, имя сотрудника и схемы, автор и время. Привязка возможна только при INSERT. Нельзя привязать старую запись, убрать ссылку, заменить сумму/период/сотрудника, удалить историю или воскресить отменённую запись. Величины сверх `numeric(12,2)` отклоняются без округления и усечения.

## Текущая граница готовности

Связанное начисление создаётся как черновик. `officialReady=false`, `payoutEligible=false`. Миграция запрещает approved/paid и expense/payment metadata, существующий PATCH возвращает понятный отказ до обращения к расходам. Разрешена отмена. UI показывает эту границу и не предлагает утверждение/выплату.

Это часть общей реализации, не завершение зарплатного модуля. Чтобы открыть денежный цикл, остаются correction-aware source capability, явное решение владельца по позднему возврату, однократное применение только к выбранному открытому draft с защитой фиксированной части, затем источниковые проверки approve/pay, единственный expense и сквозная финансовая приёмка. Прочие режимы исходного ТЗ остаются обязательными.

Финансовый контракт не меняется: draft не входит в P&L; approved/paid `amount` распределяется по календарным дням расчётного периода; payroll expense отражает денежную выплату один раз. Дневные snapshots не создают самостоятельный дополнительный расход.


## Обновление205: owner lifecycle и текущая сумма

Предыдущая граница draft-only описывает состояние202. С205 связанное начисление проходит owner-only `GET /api/payroll/calculation-entries/:id/state` и `POST /api/payroll/calculation-entries/:id/transition`. POST принимает ровно action, expectedStateHash, idempotencyKey, paymentDate, paymentAccountId, paymentMethod, reason; неиспользуемые поля равны null. GET — предварительная проверка, а approve/pay заново проверяют источники и полный ledger203 в своей транзакции. Generic PATCH отклоняет все действия с linked начислениями.

Создание сохраняет старый неизменяемый receipt202 в `.entry`. Актуальный `.currentEntry` возвращается отдельно при каждом ответе, включая первый; список связей также показывает actual net amount и frozen gross. UI предпочитает currentEntry, а действия получает из lifecycle state. Исторический receipt не служит разрешением выплатить деньги. Нулевое завершение не создаёт фиктивный расход. После потери ответа браузер сохраняет точный запрос/ключ под owner+venue+entry и восстанавливает его после перезагрузки.

Остаток общей цели: полный открытый расчёт с возвратами204, денежное подключение корректировок и все нелинейные режимы/исторические основания; завершение205 само по себе не закрывает эти требования.

## Обновление203/206: явные денежные корректировки

Owner API: `GET /api/payroll/calculation-entries/:id/corrections`, `POST /api/payroll/reviewed-corrections/preview`, `POST /api/payroll/reviewed-corrections`. Применение требует выбранного draft того же сотрудника за более поздний период; waiver цели не требует. Полный intent/plan hash/ключ сохраняются до отправки. При восстановлении UI читает текущую сумму цели отдельно от исторической квитанции. Paid original с нулевой выплатой подтверждается неизменяемым205 zero transition и журналом запроса вместо расхода (206); incoming corrections не становятся собственными возвратами.

Local actual-source PG/browser23185 PASS: применение, отмена/release, нулевое завершение, собственный последующий возврат, waiver, rollback и exact replay. Нелинейная оценка и полный открытый пересчёт204 остаются отдельным незавершённым требованием.
