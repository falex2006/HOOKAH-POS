# Payroll calculator input contract

**Status:** implemented fail-closed candidate boundary; not a source adapter, calculation, run, or payout approval.

`payroll-calculation-input-contract.js` is the pure validation boundary between server-owned payroll evidence and `calculatePayrollScheme`. It does not query data or infer missing rows. The sourced-preview API includes the contract result so the caller can see why real source evidence cannot yet be handed to the calculator.

## Required envelope

An eventual `sourceBundle` must bind the selected tenant, saved scheme version, currency, exact period, and readiness-component fingerprint. Every required component must be `available`, carry a SHA-256 source watermark and non-empty watermark scope, and match tenant/currency/period. The bundle itself must carry an input watermark equal to the canonical fingerprint of its contents. Required collections are supplied explicitly; missing rows must not be replaced with empty arrays. Calculator coverage and attendance coverage must both cover the complete period from the first day of that month.

The candidate input must include employee identities, effective role assignments, approved attendance rows, recognized sale lines, and venue daily turnover when the selected mode consumes it. Employee IDs and active dates must exactly match the owner-attested eligibility revision bound into the same source bundle; a matching checksum without matching roster/period rows is insufficient. A revision ID mismatch, missing employee, extra employee, or changed date interval blocks the bundle. Gaps and multiple disjoint employment intervals are preserved explicitly. The pure wage engine now consumes closed, non-overlapping `activeIntervals` across role coverage, attendance, line attribution, daily membership, team-fund recipients, and milestone eligibility. The interval capability does not certify source completeness or enable an official calculation. Configuration dependencies are selected from the seven-mode availability matrix. Department, team, margin, personal net revenue, and closed-month sources are required only when the selected mode/configuration requires them.

The sourced-preview service now carries verified approved-attendance rows and their full-period coverage internally from the same owner-checked `REPEATABLE READ READ ONLY` transaction. The rows are validated by the existing attendance manifest loader against the saved approval and current source watermark. They are not returned in the public preview DTO. The partial bundle deliberately omits employee, role, sales, and other unattested collections, so this source alone remains blocked and cannot produce a calculator input.

Before a source bundle can be returned as calculator input, its row collections are checked for unique UUIDs, employee references, exact saved-scheme role assignments, valid non-overlapping role intervals, and one role on each employee active day. Attendance rows must be approved, unique, within the selected period, and internally consistent in planned/worked minutes. Sales rows must be unique, period-scoped, currency-consistent, attributable to a bundled employee or explicitly null, and have valid payroll department keys and safe non-negative amounts. Every attendance/sale author must resolve to a role assignment on that event date. These checks are a second boundary after source watermarks; they do not certify incomplete upstream sources or replace the required owner/source attestations.

Attendance coverage must carry the exact approval watermark from its readiness component. Each sale row must carry the recognized-manifest watermark. A positive-turnover row without a seller blocks the bundle. If an employee has no narrower active window, role coverage is checked across the full selected period; missing or ambiguous coverage is never interpreted as verified non-employment.

The candidate calculator may use the unsupported signed-refund input capability only for a verified zero-related-refund snapshot. The recognition manifest must provide `relatedRefundCoverage` with the all-recorded-related-header-and-item scope, `status: complete`, an exact `sourceWatermark` equal to the manifest watermark, the same sorted period-sale order cohort as the manifest, and `coveredOrderIds` containing every such sale order. Related raw refund header, recognition event, item, and line-event ID lists must all be empty. The server loads raw headers and raw refund items by explicitly scoped order IDs without a date cutoff inside the same repeatable-read snapshot; a later refund, an unrecognized header, or an item without matched header and detailed history blocks the candidate input even when the period-only refund projection is empty. This proves only the observed history at that snapshot, not absence of a later event, and does not change `signedRefundAdjustments:false`, `officialReady:false`, or writer eligibility.

Venue daily turnover is a separate server-attested component, required only for modes/caps/milestones that consume it. Its `venueDailyTurnoverCoverage` is validated independently: exact month-start-to-period-end daily rows, safe non-negative cents, tenant/currency/timezone, component watermark and source payload binding. It must not borrow or imply line-level sales coverage. The source reports `refundsIncluded:false`, so this is a pre-refund venue aggregate and remains candidate evidence.

## Current engine boundary

The engine declares `signedRefundAdjustments:false`, `fullEmployeeNetRevenue:false`, and `historicalEmploymentIntervals:true`. A `candidate_preview` may return `status: candidate_only` with a calculator input only when all mode-dependent evidence is complete and the same snapshot proves there are no related recorded refunds. That input is for a visibly non-payable scenario preview; it is not official readiness, a saved payroll snapshot, or permission to create a run or entry. Any related refund, incomplete evidence, or failed watermark binding blocks it.

An `official` purpose remains blocked: signed refunds cannot be passed as deductions, and the engine does not consume the separate full-employee merchandise-net series. The current series is useful candidate evidence, but does not prove that all income relevant to an absolute personal cap is covered. `historicalEmploymentIntervals:true` means only that tested calculator logic accepts a verified dated roster; it does not make sourced preview ready for official calculation.

No payroll entry, calculation run, expense, payment, or POS/Finance/Loyalty/shift ledger write is performed by this contract.

## 2026-10-19 — Explicit personal revenue source

Bounded Finance review accepted `employee_attributed_merchandise_net_v1` for local no-refund source integration: all attributed immutable merchandise/service line net, including noncommissionable lines. Deposit/prepayment/loyalty liability movements are not added as revenue; paying for an already recognized sale with such tenders does not exclude its line net again. Minimum adjustment and other unattributed order residuals remain unsupported. Configurable role/employee caps remain separate and unchanged.

`calculatorInput.personalRevenueSource` is produced from rebuilt full employee net, complete all-related-refund absence and exact order/line reconciliation. It carries policy, period, currency, complete coverage, explicit employee/day net series and source hashes. Runtime always supplies it; input contract and snapshot rebuild and compare it. The engine validates every row, active employee/date, safe nonnegative cents, duplicate coverage and equality against all attributed sale turnover. An invalid supplied source blocks; only manual legacy scenarios that omit the field use their previous fallback. Explicit daily amounts drive personalRevenueCents and the absolute ceiling. Fixed/milestone amounts exceeding it remain visible as conflicts, never silently reduced.

Capability `explicitNoRefundEmployeeNetRevenue:true` describes this narrow implemented engine input. `fullEmployeeNetRevenue:false` and `signedRefundAdjustments:false` still preserve the broader official gate. Candidate snapshot includes `personalRevenueCeilingSource`; no writer enabled.

## 2026-10-20 — Closed-period no-refund input capability

`purpose: official_no_refund_input` returns `verified_no_refund_input` only after all original mode/configuration/component checks pass, complete related-order refund absence is proven, and `explicitNoRefundEmployeeNetRevenue` is supported. Independent `calculatorInput.personalRevenueSource` is mandatory: rebuilding it must reconcile all employee merchandise net to the covered closed orders with zero unexplained or minimum-price residuals. Neither incomplete readiness nor missing source policies are promoted to available.

The caller supplies `periodClosure` separately from `sourceBundle`. The owner-authenticated server creates it in the same repeatable-read, read-only source transaction using PostgreSQL transaction time, venue timezone and venue-local date. Validation binds venue, requested range and timezone and recomputes the local date; it must be strictly after the requested period end. This is an internal server contract, not a client request field. Modes requiring closedMonthCoverage still require that distinct fact.

`inputWatermark` remains the stable fingerprint of calculation sources. `closureWatermark` separately hashes closure evidence and that input fingerprint. This preserves repeated-preview determinism while retaining the evidence of when closure was checked. A future persisted run must retain both source provenance and closure proof; the current writer does not yet do so.

The public sourced-preview DTO adds `noRefundInput` containing schemaVersion, status, capabilityVersion, requiredFacts, reasons, inputWatermark and closureWatermark. It never exposes the new internal calculatorInput and always reports officialReady:false, payoutEligible:false and persistence:none. The normal official purpose remains blocked; candidate preview behavior is unchanged. Margin/team dependencies remain blocked for the new purpose.

This capability verifies input only. It does not authorize persistence, entry materialization or payment. Those require integrated producer fencing, authoritative server recomputation, typed snapshot assembly, atomic run persistence, run-to-entry linkage and revalidation before entry/approval/payment.
