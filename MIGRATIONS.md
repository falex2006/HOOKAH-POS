# Миграция PostgreSQL

1. Создать базу и пользователя из `.env`.
2. Применить `schema.sql` одним запуском.
3. Применить `seed.sql` только для тестовой площадки.
4. Проверить индексы и healthcheck CRM.
5. Для production использовать отдельные миграции и резервную копию перед изменением схемы.
6. Для существующей базы применить `migrations/001_auth_sessions.sql` перед включением persistent sessions.

Finance-блок свежего `schema.sql` включает базовые зависимости из миграций `021`, `022`, `038`, `039`, `042`, `044`, а затем финансовые миграции `103–114`: payroll и закупочные документы, расходы с категорией/способом оплаты, а также привязку POS-платежей к смене. Составной индекс `users(venue_id,id)` нужен tenant-scoped внешним ключам. `scripts/migrations-contract.mjs` проверяет точное однократное включение и порядок этих блоков; миграционные файлы остаются источником изменений для существующих баз.

Пример для контейнера:

```bash
docker compose up -d db
# init scripts из /docker-entrypoint-initdb.d выполняются автоматически на новом томе
```

Для существующего тома:

```bash
docker compose exec -T db psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" < migrations/001_auth_sessions.sql
```

Либо использовать подготовленный `./migrate-vps.sh`: он дождётся готовности PostgreSQL и применит все SQL-файлы из `migrations/`.

Проверку остановки и повтора оболочки runner можно выполнить командой `bash scripts/migrate-vps-runner-qa.sh`. Она использует временные SQL-файлы и подмену Docker/psql, не подключается к базе и не доказывает откат транзакции PostgreSQL.

Миграция `006_guest_venue_phone_unique.sql` переводит уникальность телефона гостя на составной ключ точки и телефона для сетевого режима.

Миграция `011_user_preferences.sql` добавляет JSON-поле персональных настроек аккаунта: таймер блокировки рабочего места и настройки отображения главной/аналитики. Она безопасна для повторного запуска через `ADD COLUMN IF NOT EXISTS`.

## 099 — отдельное исполнение строк заказа (FIX-03.1)

`migrations/099_order_item_execution.sql` аддитивно добавляет nullable `products.preparation_station` и таблицу `order_item_execution`: одна запись на order_item_id, station bar/hookah/null, status new/queued/in_progress/ready и nullable временные отметки. Tenant/заказ определяются через order_items→orders. Legacy station/status, цены и immutable финансовые guards не меняются.

Повторный запуск безопасен: DDL IF NOT EXISTS и backfill ON CONFLICT DO NOTHING. Переносится только активная история: точные legacy station bar/hookah распознаются, прочие становятся null; order ready→execution ready, in_progress→queued, open→new. Историческое время передачи не выдумывается. Закрытая старая история не заполняется; новые оплаченные работы сохраняются до исполнения.

Порядок выпуска: backup и проверка миграции в изолированной БД, затем099, совместимый API и UI. Старый код может не читать новые поля, но откат приложения требует отдельно учитывать уже созданные работы и ограничить несовместимые изменения. Разрушительный rollback с DROP таблицы/колонки не предусмотрен: он удалил бы факты исполнения. При проблеме сохранять данные, останавливать затронутый функционал и выпускать совместимую исправляющую миграцию. Само наличие документа не означает production-развёртывание.

## 100 — расписание минимального чека столов

`migrations/100_table_minimum_schedule.sql` добавляет nullable время начала и окончания локального интервала к столу. Пара `NULL/NULL` сохраняет прежнее поведение: заданный минимум действует всегда. Интервал рассчитывается в часовом поясе заведения; окно 18:00–09:00 включает время с 18:00 до 08:59 и выключается ровно в 09:00. Заказ сохраняет применённый минимум как снимок, поэтому последующие изменения настройки не переписывают открытые заказы.

## 101 — связь техкарты премикса со складским результатом

`migrations/101_premix_recipe_output_binding.sql` добавляет к карте премикса обязательную для новых выпусков позицию результата. Старые партии автоматически связываются только если у карты все партии имеют одну и ту же позицию и она не закреплена за другой картой. Неоднозначные карты остаются без привязки; владелец склада выбирает позицию для будущих выпусков в редакторе. Старые партии и их складские остатки сохраняются со своими прежними позициями. Уже закреплённую позицию нельзя переназначить после выпуска партий. Составные внешние ключи и триггеры закрывают подмену арендатора и несоответствие новых партий техкарте.

## 103 — ручные финансовые обязательства

`migrations/103_finance_payables.sql` добавляет разовые обязательства, месячные правила с неизменяемыми версиями условий, строки обязательств и append-only связи фактических оплат с существующими `expenses`. Генерация повторяема и создаёт только черновики. Подтверждённые суммы/строки не редактируются; частичная оплата ограничена остатком и не создаёт второй денежный реестр. POS, закупки и payroll сохраняют собственные источники истины. Миграция аддитивная; production не запускать в составе локальной задачи.

## 104 — классификация признанной POS-выручки

`migrations/104_finance_pos_income_categories.sql` добавляет неизменяемые помесячные соответствия между замороженной категорией меню и финансовой статьёй дохода, а также snapshot/allocations на закрытом чеке. Итог сверяется с canonical `pos_order_pricing_snapshots`; надбавка минимального чека хранится отдельной строкой. Старые чеки не классифицируются автоматически. Суммы возвратов показываются отдельно и не вычитаются из выручки до утверждения политики признания возвратов.


## 105 — явные категории профильных финансовых источников

`migrations/105_finance_source_category_links.sql` добавляет nullable `finance_category_id` и `finance_category_name_snapshot` в `payroll_entries` и `inventory_purchase_documents`. Составные venue FK с RESTRICT сохраняют историю. DB guards проверяют активную расходную статью при назначении и утверждении/проведении, фиксируют историческое название, разрешают последующую оплату/отмену после архива и блокируют смену направления используемой статьи. Старые строки сохраняют NULL; backfill отсутствует. API/UI изменения должны выпускаться вместе с миграцией. Существующие guards закупочного сторно не заменяются. Локальный SQL-contract не подтверждает применение/исполнение в PostgreSQL; production-миграция не выполнялась.

## 106 — прочие бизнес-доходы вне POS

`migrations/106_finance_other_income.sql` adds tenant-scoped recognition documents and append-only partial receipt facts. Documents require an explicit income category, historical name snapshot, recognition date, basis and idempotency key; only drafts can be edited/cancelled, posting freezes the document. Receipt rows have a separate date/method/actor/key, lock their document, reject receipts for non-posted documents and prevent total receipts from exceeding the posted amount. No existing POS, expenses, payroll or purchase source is rewritten. Owner contributions, loans, transfers, deposits/advances and refunds remain outside this business-income slice. Local migration contracts do not prove PostgreSQL execution or production installation.

## 107 — корректировки признания и возвраты прочих доходов

`migrations/107_finance_other_income_reversals.sql` adds immutable reductions to recognized non-POS income and immutable refunds linked to a specific received receipt. Both preserve the original event and use event date, required reason, actor and venue-unique idempotency key. Parent-document row locks serialize the cumulative caps; refunded amounts cannot exceed a specific receipt, and recognition corrections cannot exceed gross recognition. Refund events do not mutate income recognition or create general expense rows. Database execution and browser lifecycle remain subject to guarded disposable QA.

## Finance payable recognition migration

Следующая схема `108_finance_payable_recognition.sql` добавляет неизменяемые recognition/reversal события для уже существующих обязательств. Migration additive; автоматического исторического признания и изменения документов нет. До миграции читатели должны оставаться совместимыми со схемой без этих таблиц; после неё обновлённый P&L исключает только linked payable cash expenses и добавляет доступные recognition events, а coverage явно показывает approved обязательства без признания. `expenses` и payment links не переписываются.

## 109 — исправляемые версии POS category mappings

`migrations/109_finance_income_mapping_corrections.sql` сохраняет существующие mapping-строки append-only, снимает уникальность одного соответствия на источник/месяц и добавляет tenant-scoped ссылку `supersedes_mapping_id`. Исправление пишет новую запись; селектор применяет последнюю созданную версию для данного effective month. Уже закрытые POS snapshots/allocations не пересчитываются.

## 110 — порядок и конкуренция POS mapping corrections

`migrations/110_finance_income_mapping_revision.sql` нумерует версии каждого источника/месяца в историческом порядке и запрещает повтор revision tenant-scoped уникальным индексом. Новая revision назначается после advisory lock; клиент также передаёт `expectedMappingId`, поэтому устаревший повтор после чужого исправления завершится конфликтом, а не вернёт старое решение. POS allocations остаются snapshot facts и не переписываются.

Миграция не содержит собственных `BEGIN`/`COMMIT`: границы транзакции задаёт migration runner, который применяет весь набор атомарно.

## 111 — подтверждение переменной суммы обязательства

`migrations/111_finance_variable_payable_confirmation.sql` сохраняет автора и время подтверждения суммы для черновиков, созданных из правила с переменной оплатой. Проведение такого обязательства невозможно без явного подтверждения; фиксированная сумма не требует дополнительного шага. Связь с пользователем и пара полей подтверждения проверяются на уровне PostgreSQL.

## 112 — счета оплаты обязательств и POS-смена

`migrations/112_finance_accounts_and_payable_payment_sources.sql` добавляет venue-scoped каталог касс/счетов, POS-кассу по умолчанию, account ID и snapshot в `expenses`, а также необязательную ссылку на смену. Legacy расходы остаются с неизвестным источником. POS cash требует активную POS-кассу и смену; внешние cash и bank/electronic источники не изменяют кассовую смену. Каталог не создаёт параллельный денежный ledger: оплата по-прежнему ровно одна строка `expenses`, а payable link — только связь. Миграция аддитивна; применение и PostgreSQL runtime требуют guarded disposable QA.

## 113 — источники счетов для прочих доходов

`migrations/113_finance_other_income_account_sources.sql` добавляет к фактам поступления и возврата прочего дохода явный счёт, снимок его названия и, для наличных, связь со сменой. Ограничения проверяют принадлежность заведению, совместимость способа оплаты и счёта, а также обязательную смену для POS-кассы. Старые факты остаются без счёта: источник не восстанавливается по способу оплаты.

## 114 — счета POS-тендеров и выплат возвратов

`migrations/114_pos_tender_finance_accounts.sql` добавляет account ID и неизменяемый snapshot названия к новым денежным POS-платежам и каждой выплате по возврату. Триггеры проверяют заведение, активность, совместимость метода и счета; POS cash привязывается к смене, card/QR не увеличивают кассу. Бонусы, депозит гостя и зачёт предоплаты остаются без счёта. Исторические события остаются неатрибутированными; ни миграция, ни отчёт не угадывают их источник. Перед применением требуется guarded PostgreSQL QA.

## 115 — целостность распределения POS-дохода

`migrations/115_finance_pos_income_snapshot_integrity.sql` закрывает снимок дохода только через промежуточное состояние `building`; незавершённый снимок нельзя зафиксировать. Отложенная проверка на commit сверяет дату и момент закрытия с источником, использует сохранённый часовой пояс заведения и требует точного соответствия каждой строке pricing snapshot по позиции, сумме и замороженным данным категории/цеха/названия. Она проверяет отдельную доплату минимального чека и mapping на активную доходную статью при создании; направление статьи после использования защищено. Архив доходной статьи не переписывает исторические снимки, а версии mapping не пересчитывают старые распределения. Проверка PostgreSQL должна подтвердить успешный и отклонённые транзакционные сценарии до выпуска.

## 116 — черновики ручных расходов

`migrations/116_finance_expense_drafts.sql` добавляет venue-scoped черновики ручных расходов с версиями, которые не входят в кассу и P&L до проведения в одну связанную строку `expenses`. Проверки БД защищают жизненный цикл черновика, соответствие проведённого расхода, неизменяемость ручного денежного факта и направление использованной категории. Существующие строки не меняются; контрагент остаётся NULL, если он явно не задан.

## 119 — повторы создания обязательств и правил

`migrations/119_finance_create_idempotency.sql` добавляет общий venue-scoped журнал ключа, fingerprint запроса и первоначального ответа для ручных обязательств и новых правил регулярных платежей. Резервирование ключа и создание строк выполняются одной транзакцией; точный повтор возвращает исходный результат, а повтор ключа с изменёнными данными отклоняется. Автоматическое создание месячных периодов продолжает использовать собственную уникальность по правилу и месяцу.

## 120 — append-only коррекции ручных расходов

`migrations/120_finance_expense_corrections.sql` хранит последовательные снимки до/после, причину, автора, время, signed amount delta и сохранённый ответ для точного идемпотентного повтора. DB guard блокирует изменение/удаление события, проверяет версию под блокировкой исходного расхода и запрещает коррекцию расходов другого source-ledger, закупки, зарплаты или оплаты обязательства. Исходная выплата `expenses` не переписывается.

## 121 — устранение неоднозначности в проверке переменного обязательства

`migrations/121_finance_payable_variable_confirmation_ambiguity.sql` переименовывает локальный признак переменной суммы в функции подтверждения обязательства, чтобы PostgreSQL однозначно разрешал столбец и не отклонял проведение из-за неоднозначной ссылки.

## 122 — tenant-ссылки категорий в истории исправлений

`migrations/122_finance_expense_correction_category_refs.sql` добавляет generated category IDs из неизменяемых снимков «до/после», tenant-scoped FK и guard типа «расход». Миграция сначала блокирует конкурентные записи и смену направления категории, проверяет старые снимки и завершает работу с ошибкой при неизвестной либо доходной категории. Операции не переписываются; уже использованную статью можно переименовать или архивировать, но нельзя менять её тип.

## 123–124 — предпросмотр ставки и восстановительная генерация регулярных обязательств

`migrations/123_finance_recurring_version_preview_idempotency.sql` связывает подтверждение новой ставки с просмотренным снимком и сохраняет безопасный точный повтор. `migrations/124_finance_recurring_generation_idempotency.sql` добавляет тот же tenant-scoped журнал для подтверждённой генерации пропущенных периодов; сущность ключа обязана быть обязательством того же заведения. Генерация создаёт только черновики, а не платежи или признания. Изменения применяются migration runner; production не затрагивался.

## 125 — журнал возвратов ручных расходов

`migrations/125_finance_manual_expense_refunds.sql` добавляет append-only события фактического возврата денег по точному ручному расходу, сохраняя исходную выплату и отдельно фиксируя cash event.

## 126 — снимки единого финансового отчёта

`migrations/126_finance_unified_report_snapshots.sql` хранит полную неизменяемую venue-scoped JSON-проекцию отчёта на 15 минут, с creator-scoped идемпотентностью и подписанными курсорами. Истёкшие строки разрешено очищать; до истечения изменение и удаление запрещены.

## 127 — документы вкладов владельца и principal займов

migrations/127_finance_funding_events.sql добавляет tenant-scoped документы funding и append-only денежные события. Триггеры сериализуют principal limit/repayment под блокировкой документа, сверяют активный счёт и POS-смену, блокируют переписывание и очистку event-таблицы. Backfill нет.

## 129 — явный расчёт неполного месяца аренды

`129_finance_recurring_partial_month.sql` добавляет policy правила с default `full_months_only` и nullable immutable `proration_snapshot` обязательства. Существующие правила/документы не переоцениваются. Migration replay сохраняет значения; схема свежей установки содержит тот же блок. Сначала применяется миграция, затем приложение. Старое приложение не понимает `calendar_days`: перед его откатом следует остановить генерацию таких правил и сохранить записи. DROP колонок не является безопасным rollback. Проверки выполняются только на disposable PostgreSQL.


## 130 — возврат оплаты обязательства

`migrations/130_finance_payable_payment_refunds.sql` расширяет существующий `finance_expense_refunds`: связь `payable_id` выводится из точной неизменяемой связи платежа, эффект признания обозначен `separate_payable_recognition`. Исходный платёж сохраняется; возврат увеличивает долг и разрешённую сумму повторной оплаты. Отмена требует нулевой оплаты за вычетом возвратов и полного сторно признания. Миграция не создаёт второй денежный реестр и не меняет старые ручные возвраты. Повторное применение проверено guarded PostgreSQL QA.


## 131 — неденежное распределение договорной оплаты

`migrations/131_finance_payable_offsets.sql` добавляет append-only распределения существующего expense между обязательствами, функции доступной доли оплаты и итогового погашения, проверки цепочек/сторно и единый порядок блокировок. Денежный возврат ограничен долей на первоначальном обязательстве; оплата и отмена учитывают распределения. В fresh schema включён точный блок миграции. Guarded PostgreSQL replay и конкурентные сценарии прошли. API/UI зачётов и подключение всех отчётов пока не завершены; это не готовый пользовательский релиз.
