# Дерево сайта HOOKAH POS

`/admin#staff-schedule` имеет два представления по серверным правам. При `staff_schedule_view` доступен «Команда → График сотрудников»: самостоятельный экран недели/месяца/дня/списка; owner выдаёт admin/manager просмотр либо изменение отдельно для заведения. При `staff_schedule_self` без view пункт «Мой график» в операционном меню открывает личный календарь месяца/недели/дня: собственные опубликованные записи и рабочие смены коллег выбранного дня, без чужих отсутствий и частных заметок. Без обоих полномочий пункт и прямая ссылка недоступны; API повторно проверяет права. Self-only загрузчик не зависит от planning UI и не запрашивает административный справочник сотрудников. Подробные действия и DTO: [API.md](API.md).

Личная отметка «Выход на работу» доступна активному сотруднику кнопкой в рабочем меню `/`; она открывает доступную диалоговую панель и не переводит в `/admin`. Управление находится в «Команда → Выходы сотрудников», `/admin#staff-attendance`, отдельно от графика: маршрут доступен при любом из `staff_attendance_policy_manage`, `staff_attendance_approval` или `staff_attendance_close`. По умолчанию открывается обзор текущих отметок и запросов; «Правила и доступ» видно только пользователям с соответствующими полномочиями. Настройка политики, согласование и завершение чужой отметки — независимые права; выдаёт их владелец, а право закрытия требует причины и подтверждения. Уведомления ведут в личную панель `/#staff-attendance` или управленческий раздел `/admin#staff-attendance` по назначению; личные уведомления не показывают финансовые категории. Личная отметка не открывает кассовую смену, не создаёт автоматически `staff_work_logs` и не рассчитывает зарплату. Сервер повторно проверяет сессию и права для всех операций.

Управленческий календарь сохраняет ночные продолжения без дублирования плановых часов. Справка из15 поисковых тем доступна owner/admin/manager с view, отсутствует в personal UI; она объясняет прямые правки, черновики, публикацию, шаблоны, серии и ограничения. Поиск нормализует ё/е, предпочитает совпадения заголовков; очистка восстанавливает порядок и раскрытие тем. План отделён от фактического времени и кассовой смены.

Переход на график и выход повторно загружают портал с проверкой сессии, без запросов общего dashboard. Прямой вход читает серверную настройку темы с защитой от позднего ответа после смены route/session. Переключатель «Настройки → Интерфейс → Светлая схема» сохраняется; light-поправки календаря и shell ограничены `body.portal.light-theme.schedule-route`, не расширяют область management-theme и права.

Боковое меню CRM не имеет горизонтальной прокрутки или видимой вертикальной полосы. Длинные группы сохраняют вертикальную прокрутку колёсиком и доступ клавиатурой; бренд, «Главная» и выход остаются отдельными элементами каркаса. Прокрутка основного рабочего контента независима.

Административное меню обычно раскрывает максимум одну группу; повторное нажатие закрывает её. Переход на другой URL, включая hash, inventory view query и «Назад/Вперёд», раскрывает доступную группу этого маршрута; возврат из BFCache также синхронизирует текущий маршрут. Обновление того же URL сохраняет ручной выбор, включая полностью свёрнутое меню. На главной `/admin` без подраздела при обычном входе группы свёрнуты.

Состояние меню хранится одним объектом `{version:2, route, openGroup}` в `crm_sidebar_state_v2:<encoded user.id>:<encoded venueId>`; `openGroup` — одна из operations/menu/inventory/finance/team/system либо `null`. Оба идентификатора берутся из подтверждённой сервером сессии, не из роли, имени или query. При неизвестной identity или недоступном storage меню работает в памяти. Старые отдельные `crm_sidebar_group_*` флаги игнорируются без переноса и массового удаления. Невалидный объект либо недоступная группа дают безопасное раскрытие группы текущего маршрута или полностью свёрнутое меню. Другие предпочтения, сессии и черновики эта миграция не очищает.

Поиск меню — явное временное исключение: непустой запрос может раскрыть несколько совпавших групп. Совпадение по названию группы показывает её доступные дочерние ссылки; совпадение по ссылке показывает доступные совпавшие пункты. Поиск пересекается с серверными правами, существующими ограничениями роли и настройками видимости меню; скрытые ими ссылки не появляются. Поисковые раскрытия и запрос не сохраняются. Очистка возвращает обычный ручной выбор, включая `null`; временное закрытие группы при поиске этот выбор не заменяет. Переход на другой URL очищает поиск и показывает группу назначения. Поздняя загрузка настроек сохраняет это пересечение; если обычная выбранная группа стала недоступна, применяется доступная группа текущего маршрута либо `null`.

Канонические ссылки и браузерная история сохраняются. `/inventory` определяет активный пункт по `view`, сохраняя посторонние query/hash; admin hash и `/finance#payroll` сохраняют свои прежние назначения. Существующий перенос query для inventory и контекста в плоском меню сотрудника остаётся; обязательного добавления venue/workspace query во все управленческие ссылки нет. Tenant задаётся подтверждённой сессией, а не URL. Выбор точки использует существующий серверный сценарий и после проверки новой сессии получает отдельное состояние меню. Операционные роли сохраняют плоское меню без управленческого аккордеона.

Карточка сотрудника: «Команда → Персонал → Карточка», `/admin#staff`. «Контакты» содержит необязательную почту, Telegram и телефоны; «Доступ в систему» — логин и PIN блокировки. Смена логина требует `staff_manage` и подтверждения завершения сеансов; защищённые учётные записи меняет владелец. Контактная почта не заменяет логин и не запускает восстановление пароля.

Условия входа в страницу, чтения данных и выполнения действия различаются. Для реальной сессии источник прав — `GET /api/session`; демонстрационные списки ролей не являются серверным RBAC. Особые случаи `staff`, вспомогательных сотрудников, уведомлений и зарплаты перечислены в текущей матрице.

Контекст административной шапки: название текущего заведения из карточки (`GET /api/venue → name`) / текущий раздел. Ошибка чтения отображается явно; название не подменяет продуктовый логотип.

Публичный адрес каждой страницы один. HTML-файлы лежат в корне приложения как внутренние шаблоны, но пользователю доступны только канонические маршруты.

Шапка рабочего зала отделяет название от действий: смена → настройки автоблокировки → блокировка → профиль. Кнопка смены показывает состояние и явное действие «Открыть»/«Закрыть»; ошибка чтения предлагает повтор проверки. До 650px действия занимают отдельную строку. Управленческий колокольчик доступен по серверным правам, а не по наличию событий; API не разрешает его операционным сотрудникам.

Продуктовый логотип во всех боковых панелях ограничен внутренней шириной блока бренда и размером 190×61px, изображение целиком вписывается с сохранением пропорций. До 900px используется компактный символ 42×40px, также в раскрытом меню. Размер исходного файла не увеличивает боковую панель и не перекрывает рабочую область.

Полный логотип в staff/admin/platform sidebar и на `/login` использует анимированный вариант из пользовательского brand kit. При системном уменьшении движения выбирается статичный вариант. Каноническое семейство активов `/assets/brand/`; favicon, install metadata и Open Graph подключены во всех опубликованных шаблонах. Product logo на входе не заменяется tenant logo.

Просмотр `/clients` и ссылка «Гости» разрешены при `orders` или `staff_view`, как в API. Это не добавляет операционному сотруднику кадровые права. Его карточка гостя не содержит полей бонусов/депозита; заполнение формы учитывает отсутствие этих элементов. Настройки видимости меню сохраняют проверку прав.

`/admin` не является заменой `/`: это отдельный административный режим. Возврат из него выполняется на `/` с сохранением выбранного рабочего режима только через query-параметр `mode`. Прямые адреса `/index.html`, `/admin.html` и остальные HTML-имена возвращают постоянный редирект 308 на канонический маршрут.

Операционные роли с правом `orders` используют `/admin#tasks` для личных поручений: переход «Задачи» из рабочего зала ведёт в этот раздел, а не фильтрует очередь заказов. Управление персоналом и настройками от этого не добавляется. `/finance/report` для сотрудника показывает собственные оплаты за текущий день точки и число закрытых им сегодня чеков; редактирование даты и общий отчёт заведения ему недоступны.

Историческое требование минимальных селекторов: `GET /api/payroll/employees` при `finance` должен отдавать только `id/name/active`, `GET /api/reservations/guests` при `reservations` — `id/name/nickname/phoneNumbers`; чтение схемы предполагалось при `floor/reservations/settings`. **Реализация этого требования не подтверждена:** в локальном снимке UI-01.1 и свежем `origin/main` `2e6f557934fe29a9a227dda73277f6c3f99af939` перечисленных selector endpoints нет. Фактическая форма брони читает `/api/clients` и `/api/floor`; зарплата использует `/api/staff`. Наличие одного `reservations` или `finance` поэтому не доказывает доступ к зависимым селекторам. Это существующее расхождение документации и реализации требует отдельного API/RBAC пакета; UI-01.1 права не расширяет. Подробности и владельцы — в матрице.

В `admin#venue-layout-settings` зал/этаж создаётся первым; сохранение сразу предлагает добавить в него стол, а столы и VIP-комнаты привязываются к выбранному залу. Название и диапазон гостей после сохранения используются на рабочей панели, в бронированиях и при открытии заказа. В форме бронирования столы сгруппированы по залам; рядом указаны вместимость и депозит, чтобы различать одинаково названные столы. Число гостей ограничено вместимостью, а журнал и поиск сохраняют контекст зала. Дата и время бронирования единообразно работают в часовом поясе точки.

Вложенные маршруты со завершающим слешем (`/orders/`, `/inventory/` и т. п.) также получают 308 на slashless-вариант через Nginx; корневой адрес `/` сохраняется без изменений.

API находится только под `/api/*` и не смешивается со страницами. Статические ресурсы (`app.js`, `portal.js`, `header-shell.js`, `lock.js`, `style.css`, изображения и шрифты) не являются страницами и не добавляются в навигационное дерево. Все административные маршруты используют общий `header-shell.js`; рабочая панель сотрудника сохраняет отдельную операционную шапку.

В боковом меню каждый раскрываемый раздел имеет свой значок в заголовке, а вложенные маршруты показываются текстом, выровненным под названием раздела. Правила восстановления группы и временного поиска приведены в начале документа; точная область локальной приёмки и её ограничения записаны в результате UI-03.2. Если активный маршрут спрятан в свёрнутой группе, заголовок группы сохраняет его активный индикатор. При обычной высоте окна прокручивается только область групп; бренд, главная, профиль и выход остаются на месте. На очень низком окне включается дополнительная прокрутка всей боковой панели, чтобы закреплённые элементы оставались достижимы; рабочая область прокручивается независимо. Активная ссылка автоматически показывается, только когда её группа уже раскрыта. Это визуальное правило не меняет канонические адреса и права маршрутов.

У `/inventory` есть сохраняемые представления одной страницы: `?view=products` — каталог товаров, `?view=recipes` — технологические карты, `?view=stock` — остатки, `?view=auto-orders` — пополнение запасов, `?view=movements` — поставки и списания, `?view=premixes` — выпуск заготовок и премиксов, `?view=directories` — цеха и категории. Без параметра `view` открываются остатки. Эти значения синхронизированы с раскрываемыми группами «Меню» и «Склад»: производство премикса учитывает складские остатки и поэтому находится в группе «Склад».

Для статической публикации `dist/` использует ту же схему: у каждого канонического раздела есть собственный каталог с `index.html` (`dist/admin/index.html`, `dist/finance/index.html`, `dist/finance/categories/index.html` и т. д.). Эти файлы синхронизируются с корневыми шаблонами перед публикацией, поэтому Sites не получает старую копию страницы.

`notification-center.js` — общий модуль уведомлений административной и рабочей шапки, подключён перед `portal.js`/`app.js`. События смены ведут в `/admin#shift-control`, при доступе только к финансам — в `/finance`. Новый публичный раздел не добавляется; колокольчик определяется текущей ролью и правами.

Справочники `/inventory?view=directories`: цех → подцех (все / без подцеха / выбранный) → категории. Это внутренний каскад одного маршрута, без новых пунктов бокового меню. Создание и изменение открываются в модальном редакторе; информационные каталоги доступны вторично.

`/inventory?view=movements` показывает документы и операции в двух внутренних представлениях; создание приёмки/движения и изменение черновика открываются модально. Канонический маршрут и боковая навигация сохраняются.

Остатки, пополнение и заготовки сохраняют свои view. Компактные таблицы/истории прокручиваются локально; пополнение отделяет рекомендации от истории внутри существующего маршрута; заготовки показывают форму при выполненных предпосылках.

Финансовый маршрут /finance#payroll показывает отдельную рабочую область зарплаты, сохраняя существующий URL. Активный пункт меню соответствует hash; другие финансовые якоря раскрывают сводку. Финансовые страницы проверяют permissions через /api/session до рендера; запрет доступа не маскируется ошибкой загрузки.

## FIX-03.1 — приготовление внутри рабочего места

На `/` добавлена отдельная секция «Приготовление» рядом с существующей очередью заказов: построчные работы бара/кальянного мастера, состояние «Ожидает»/«В работе», действия «Взять в работу»/«Готово», обновление и ошибка с повтором. Это внутренний блок POS, не новый маршрут и не пункт бокового меню. Общая очередь заказов и административные «Задачи» остаются отдельными представлениями.

Кнопки передачи открывают выбор конкретных строк: совпадающее направление выбрано заранее, неизвестное требует явного выбора. В редакторе товара меню задаётся отдельное «Направление приготовления» (Бар/Кальяны/выбрать при отправке), независимо от категории. Контракт: `docs/architecture/FIX_03_1_DISPATCH_CONTRACT.md`.

## Единый каркас сотрудника

Для операционных базовых ролей bartender, hookah_master, senior_bartender, senior_hookah_master, cleaner, security, technician, other_staff и staff портальные страницы используют плоское рабочее меню. Переходы в бронирования, гостей, задачи и доступные финансовые/складские разделы не переключают меню на раскрываемые управленческие группы. Пункты определяются подтверждёнными сервером разрешениями; имя пользовательской роли и дополнительные права не меняют тип каркаса. Для owner/admin/manager/developer сохраняется управленческое меню.

«Заказы» рабочего места доступны через /?view=orders с восстановлением вида после reload; при orders без floor портальный переход остаётся /orders. Личные задачи ведут в /admin#tasks и доступны при orders либо tasks_manage. Существующие проверки маршрутов/API остаются обязательными.

В портальной шапке сотрудника сохраняются профиль, настройки PIN-блокировки, блокировка и индикатор смены; управление открытием/закрытием смены выполняется в рабочем зале. Рабочая область конкретного раздела сохраняет собственное содержание.

`/admin#company` — отдельный сфокусированный экран «Настройки заведения»: заголовок страницы и верхней панели совпадает, показываются карточка компании и её заголовок без KPI, аналитики смены, персонала и интерфейсных/планировочных настроек. Настройка сторно показывается здесь; на страницах интерфейса и планировки она скрыта. Заголовок карточки компании скрывается, когда экран принадлежит вложенным интерфейсным или планировочным настройкам. Поздняя загрузка персональных настроек главной не должна раскрывать dashboard-блоки поверх карточки. Все hash-подразделы административной панели используют единый фокус-маршрут, который управляет видимостью модулей даже при асинхронной загрузке предпочтений. Состояние компании помечается классом `company-page-active` на контейнере и `body` для локальной рамки; оно снимается при переходе на другой hash.

## Короткое имя в рабочей шапке
Видимая подпись операционного сотрудника в POS и портальных разделах использует общий staff-display-name.js. Полное имя остаётся в title, аватаре и данных сессии; управленческие роли сохраняют полное имя. Неоднозначные свободные имена не разбираются принудительно, дополнительные кадровые запросы не выполняются. В карточке стола одно меню «Ещё действия» с исходной кнопкой переноса; быстрые действия бронирования и мобильного закрытия карточки сохраняются.

## Дизайн плиток рабочего зала
Внутренние плитки на `/` используют единое задание `docs/design/TABLE_TILES_DESIGN_PROMPT.md`. Это изменение существующего рабочего зала, без новых страниц, маршрутов или пунктов меню.

## Оставшиеся пакеты рабочего места
Доработаны внутренние представления существующих `/`, `/admin#tasks`, `/clients`, `/finance`: время очереди, обновление и статусные действия задач, порядок гостевой информации и пояснение оплат сотрудника. Новых маршрутов и пунктов меню нет.

Рабочий зал (`/`): над сеткой столов расположены зоны и раскрываемое «Вид», внутри которого доступны «Размер столов» и «Вместить»; только локальная настройка представления. На экране зала очередь заказов не дублируется. «Готовые заказы» и «Открытые счета» открывают существующий `/?view=orders` с соответствующим фильтром и заголовком; «В зал» возвращает прежний зал и стол в текущей сессии страницы. При смене фильтра выбранный заказ очищается, чтобы панель не противоречила списку. Новых маршрутов/API нет.

Бронирования (`/reservations`): «Новая бронь» открывает3-шаговый диалог; «Изменить бронь» открывает ту же форму. После сохранения список показывает дату записи. tableId-only — создание; reservationId и action=seat — прежние сценарии существующей брони. API/навигация не меняются.

Персонал отображается только в разделе «Команда → Персонал» (`/admin#staff`); список и форма сотрудников не входят в главную `/admin`. Настройки блоков главной не скрывают каталог персонала или страницу прав `/admin#permissions`.

### 2026-10-18 — уточнение существующих маршрутов
/admin#lock-security: компактный вход в существующие личные настройки PIN и автоблокировки, без повторения общей сетки настроек. /admin#tasks: бейдж отражает открытые задачи и задачи в работе из того же /api/tasks, что используется списком; заявки на скидку в него не входят. /admin#staff: фото изменяется из профиля, нажатие аватара открывает профиль с существующими ограничениями доступа.

Финансы: /finance?action=expense|obligation|recurring&categoryId=... открывает соответствующую существующую форму только с правом finance. Категория проверяется по доступным активным расходам; ссылка не создаёт записей. Параметры действия потребляются однократно. Незавершённые попытки и текущие черновики имеют приоритет. В справочнике активных расходов выбор доступен через «Оформить расход».

Финальные категории: локальные вкладки «Категории», «Распределение POS», «Отчёт выручки POS» в существующем /finance/categories. Выбор сценария расхода открывается dialog, архивирование — меню дополнительных действий. Отчёт доступен после выбора валидного заведения.

Финансовые переходы (локальная QA 2026-10-18): вкладки `/finance/categories?tab=categories|pos-mapping|pos-report` восстанавливаются после reload и Back/Forward. «Операции» ведут в `/finance/report?categoryId=…&from=…&to=…#financial-sources`; архивная статья добавляет `includeArchived=true`. Активная доходная категория с правом `finance` открывает `/finance?action=other-income&categoryId=…#other-income`: только выбор статьи в пустой форме, без создания документа. Заполненная или отправляемая форма не заменяется. Параметры входа потребляются однократно.

Рабочий зал `/`: столы и действия с заказами доступны только после подтверждения открытой смены. При закрытой смене вместо схемы показывается «Откройте смену» с кнопкой существующего сценария открытия; без права управления сменой — пояснение обратиться к уполномоченному сотруднику. Ожидание и ошибка проверки смены не раскрывают схему. После открытия смены зал восстанавливается; подтверждённое закрытие убирает столы и открытые редакторы.
Тихая фоновая проверка сохраняет последнее подтверждённое открытое состояние до ответа, чтобы не прерывать работу каждые 20 секунд. Закрытие на другом устройстве отражается после очередной проверки или возврата фокуса; ошибка проверки блокирует зал.


### Finance section navigation (2026-10-18)
`/finance` shows the overview only. Existing hashes select mounted sections: expenses,
other-income, business-obligations, payables, finance-payments-panel, cash-register-panel,
finance-result-panel, finance-staff-panel, discounts and payroll. Nested links (expense-form,
payment-list) select their parent section. Back/Forward and mobile section picker use the
same hash contract; switching sections preserves unsaved input. Category entry routes and
permissions remain unchanged. Closed POS shift has one primary opening action; its header
shows status while the floor gate is visible.


Finance section internals (2026-10-19): `#finance-account-settings` is a nested
anchor of `#cash-register-panel`; the obligations shortcut selects cash and opens
settings without resetting their form. Expenses/income creation and payroll
scheme settings are native disclosures; existing mutation endpoints and role
checks are unchanged. Editor entry/edit/error paths reveal their mounted forms.

model → period → draft, then the existing approval/payment actions. A sibling
model form calls the existing `POST /api/payroll/rules`, refreshes the model list
and selects the confirmed saved ID. No scheme-version ID is substituted for a
basic model ID. Advanced scheme workspaces (list/configuration/checks/trial)
are local presentation state, keep mounted input and do not add routes.
