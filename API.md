# API-контракт MVP

Базовый URL локально: `http://localhost:3000`.

## График сотрудников — контракт после миграций 101–112

### Личный календарь и минимизация данных

`self:true` возвращается только после проверки активного пользователя, активного заведения и допустимого tenant-контекста. `/api/session` добавляет `staff_schedule_self`; это не grant `view/manage` и не право настройки или публикации. Существующая матрица owner/admin/manager не расширяется.

`GET /api/staff/schedule/personal` возвращает `{selfUserId,timezone,from,to,items,team}`. Период включительно — 1–93 дня; по умолчанию сегодня в часовом поясе заведения. `items` содержит только собственные записи `planned`, включая выходные/отсутствия. `team` содержит только чужие `planned` записи типа `shift` текущего заведения. Ночные смены, пересекающие начало периода, также возвращаются; окончание ровно в начале периода не считается продолжением.

Общие поля записи: `id,userId,userName,workDate,plannedStart,plannedEnd,functionName`. Только собственные записи дополнены `kind,breakMinutes`. Заметки, причины, история, фактические часы, чужие отсутствия, отменённые и свободные смены не возвращаются. Параметры `userId/venueId` не переключают область: она определяется сессией. Personal endpoint принимает только GET (прочие методы405); self-only пользователь не получает административные schedule API или mutations (403). Неактивная учётная запись со старой сессией не получает данные.

`avatarUrl` административного `/employees` — существующий raster data URL либо null, без расширения персональных полей. До проверки base64 применяется предел длины110000 символов; декодированные данные — до80KiB, суммарный бюджет avatar data URL —1MiB. GET не выполняет повторную нормализацию изображения; UI сохраняет инициалы при ошибке картинки.

### Управленческий API

Префикс `/api/staff/schedule`. Только PostgreSQL; без него503 `schedule_postgres_required`. Контекст пользователя/заведения берётся из авторизованной сессии, не из тела. Владелец имеет полный доступ в своих заведениях; admin/manager — только по выданному владельцем grant текущего заведения. `staff_manage` сам по себе доступа не даёт. Изменения cookie-сессией требуют допустимый Origin.

Пустой `from` означает текущую дату заведения, пустой `to` — from; диапазон максимум92 дня разницы. Список содержит отменённые записи и отсутствия. `open_shift` — только предложение через draft preview/apply/publish: `userId=null`, обязательны время и `functionId`; direct create/reassignment запрещён. Она видна как «Свободная смена», не входит в персональные часы и payroll, а последующее назначение сотрудника проходит как update того же ряда с проверкой квалификации, доступности и конфликтов. DTO: id,userId,workDate,plannedStart,plannedEnd,breakMinutes,breakIntervals,kind,status,version,note,cancelReason,userName. Для прежних читателей сохранены user_id,work_date,planned_start,planned_end,venue_id,created_by,created_at; note сохраняет null. Время — ISO с часовым смещением; workDate — дата начала по timezone заведения. Старые неполные времена остаются NULL и требуют уточнения, не считаются выходными.

В меню «Фильтры, действия и экспорт» CSV и печать используют тот же текущий период/фильтры и доступны пользователю с `view`. CSV содержит только отображаемое имя, роль, функцию, тип записи, даты/время, перерыв и статус; контакты, внутренние идентификаторы и заметки не выгружаются. Включены период, timezone заведения и время формирования. Все ячейки CSV кавычатся, формульно-опасный ввод нейтрализуется апострофом. Печать форматирует текущий календарный вид для листа; CSV не является XLSX. Экспорт клиентский и не добавляет отдельный API или фоновые уведомления.

Demand rule: `{functionId,scope:'weekly',weekday,startTime,endTime,endDayOffset,requiredCount,active,requestKey,version}` либо `scope:'date_range'` с `effectiveFrom/effectiveTo`; локальные интервалы толкуются в timezone заведения. Датированный диапазон полностью заменяет недельные правила этой функции для покрытых дат; сервер отклоняет пересечение эффективных недельных/датированных интервалов, включая переход через полночь. Coverage разбивает интервалы по границам спроса, смен и явно размещённых `breakIntervals`; один сотрудник считается не более одного раза в функции, `open_shift` добавляет незакрытую единицу только своей функции. `breakMinutes` без точного интервала помечается как неизвестное покрытие, расположение перерыва не угадывается. Дефицит/избыток — справочные advisories, не hard conflict. Версия правил включена в preview fingerprint; изменение demand инвалидирует старый preview. Если часовой пояс venue изменён после создания правил, требуется переутвердить их в новом часовом поясе.

Availability `rules` содержит `{weekday,kind,startTime,endTime,endDayOffset,effectiveFrom,effectiveTo,note}`, `kind=available|unavailable|preferred`; `exceptions` заменяет повторяющиеся правила для указанного `workDate`. `available` ограничивает смену заданным окном только в дни, где окно настроено; `unavailable` блокирует пересечение; `preferred` формирует мягкое предупреждение. Интервалы через полночь должны иметь `endDayOffset=1` и проверяются по фактическим моментам времени в timezone заведения. Пустые правила означают отсутствие ограничения, а не выходной. Запланированные выходные/отсутствия остаются отдельными строками графика и блокируют пересечения. Черновой preview возвращает `conflicts` и `warnings`; отпечаток preview включает версию правил доступности, поэтому изменение настроек между preview и apply требует повторной проверки. Для прямого сохранения и публикации с предупреждениями нужны строго `confirmWarnings === true` и непустая причина. Причина записывается в историю смены; структурированный список принятых предупреждений в истории пока не хранится.

Создание: userId,workDate,kind (shift по умолчанию),plannedStart/plannedEnd для смены,breakMinutes (0 по умолчанию),note,reason,requestKey UUID. Смена больше0 и максимум24 часа; целые минуты, неоплачиваемый перерыв меньше длительности. Виды отсутствия: day_off/vacation/sick/other_absence, без времени и перерыва. Пересечения запрещены, соседние интервалы допустимы. PATCH редактирования передаёт все поля записи и прочитанную version. Отмена: status=cancelled,version,reason,requestKey; физического удаления и восстановления нет. Прошлые даты и отмена требуют явно введённой причины, максимум500 символов.

requestKey стабилен для одного действия и повторной отправки неизменного JSON. Успешный повтор возвращает сохранённый результат без новой записи; другое содержимое с тем же ключом409. Новый черновик — новый ключ. Создание с version отклоняется400 `schedule_create_version_forbidden`: для изменения нужен PATCH /:id. Устаревшая version409 `schedule_version_conflict`; клиент перечитывает /:id, сохраняет черновик и требует явного согласования перед повтором.

Совместимость записи: прежний POST без ключа возвращает400 `schedule_request_key_required` без изменения данных. Blind upsert по сотруднику/дате намеренно не поддерживается: теперь за день может быть несколько смен. Старый клиент должен перейти на создание с ключом либо выбрать конкретный id и передать version в PATCH; сервер не угадывает цель и не подставляет текущую версию. Обновлены встроенный UI и seed-local-full-qa; внешние клиенты требуют такой же адаптации до выпуска. Старые недостижимые handlers удалены.

Ошибки:401 без аутентификации,403 нет прав/недопустимый Origin,404 запись или сотрудник другого заведения/не найдены,400 валидация,409 overlap/version/request/grant/copy conflict,503 недоступность. SQL-детали не возвращаются. Copy сохраняет локальное время, отвергает неоднозначное/несуществующее время при переводе часов; изменившийся источник требует нового preview. Неполный исходный план не копируется.

actual — отдельные итоги закрытых staff_work_logs (объединённые пересечения), openIntervals/invalidIntervals помечают неполный факт. Итоги относятся к дате начала; плановый перерыв не вычитается из факта. План не создаёт кассовую смену, work log или зарплату; утверждённые payroll snapshots не переписываются.

## Минимум по времени для стола

`POST /api/floor/tables` и `PATCH /api/floor/tables/:id` принимают `minimumOrderTotal` вместе с парой `minimumOrderStartTime` и `minimumOrderEndTime` в формате `HH:mm`. Для выключения расписания передаются оба времени как `null`; если оба не заданы, сохраняется прежний постоянный минимум. Неполная пара, некорректное время и одинаковые начало/конец отклоняются с `400 invalid_table_minimum_schedule`.

`GET /api/floor` возвращает эти поля для каждого стола. При `POST /api/orders` сервер сам применяет или отключает минимум по локальному времени и часовому поясу заведения; значение минимума от клиента не считается авторитетным. Применённая сумма записывается в заказ и остаётся неизменной после редактирования настроек стола.

## Служебные
- `GET /api/health` — состояние сервиса.
- `GET /api/products?expectedVenueId=<id>` — активные позиции меню текущего заведения; необязательный `expectedVenueId` сверяется с заведением текущей сессии и при несовпадении возвращается `409 venue_context_changed`. Ответ помечается `Cache-Control: no-store`; чтение доступно по действующим правам `floor`, `inventory_read` или `inventory`. Рабочее место запрашивает список при открытии меню, возвращении к открытому меню и раз в 60 секунд, пока меню открыто и вкладка видима; исторические строки заказа не переписываются.
- `GET /api/session?role=<role>` — демонстрационный профиль и разрешения роли; для живой cookie-сессии возвращает `trustedDevice`, но не возвращает bearer token до PIN-проверки.
- `GET/PATCH /api/session/preferences` — пользовательские настройки аккаунта (таймер блокировки, модули главной, вид выручки, показатели аналитики и вид каталога персонала); сервер валидирует допустимые значения и сохраняет их в PostgreSQL. `staffDirectory.view`: `cards` / `list` / `table`; `staffDirectory.cardScale`: целое число 1–4.
- `POST /api/session/unlock` — проверка 4-значного PIN для разблокировки рабочего экрана; после успешной проверки возвращает `ok`, текущий `token` и `user`.
- `POST /api/session/pin-return` — PIN-возврат на доверенном устройстве для `owner`/`admin`/`developer`; требует, чтобы текущая cookie-сессия была создана как доверенная, затем проверяет PIN и возвращает `token`, `user`, `permissions`, `expiresIn` и `trustedDevice`.
- `GET /api/saas/account` — текущая организация, тариф, лимиты мест/заведений и активное использование (для владельца/администратора).
- `PATCH /api/staff/:id/pin` — сотрудник меняет свой 4-значный PIN; владелец/управляющий может выполнить операцию в рамках управления персоналом.
- `GET /api/notifications?limit=20&filter=all|unread` — доступные текущему пользователю уведомления (последние события), число непрочитанных и `hasMore`. Ответ не содержит сумм, строк заказа или PIN. Получатели: owner/admin с правами финансов и заказов для запросов скидки; owner/admin/manager с соответствующими правами склада или заказов; owner/admin с правом сотрудников для события смены PIN. Операционный сотрудник получает 403.
- `PUT /api/notifications/:id/read` — отметить доступное уведомление прочитанным. ID события повторно проверяется в активном заведении и по правам; чужой/недоступный ID возвращает 404.
- `POST /api/notifications` — отметить все доступные события прочитанными. Идентификатор пользователя и активное заведение берутся только из сессии; тело запроса не может менять область действия.

## Лояльность

- `GET /api/loyalty/settings` — действующие общие правила списания бонусов площадки из аутентифицированного контекста. Чтение разрешено пользователям с `orders`, `loyalty` или `staff_view`. Необязательный `expectedVenueId` используется как precondition и при смене площадки возвращает `409 venue_context_changed`. Если версии ещё нет, ответ содержит `version: 0`, `bonusRublesPerPoint: 1`, `maxRedemptionPercent: 100`, `minimumRedemptionPoints: 1`, `bonusExpirationDays: null`, `source: "legacy_default"`.
- `PATCH /api/loyalty/settings` — создать следующую неизменяемую версию; только роль `owner` или `admin`. Тело: `{ expectedVenueId, expectedVersion, bonusRublesPerPoint: 1, maxRedemptionPercent, minimumRedemptionPoints }`. Курс принимается только равным 1; срок и неизвестные поля отклоняются. `expectedVenueId` обязателен (`428 venue_precondition_required`), устаревшая площадка даёт `409 venue_context_changed`, конкурентно изменённая версия — `409 loyalty_settings_version_conflict`, невалидное значение — `400 invalid_loyalty_settings`, чужое поле — `400 unknown_loyalty_setting`. Сохранение версии и audit event атомарны; ошибка БД/аудита не фиксирует версию.
- При создании заказа сервер фиксирует активные версию курса/cap/минимума; legacy-заказы без снимка используют defaults version 0. Денежная база для cap фиксируется при первой бонусной оплате. `GET /api/orders/:id/payments` сообщает `bonusRedemptionRemaining` и `bonusRedemptionPolicy`; лимит повторно проверяется сервером на каждом платеже. Первая операция меньше `minimumRedemptionPoints` или любая операция выше оставшегося cap отвергается (`409 bonus_redemption_below_minimum` / `bonus_redemption_limit_exceeded`); последующая операция может использовать остаток ниже минимума. Изменение версии не меняет уже созданный заказ.
- Истечение бонусов выключено: нет модели отдельных лотов начисления. Изменяемый курс также недоступен до разделения единиц тендера на баллы и рубли.

Состояние прочтения в PostgreSQL хранится отдельно по заведению, пользователю и стабильному ключу события (`notification_reads`, миграция `054_notification_reads.sql`). Demo/fallback без БД использует память процесса и не гарантирует сохранение после перезапуска. Ошибка источника возвращает 503, интерфейс показывает повтор загрузки. Открытие панели не отмечает уведомления прочитанными.

Открытие и закрытие смены также входят в уведомления: получатели — `owner/admin/manager` с правом `floor`, `orders` или `finance_read`. События активного заведения имеют стабильные ключи `shift_opened:<auditId>` / `shift_closed:<auditId>`; суммы кассы не включены в DTO. Колокольчик доступен этим руководителям и в рабочем зале. Прочтение индивидуально для пользователя и заведения. Это уведомления внутри CRM; отправка в Telegram не реализована этой функцией.

## Смены

- `GET /api/shifts` — `current` (активная смена либо `null`) и история `items`; нужны `floor`, `orders` или `finance_read`.
- `POST /api/shifts` — открыть смену с `openingCash`; нужны `floor` или `orders`. Повторное открытие активной смены возвращает 409.
- `POST /api/shifts/:id/close` — закрыть с `closingCash` и `checklist: {version: 1, items: {ordersReviewed, cashCounted, inventoryReviewed, externalFiscalReportsHandled}}`, где каждый пункт должен быть `true`; нужны `floor` или `orders`. Закрытие, cash reconciliation, неизменяемый внутренний снимок смены и audit записываются одной транзакцией. Снимок содержит сверку наличности, ledger и отдельные подтверждения оператора; это не фискальный Z-отчёт и не интеграция с фискальным устройством. Повторное закрытие/чужая смена возвращает 404.
- `GET /api/shifts/:id/close-snapshot` — прочитать сохранённый неизменяемый внутренний снимок. `finance_read` может читать снимки своей точки; без `finance_read` доступен снимок, закрытый самим текущим пользователем.
- Денежные поля обязательны: число либо десятичная строка, от 0 до 100 000 000 включительно, не более двух знаков после точки. `null`, boolean, массивы, объекты и отрицательные значения отклоняются.
- В PostgreSQL изменение смены и событие `audit_events` сохраняются одной транзакцией. Ошибка записи аудита откатывает изменение смены. Конкурентные запросы не создают вторую активную смену/повторное закрытие.
- При настроенной, но недоступной БД возвращается 503 `shift_status_unavailable`; переключения на фиктивную локальную кассу нет.
- UI рабочего зала, главной и финансов перечитывает сохранённое состояние после действия, возврата в видимую вкладку и каждые 20 секунд в видимой вкладке. Показатели выбранного дня/смены обновляются при изменении состояния смены. Финансовая роль без управления видит статус без кнопки открытия/закрытия.
- `POST /api/login` — вход и выдача bearer-токена. Для `owner`/`admin`/`developer` поле `trustDevice: true` выдаёт долгую доверенную сессию, которая затем может быть восстановлена через PIN.
- `GET/PATCH /api/venue` — карточка компании, телефон, адрес и логотип.
- `GET/POST /api/staff`, `DELETE /api/staff/:id`, `POST /api/staff/:id/avatar` — управление сотрудниками и аватарами.
- `GET /api/staff/schedule?from=YYYY-MM-DD&to=YYYY-MM-DD` — плановые смены текущей точки; чтение доступно с `staff_view`, `staff_manage` или отдельным `staff_schedule`.
- `POST /api/staff/schedule` — создать или скорректировать смену `{userId,workDate,plannedStart,plannedEnd,note}`; запись требует `staff_schedule`.
- `DELETE /api/staff/schedule/:id` — удалить плановую смену текущей точки; требует `staff_schedule`.
- `POST /api/staff/:id/archive` — владелец удаляет заранее заблокированного сотрудника из рабочего списка; кадровая и операционная история остаётся в аудите.
- `POST /api/products/:id/image` — загрузка изображения товара (PNG/JPG/WebP до 1.5 МБ).

## Планируемые маршруты
- `POST /api/auth/login` — вход по логину и паролю. PIN не участвует в авторизации и используется только для разблокировки экрана. Ответ содержит `user.organizationId` для tenant-контекста SaaS.
- `GET /api/floor?zone_id=` — зоны и столы со статусами.
- `GET /api/floor?includeArchived=true` — включает архивные столы и поля `archivedAt` и монотонный `archiveVersion`; требует `settings`. Обычный `GET /api/floor` возвращает только активные столы, также с этими полями. Архивирование/восстановление доступны только ролям с `settings` через `POST /api/floor/tables/:id/archive` и `/restore`, с `{expectedVenueId,expectedArchivedAt,expectedArchiveVersion}`. Для архива ожидаются `expectedArchivedAt: null` и текущий `archiveVersion`; для восстановления передаются текущие `archivedAt` и `archiveVersion`. Версия увеличивается при каждом фактическом изменении состояния. Повтор уже достигнутого состояния возвращает 200 без повторного аудита только с текущей или непосредственно предыдущей версией; более старый запрос возвращает 409 `table_archive_state_changed`, в том числе после следующего цикла архивации и восстановления. Архивирование блокируется открытым заказом или подтверждённой бронью на текущую дату заведения; архивированная строка, ID, зал и исторические связи сохраняются. Архивные столы нельзя редактировать, физически удалить, привязать к заказу, брони или перевести заказ на них. Владелец, администратор и управляющий имеют `settings` в стандартной матрице ролей.
- `GET /api/orders?status=open` — открытые заказы. Необязательный `withPricing=1` добавляет активным заказам `pricingTotal`: серверный итог (`/summary.due`) со скидками и минимальным чеком, включая уже оплаченную часть. Значение `null` означает временную недоступность расчёта; отсутствие параметра сохраняет прежний ответ. Расчёт не меняет заказ и ограничен текущим заведением/правом `orders`.
- `POST /api/orders` — открыть заказ на стол или свободный чек; для операционных ролей нужна открытая смена.
- `PATCH /api/orders/:id` — изменить заметки или гостя открытого заказа; для операционных ролей нужна открытая смена.
- `POST /api/orders/:id/items` — добавить позицию.
- `PATCH /api/orders/:id/items/:item_id` — изменить количество или станцию.
- `POST /api/orders/:id/split` — разделить позиции по гостям/новый заказ.
- `POST /api/orders/:id/discount-requests` — заявка только на процентную скидку (`type: "percent"`, `value: 1..100`, `reason`).
- `POST /api/clients/:id/loyalty` — ручная корректировка бонусного баланса с причиной и обязательным `idempotencyKey` (или заголовком `Idempotency-Key`); операция и баланс сохраняются атомарно в `guest_account_entries`, повтор возвращает результат прежней операции, списание сверх остатка отклоняется.
- `GET /api/clients/:id/account-entries` — tenant-scoped журнал бонусного и денежного счёта гостя с текущими остатками, `reversibleRemaining`, `canReverse`, историей метода и смены сторно и общей суммой `bonusClawback`. Сторно начисления с нулевым немедленным движением возвращается как событие `entryKind: "reversal"`, `amount: 0`, `reversedAmount` — без имитации списания из остатка.
- `POST /api/clients/:id/account-entries/:entryId/reversals` — сторнировать допустимую часть неизменяемой записи: `{amount,method:"wallet"|"cash"|"card"|"qr"|"clawback",reason,idempotencyKey}`. Бонусные суммы должны быть целыми. Отрицательное списание возвращается в тот же счёт; возврат пополнения уменьшает денежный остаток гостя. Внешнюю выплату `cash/card/qr` может провести только владелец или администратор с `finance`; для корректировки в счёт гостя достаточно `finance` или `loyalty`. Требуется открытая смена. Остаток ограничен исходной суммой минус успешные сторно; гость, запись и лимит сериализуются транзакцией. Исходная операция не редактируется. Бонусный award сначала отзывается из текущего остатка, а непогашенная сумма удерживается из будущих начислений. Повтор того же ключа и тела возвращает исходное сторно; изменённый payload отвечает `409 idempotency_key_reused`. `cash` уменьшает ожидаемую кассу смены; `card`, `qr`, `wallet` и `clawback` наличную кассу не меняют.
- `POST /api/clients/:id/deposit-top-ups` — принять деньги на счёт гостя: `{amount,method:"cash"|"card"|"qr",reason,idempotencyKey}`. Требуется открытая смена и право orders или finance. Пополнение сохраняет отдельную квитанцию с кассиром и сменой и положительное движение обязательства; оно не создаёт продажу или платёж заказа. Наличные пополнения включены в ожидаемую наличность смены, карта/QR — нет. Повтор с тем же ключом и телом возвращает исходную квитанцию; иной payload под тем же ключом отвечает `409 idempotency_key_reused`.
- `GET /api/loyalty/reconciliation?from=YYYY-MM-DD&to=YYYY-MM-DD` — только `finance_read`/`finance`; считает movements за локальный диапазон (конец включительно) и текущие остатки отдельно. `periodMovements` раскрывает начисления/списания/сторно бонусов, денежные пополнения/списания/возвраты и собранные/зачтённые/возвращённые предоплаты брони. `periodBusiness.sales` агрегирует закрытые продажи и зафиксированные скидки по локальной дате закрытия (источник, группа, акция; считает ценовые снимки, старые чеки без снимка помечаются как `unsnapshottedOrders`, gross берётся из сохранённых строк заказа, net — из оплат); `receipts` показывает реальные поступления по дате события, методу и типу (без бонусных и внутренних reservation tender); `payouts` показывает фактические выплаты по immutable reversal и каналу. Зачёт предоплаты и его отмена не являются новым поступлением или выплатой. Все денежные ряды отдельно от баланса points. Поле `minimumAdjustment` включено в сверку итогов продажи. `balances` сверяет кошельки с журналами, считает незачтённые предоплаты, сверяет `verified_deposit_paid` с квитанциями и отдельно показывает старые неподтверждённые `deposit_paid`; `legacyReservations` возвращает до 250 броней для ручного разбора с суммами старого поля и подтверждённых квитанций, не изменяя их и не превращая legacy в факт оплаты. Операционные сотрудники получают 403. Роли с finance_read без finance видят только агрегаты; строки legacyReservations и имя гостя доступны только owner/admin, иначе возвращается legacyReviewAccessRequired=true.
- `POST /api/reservations/:id/legacy-deposit-reviews` — только owner/admin с правом `finance`; фиксирует документальный статус старого `deposit_paid` отдельным неизменяемым событием: `{expectedReviewId,disposition,note,evidenceReference,idempotencyKey}`. Допустимые статусы `documents_found`, `documents_not_found`, `disputed`; для `documents_found` обязателен номер/ссылка на документ. Ответ содержит сумму source snapshot, sequence, автора и время. Ожидаемый head и idempotency key защищают от гонок/повторов; конфликт версии возвращает 409. Запись и audit event атомарны. Статус означает только результат поиска/проверки документов: он не утверждает, что деньги получены/не получены, не меняет `deposit_paid`/`verified_deposit_paid`, баланс, квитанции, оплату заказа или кассу и сам по себе не снимает блокировку нового приёма предоплаты.
- `PATCH /api/clients/:id` — профиль больше не меняет бонусный или денежный баланс. Изменение ненулевого остатка при создании гостя также отклоняется; баланс меняется через журналируемую операцию.
- `GET /api/discount-requests` — список заявок для финансовых ролей.
- `POST /api/discount-requests/:id/approve` или `/reject` — согласование или отклонение процентной скидки финансовой ролью.

На заказ допускается одна одобренная ручная скидка; повторное одобрение отвечает `409 approved_discount_exists`. При привязке гостя `PATCH /api/orders/:id` фиксирует текущую активную группу точки и её процент на заказе; `clientId: null` снимает привязку, но смена гостя после принятой оплаты отклоняется с `409 guest_change_after_payment`. Для legacy заказов общая скидка ограничивается стоимостью товаров. Групповая и ручная скидки не суммируются: берётся одна большая, при равенстве групповая. Оплата рассчитывается как `max(subtotal - selected_discount, vip_minimum)`, а VIP сводка показывает дефицит уже после скидки. `GET /api/orders/:id/summary` и `GET /api/orders/:id/payments` возвращают текущую цену и основание скидки; закрытый заказ новой версии отдаёт неизменный ценовой снимок.
- `GET /api/pos/payment-accounts` — минимальный список активных счетов текущего заведения для POS-оплаты: ID, название, тип и разрешённые способы; требует `orders`.
- `POST /api/orders/:id/payments` — частичный или полный платёж способами `cash`, `card`, `qr`, `bonus`, `deposit` или `reservation`. Для cash/card/QR обязателен `{paymentAccountId}`: наличные принимаются только в POS-кассу, карта — на банковский/электронный счёт, QR — на электронный. ID и название счёта фиксируются в исходной строке `payments`, а точный повтор включает счёт. Для бонусного тендера передаются `{method:"bonus",amount:<целое число>,idempotencyKey:<строка 8–120 символов>}`; один бонус равен одному рублю в этой временной локальной политике. Для денежного счёта передаются `{method:"deposit",amount:<положительная сумма>,idempotencyKey:<строка 8–120 символов>}`. Оба списания требуют привязанного гостя, не могут превысить баланс/долг и атомарно создают отдельный тендер и отрицательное движение журнала. Зачёт предоплаты передаётся как `{method:"reservation",receiptId,amount,idempotencyKey}` и не создаёт повторного денежного поступления. Повтор с тем же ключом и телом возвращает исходный платёж; тот же ключ с другим телом отвечает `409 idempotency_key_reused`. Ответ и GET содержат актуальный `guestAccount`; внутренние списания бонуса, депозита и предоплаты не относятся к денежным счетам. При полном закрытии заказа обработчик атомарно начисляет целое число бонусов по `bonus_percent` активной группы гостя. `POST /api/orders/:id/close` также требует `paymentAccountId`, если закрывает остаток cash/card/QR. База начисления — стоимость товаров после скидки, но до доплаты до VIP-минимума; из базы исключены потраченные при оплате бонусы, но не денежный счёт; дробные бонусы округляются вниз. Частичная оплата начисление не запускает; `GET /api/orders/:id/payments` возвращает сохранённый снимок условий начисления.
- `POST /api/finance/orders/:orderId/refunds` — только PostgreSQL и право `finance`; запрос `{amount,reason,idempotencyKey,allocations:[{sourcePaymentId,amount,payoutMethod,paymentAccountId}],items?:[{orderItemId,quantity}],noItemReturn?:boolean}`. `amount` и allocation суммы — положительные RUB decimal не более двух знаков; allocation сумма должна точно совпадать с заголовком. Каждый исходный платёж должен быть cash/card/QR и paid/partially_paid; заказ должен быть закрыт. Каждая выплата требует совместимый `paymentAccountId`: наличный возврат идёт только из POS-кассы открытой смены, карта — с банковского/электронного счёта, QR — с электронного. Счёт сохраняется на каждой строке возврата; точный повтор сравнивает его вместе с остальным телом. Сервер блокирует заказ и исходные платежи, ограничивает накопительный возврат суммой каждого платежа и требует открытую смену для возврата наличными. Выплатный канал может отличаться от исходного. Денежная выплата и возвращаемые товарные количества передаются отдельно. Для новых заказов с immutable pricing snapshot item lines связываются с исходными строками, а накопительные количество/стоимость ограничиваются замороженным net value; `noItemReturn:true` явно фиксирует возврат без товара. Без подтверждённой item lineage событие остаётся `unattributed`. Создаются append-only событие возврата и тендерные/item-строки, аудит пишется атомарно; исходные оплаты, статус и заказ не меняются. Точный повтор ключа с тем же телом возвращает исходную запись; другой payload — `409 idempotency_key_reused`.
- `GET /api/finance/orders/:orderId/refunds` — требует `finance_read` или `finance` и `orders`; для связанного с бронью заказа дополнительно `reservations`. Возвращает immutable возвраты, выплаты по исходным payment ID и выплатному каналу, доступные замороженные строки возврата и их количество/net value. `itemAttributionStatus` различает `complete`, `not_applicable` и `unattributed`; `producerSequence` подтверждает только порядок после 092, а старые 091 события остаются `legacy_unsequenced`. Legacy `payments.status='refunded'` остаётся неизвестным и не реконструируется. Выплата попадает в финансовый payout отчёт по времени события и наличный возврат вычитается из кассы своей смены. Возвращённая стоимость товара пока не сторнирует POS-выручку и не влияет на payroll; гостевые счета и предоплаты брони остаются в своих ledgers.
- `POST /api/reservations` — создаёт бронь; поле `deposit` — требуемая сумма, а не принятое поступление. Новые брони сохраняют `deposit_required=deposit` и `deposit_paid=0`.
- `POST /api/reservations/:id/deposit-receipts` — принимает частичную/полную предоплату `{amount,method:"cash"|"card"|"qr",reason,idempotencyKey}`. Нужны право `reservations`, подтверждённая бронь и открытая смена; сумма ограничена `deposit_required - verified_deposit_paid`. Переплата, отменённая бронь и неразобранный старый `deposit_paid` отклоняются. Квитанция записывает площадку, бронь, смену, сотрудника и время; квитанция, остаток и аудит сохраняются транзакционно. Точный повтор возвращает прежнюю квитанцию, повтор ключа с изменённым телом — `409 idempotency_key_reused`.
- `POST /api/orders` принимает необязательный `reservationId` для начала визита из подтверждённой брони. Пользователь должен иметь права `orders` и `reservations`; бронь, стол и гость проверяются в текущем заведении. Одна бронь может быть связана только с одним заказом. При создании заказа текущая активная группа гостя в этом заведении фиксируется в полях снимка скидки; затем она участвует в общем выборе лучшего предложения вместе с акцией и одобренной ручной скидкой. Снимок берётся при начале визита, а не при создании брони.
- Для связанного с бронью заказа `GET /api/orders/:id/payments` дополнительно требует право `reservations`, поскольку возвращает квитанции и доступные остатки.
- `POST /api/orders/:id/payments` принимает `{amount,method:"reservation",receiptId,idempotencyKey}` для зачёта выбранной квитанции в связанный заказ; требуются права `orders` и `reservations`. Распределение, payment tender и аудит атомарны. Исходная квитанция не переписывается; тендер не добавляет наличность второй раз, а выручка учитывается только как часть закрытого заказа.
- `POST /api/reservations/:id/prepayment-allocations/:allocationId/reversals` принимает `{amount,reason,idempotencyKey}`. Право `reservations`; разрешён полный возврат только пока исходный заказ открыт. Исходный tender сохраняет сумму, отдельная запись сторно помечает его `refunded`, снимает зачёт с заказа и возвращает сумму в доступный остаток квитанции. Денежной выплаты эта операция не создаёт.
- `POST /api/reservations/:id/deposit-receipts/:receiptId/reversals` принимает `{amount,method:"cash"|"card"|"qr",reason,idempotencyKey}`; только владелец или администратор с `finance` и открытой сменой выплаты. Частичный/полный внешний возврат ограничен доступным остатком. Пока квитанция зачтена в активный заказ, сначала требуется сторно каждого её зачёта. Возврат записывается отдельным неизменяемым событием; наличный возврат уменьшает ожидаемую наличность фактической смены выплаты.
- Отмена подтверждённой брони разрешена после сторно всех зачётов и возврата всего доступного остатка по квитанциям. Возврат не проводится автоматически при отмене. Неизменённые квитанции и зачёты сохраняют историю.

Историю не переписываем; суммы без квитанции требуют сверки.

Для сохранения, проверки будущего времени, повторного чтения и определения сегодняшней брони используется один корректный часовой пояс: точки → организации → `Asia/Yekaterinburg`. ## Справочники склада: архив и удаление

- `POST /api/inventory/items` и `PATCH /api/inventory/items/:id` сохраняют старые текстовые поля `department`, `subdepartment`, `category`, `unit`, `purchaseUnit`, `packMultiplier` и `cost`. Новые клиенты передают `categoryId` из `GET /api/product-categories`; API проверяет активную категорию в текущем tenant/цехе и сохраняет legacy `category`-label для совместимости. Старый текстовый payload сопоставляется с FK только при единственном совпадении в tenant и цехе; неоднозначное имя отклоняется, а unmatched legacy-записи остаются с `categoryId: null`.
- Складской ингредиент может передать `tobaccoCatalogItemId`, ссылающийся на активную карточку `/api/tobacco-catalog` текущей организации (venue-scoped карточка дополнительно ограничена текущим заведением). `GET /api/inventory` возвращает связанную карточку в `tobaccoCatalogItem` с брендом, линейкой, вкусом, типом, крепостью и граммами упаковки. Для граммового ингредиента закупочная единица пачки и `packMultiplier` задают массу пачки; стоимость остаётся себестоимостью базовой граммовой единицы. Каталог крепкого алкоголя использует отдельную существующую связь `alcoholCatalogItemId`.
- `PATCH /api/product-categories/:id` сохраняет тот же `categoryId` у связанных складских позиций, обновляя возвращаемый legacy label и их иерархию. Tenant identity всегда берётся из авторизованной сессии; чтение/запись ингредиентов требуют `inventory`/`inventory_read`.

- `GET /api/inventory/departments?status=active|archived|all`, `GET /api/inventory/subdepartments?status=active|archived|all` и `GET /api/product-categories?status=active|archived|all`; без `status` возвращаются только активные записи. Чтение требует `inventory_read`; каждый ответ ограничен текущим заведением.
- `DELETE /api/inventory/departments/:code` и `/api/inventory/subdepartments/:id` — только обратимый архив, требуется `inventory`. `DELETE /api/product-categories/:id` требует `inventory` либо owner-настраиваемую область `inventory_categories`. Эта узкая область разрешает только просмотр, архивацию и восстановление категорий, но не создание/редактирование категорий, товаров или складских операций. Архивируются только записи без текущих ссылок; данные и история не удаляются.
- `POST /api/product-categories/:id/restore` требует `inventory` или `inventory_categories`; остальные restore-маршруты требуют `inventory`. Категория восстанавливается при активном родительском цехе и без конфликта уникальности.
- `POST /api/inventory/permanent-deletions` выполняет окончательное удаление архивной записи только для `owner`; сервер блокирует удаление при наличии подцехов, категорий, позиций или товарных ссылок. Если владелец удалил запись напрямую, ожидающий запрос управляющего закрывается в той же транзакции.
- `POST /api/inventory/deletion-requests` создаёт запрос управляющего на удаление архивной записи; категория требует `inventory` или `inventory_categories`, причём узкая область не позволяет запрашивать удаление цеха/подцеха. `GET /api/inventory/deletion-requests` показывает владельцу ожидающие запросы, управляющему — только собственные. `POST /api/inventory/deletion-requests/:id/approve|reject` доступен только роли `owner`. Подтверждение повторно проверяет ссылки и выполняется в одной транзакции с решением запроса.

## Payroll схемы и сценарный расчёт

- Настройка схем и просмотр их конфигурации доступны только активному пользователю с ролью `owner` в текущей площадке. Сервер получает пользователя и площадку из аутентифицированной сессии, повторно проверяет владельца в PostgreSQL и не доверяет actor/venue полям запроса. При отключённой общей обязательной авторизации эти маршруты всё равно требуют сессию и активную запись владельца. При отсутствии базы возвращается `503`.
- `GET /api/payroll/schemes` возвращает схемы и краткий список версий; `GET /api/payroll/schemes/:schemeId/versions` возвращает версии одной схемы. `GET /api/payroll/versions/:versionId` возвращает конфигурацию версии; `GET /api/payroll/versions/:versionId/revisions` — неизменяемые снимки её правок.
- `POST /api/payroll/schemes` принимает `{name, description?, definition, payoutRiskAcknowledgement}` и создаёт схему с первой черновой версией. `POST /api/payroll/schemes/:schemeId/versions` и `PUT /api/payroll/versions/:versionId` принимают `{definition, payoutRiskAcknowledgement}`. Для каждого сохранения требуется `{confirmed:true, policyCode:"payroll-own-revenue-ceiling-v1"}`; отсутствие отвечает `400 payroll_risk_acknowledgement_required`. Сервер сохраняет actor/time и SHA-256 нормализованной конфигурации в версии и её append-only ревизии. Подтверждение фиксирует понимание риска блокировки, не отменяет лимит выплаты. Активация блокирует строку версии и проверяет соответствие сохранённого подтверждения её текущей конфигурации; несовпадение отвечает `409` с тем же кодом.
- `definition` включает `mode`, `currency`, `effectiveFrom`, необязательный `effectiveTo`, `roleParameters`, `roleAssignments`, `employeeOverrides` и `itemRules`; допустимые режимы: `progressive_daily`, `stable_percent`, `percent_only`, `final_month_threshold`, `personal_target`, `team_fund`, `margin_target`. Суммы задаются целыми копейками, ставки — basis points. Нулевой override задаётся как `mode:"override", value:0`; `inherit` хранит наследование. Персональные и ролевые назначения включают окно действия.
- `personal_target` требует на роли `perShiftCents`, `targetCents`, `baseRateBps`, `bonusRateBps`, `excessRatePolicy` (`replace_base` либо `add_to_base`); каждый параметр можно переопределить с effective window. План сбрасывается по сотруднику каждый день; сценарная база — сумма eligible commissionBaseCents, не подтверждённая личная Finance-net выручка. `replace_base` оплачивает min(B,T) базовой ставкой, max(B−T,0) повышенной; `add_to_base` оплачивает всю B базовой плюс превышение повышенной. Компоненты округляются half-up отдельно (`component_half_up_v1`) и распределяются по строкам методом наибольших остатков. Item replacement исключает строку из плана; item additive сохраняет её в плане и добавляет обычную построчную комиссию. Preview возвращает employee `targetIncentive` и line `targetAllocation`; для пороговых строк `appliedRateBps:null`. Сохранение нового режима требует migration 083; старая схема отвечает `409 payroll_personal_target_schema_required` с rollback. Текущий serializer отвергает этот режим как `payroll_snapshot_incentive_schema_required`, пока не завершён typed snapshot contract; официальное начисление не разрешается.
- `POST /api/payroll/versions/:versionId/preview` принимает `{previewInput}`; `POST /api/payroll/compare` принимает `{versionIds, baselineVersionId, previewInput}`. Это ручные сценарии с нормализованными входными данными, а не чтение POS, официальный расчёт или расчётный run. Ответы явно имеют `official:false`, `persistence:"none"`; они не создают snapshots, `payroll_entries` или `expenses`.
- Изменяющие запросы, аутентифицированные cookie, должны содержать same-origin `Origin` и JSON для запросов с телом; Bearer-аутентификация допускает запрос без Origin. Чужие версии и схемы не раскрываются между площадками. Текущие `/api/payroll/rules` и `/api/payroll/entries` сохраняют существующий отдельный lifecycle и permission `finance`.

### Team fund configuration and preview

- `team_fund` требует `perShiftCents` и объект `teamFund` на роли: `poolId`, `targetCents`, `baseRateBps`, `bonusRateBps`, `excessRatePolicy`, уникальные `departments`, `distributionPolicy`. Для configured_weights нужен целый неотрицательный `teamWeight`, включая explicit zero и effective-dated employee override. Pool параметры не переопределяются персонально: один poolId имеет одну согласованную формулу у всех ролей.
- Fund вычисляется один раз на pool/day по eligible commission bases участников в указанных department IDs; каждый источник учитывается один раз. Item replacement исключён, additive сохраняется в базе и отдельно добавляет построчную комиссию. Формула использует component_half_up_v1 и явные replace_base/add_to_base semantics. Дневной исторический ориентир — versioned owner parameter, не оценка среднего по неполным данным.
- `approved_minutes` распределяет фонд по сумме утверждённых workedMinutes; `configured_weights` распределяет по teamWeight всех активных членов **независимо от выхода в день**. Zero-weight member sales сохраняются в базе; положительный фонд без положительных весов/минут blocked. Полный roster/coverage — сценарное требование, не production attestation.
- Preview содержит separate `teamFundCents` в employee/day и period totals, `day.teamFunds` с формулой/fund/memberIds/sourceLineIds/allocations, `line.teamFundSource` с вкладом автора. Fund recipient payout не является комиссией автора source line. Caps и личный ceiling применяются после распределения; остаток после caps не перераспределяется. Serializer явно rejects typed fund пока official snapshot contract не расширен.
- Migration 085 сохраняет 083 modes/paths и добавляет team mode/weight. Старый schema CHECK отвечает прежним совместимым кодом `409 payroll_personal_target_schema_required` с rollback; UI объясняет обновление схемы для обоих новых режимов. Official run gate остаётся.

### Margin target configuration and preview

- `margin_target` требует role/employee targetCents/baseRateBps/bonusRateBps/excessRatePolicy/perShiftCents и явные `lossPolicy:"offset_daily_losses"`, `itemRuleBasis:"net_revenue"`. Target — дневной ориентир маржи сотрудника; не месячный план и не прибыль заведения после ФОТ/накладных расходов.
- Каждый resolved-margin sales input содержит `costSnapshot:{id,version,currency,costCents}`. ID/version — непустые строки, currency совпадает со схемой, costCents — целая неотрицательная ПОЛНАЯ net-себестоимость нормализованной строки после quantity/refund корректировок. Это caller-supplied scenario evidence; текущая рецептура/цена/отсутствующий cost не подставляются. Missing/invalid/currency mismatched cost явно блокируют даже replacement строку.
- Signed margin = commissionBaseCents − costCents. Убытки всех eligible строк сначала уменьшают дневную положительную маржу; только затем payable=max(sum signed margins,0). Положительные строки получают долю уменьшенной payable margin методом наибольших остатков, затем target/base/excess компоненты; losing lines сохраняют signed evidence и нулевую маржинальную комиссию. Отдельно проверяются signed/positive/loss aggregates на безопасный диапазон, включая взаимное погашение больших сумм.
- Item replacement остаётся процентом от net revenue и исключает строку из margin pool; additive сохраняет строку и добавляет revenue-based комиссию отдельно, даже при отрицательной марже дня. Это явное itemRuleBasis, не автоматическое преобразование исторической ставки в процент маржи.
- Preview возвращает employee `marginIncentive` (signed/payable/loss offsets/formula/policies), line `costSnapshot`, `signedMarginCents`, `marginAllocation` и null scalar appliedRateBps для маржинального pool. UI показывает отдельную себестоимость и отрицательные суммы. Migration086 расширяет только config constraints; old-schema409 совместим с предыдущими режимами. Typed serializer refuses margin до официального source/snapshot контракта.
- JSONB scalar string overrides читаются как уже декодированные pg значения; второй JSON.parse не применяется. Loss/item/excess-policy строки, нулевые numeric overrides и audit digest сохраняются после reload.

## FIX-03.1 — исполнение строк заказа

Контракт: `docs/architecture/FIX_03_1_DISPATCH_CONTRACT.md`; требуется миграция099.

- `POST /api/products`, `PATCH /api/products/:id`: поле `preparationStation: "bar" | "hookah" | null`, независимо от текстовой `category` и legacy `station`. Направление копируется при создании строки заказа; позднее изменение товара не переназначает уже созданную работу.
- Строки ответа заказа дополнены `preparationStation`, `preparationStatus` (`new|queued|in_progress|ready`), `preparationDispatchedAt`, `preparationStartedAt`, `preparationReadyAt`. Старые поля сохраняются.
- `POST /api/orders/:id/dispatch`: `{expectedVenueId,station:"bar"|"hookah",itemIds:[...]}`. Требует orders и открытой смены. Непустой явный список принадлежит выбранному заказу/точке; новые строки становятся queued. Неизвестное направление назначается впервые, в том числе legacy queued/null; другое заданное направление не переопределяется. Повтор тех же IDs не захватывает новые строки. Ответ `{orderId,status,items}` содержит актуальные строки заказа.
- `PATCH /api/orders/:orderId/items/:itemId/preparation`: `{status:"in_progress"|"ready",expectedStatus:"queued"|"in_progress"}`. Требует orders и bar_tasks/hookah_tasks для направления либо tasks_manage. Переход queued→in_progress→ready; повтор результата идемпотентен, конфликт409, чужое направление403, чужой заказ/строка404. Исполнение оплаченного заказа разрешено без повторного открытия смены и не меняет финансовые факты.
- `GET /api/preparation/queue`: `{items:[{id,orderId,tableId,tableName,orderStatus,name,quantity,preparationStation,preparationStatus,preparationDispatchedAt,...}],stations:[...]}`. Только разрешённые направления текущей точки; queued/in_progress, включая финансово closed, исключая cancelled.

Общая готовность активного заказа выводится из готовности строк; добавление новой строки снимает ready, старые готовые работы сохраняются. Legacy endpoint общего ready не должен обходить этот контроль. Изменение количества/удаление отправленной работы отклоняется409. Передача и исполнение не создают оплат, списаний сырья или повторных pricing snapshots.

Для обеих мутаций исполнения `expectedVenueId` необязателен: клиент передаёт зафиксированную точку, несовпадение при наличии поля даёт409. Сервер всегда проверяет фактическую принадлежность заказа/строки независимо от этого поля.

## Table minimum schedule API

`POST /api/floor/tables` and `PATCH /api/floor/tables/:id` accept `minimumOrderStartTime` and `minimumOrderEndTime` in `HH:mm` format. Supply both values or both as `null`; equal or malformed times return `invalid_table_minimum_schedule`. `GET /api/floor` includes both fields. Reservation create/update validates the deposit against the schedule at the reservation's local start time.
# Расширение графика: календарь и планирование

`GET /api/staff/schedule?from=YYYY-MM-DD&to=YYYY-MM-DD` сохраняет прежнее значение `items` (дата начала внутри периода) и добавляет `continuations`: действующие смены, начавшиеся раньше, но пересекающие период. Продолжения показываются в календаре, не прибавляясь к итогам по дате начала. Записи с рабочей функцией дополнительно содержат `functionId` и `functionName`; если квалификацию сотрудника позднее сняли, неизменённую функцию можно сохранить при редактировании другой части смены.

Под `/api/staff/schedule` доступны `/drafts` и `/templates` (GET список, POST создание), `/:id` (GET чтение, PATCH версия). Эти сущности требуют `manage`, ограничены текущим заведением, все изменения требуют UUID `requestKey`. Изменения черновика не пишут `staff_schedules` и не меняют payroll. POST/PATCH действующего графика и copy сохраняют прежнее немедленное управление; это дополнительный процесс планирования, не обязательное согласование всех изменений.

Черновик создаётся с `{name,from,to,userIds,requestKey}` (до 93 дней, 100 сотрудников). DTO: `{id,name,from,to,userIds,timezone,state,version,operations,baseItems,publishedAt,capabilities}`. PATCH принимает полный явный массив `operations` (до 200) и `version`. Операция: `{operation:'create',payload}` либо `{operation:'update'|'cancel',sourceId,sourceVersion,payload?,reason?}`. Пропуск существующей смены не отменяет её. Закрытие — POST `/drafts/:id/discard` с версией и ключом; история сохраняется.

POST `/drafts/:id/range-preview` принимает `{version,from,to,userIds,definition}`, вместо definition — `{templateId,templateVersion}`, либо `{version,from,to,seriesId,seriesVersion}`. Возвращает `operations,conflicts,fingerprint`, ничего не сохраняет. `/range-apply` с теми же параметрами плюс `fingerprint,requestKey` атомарно добавляет предложения в черновик; при конфликте не применяет частичный результат. Повтор серии распознаёт уже опубликованные occurrences и предлагает обновление, а ручные исключения показывает как пропущенные с причиной.

Шаблон: `{name,definition:{pattern,slots},requestKey}`. Pattern: `{type:'weekdays',weekdays:[1..7]}` либо `{type:'cycle',anchorDate,cycleDays,dayOffsets:[0..cycleDays-1]}`. Slot смены: `{kind:'shift',startTime,endTime,endDayOffset:0|1,breakMinutes,note}`; отсутствие: `{kind:'vacation'|'sick'|'day_off'|'other_absence',breakMinutes:0,note}`. Неуказанные дни не становятся выходными. PATCH шаблона требует версию; `archived:true` исключает его из применения, не удаляя историю и не меняя уже составленные планы.

Серия: `{name,userId,functionId,anchorDate,untilDate,recurrence:{pattern,slots,cycleOffset?,slotKeys?},exceptions?,state,reason,requestKey}`; горизонт ограничен 365 днями, каждый слот имеет стабильный ключ. Исключение `skip` пропускает один occurrence; `replace` задаёт альтернативный слот на одной дате. Ручная правка уже опубликованной смены записывается отдельным неизменяемым по смыслу manual override с обязательной причиной. Все occurrences проходят через draft → preview → publish; публикация сохраняет `seriesId/date/key` атомарно, payroll и фактические часы не меняются.

POST `/drafts/:id/publish-preview` с `{version}` возвращает точные операции, конфликты и fingerprint. `/publish` требует `{version,fingerprint,reason?,requestKey}` и отдельного `canPublish`. Владелец имеет его автоматически; admin/manager — только по явной выдаче владельцем через PUT `/grants`. Необязательный `canPublish` сохраняется при прежнем manage и сбрасывается при понижении ниже manage; самовыдача запрещена. Сервер повторно проверяет права, исходное состояние, сотрудников, часовой пояс и конечные пересечения в транзакции. Перестановки проверяются по конечному состоянию, не промежуточным строкам. После публикации черновик неизменяем, live ID обновляемых записей сохранены, история и версия увеличены; утверждённые payroll snapshots не переписываются.

Конфликты версии/базы/предпросмотра возвращают 409, отсутствие прав — 403; чужая сущность — 404. Повтор ключа и того же тела возвращает исходный результат, другое тело с тем же ключом — 409. При изменившейся основе требуется новый черновик, автоматического rebase нет.

## Категории доходов и расходов

- `GET /api/finance/categories?q=...&includeArchived=true&venueId=<uuid>` — возвращает категории и раздельные количества связанных записей за всё время: расходные строки, POS-заказы с доходной allocation, обязательства, регулярные правила, начисления зарплаты, закупочные документы и документы прочего дохода. Все статусы источников входят в счётчики. Это не количество уникальных хозяйственных операций и не суммы: платёж из `expenses` может быть связан с обязательством, закупкой или начислением зарплаты. Поле `operationCount` оставлено для совместимости и учитывает только расходы плюс POS-продажи; для отображения используйте отдельные поля. `payrollAccrualCount` равно `null`, когда у читателя нет права `finance` на выбранной точке. Доступны `finance_read` и `finance`, кроме операционных сотрудников; просмотр архива требует `finance`.

## Ручные финансовые обязательства

- `GET /api/finance/payables?from=YYYY-MM-DD&to=YYYY-MM-DD&status=draft|approved|cancelled&includeOverdue=true` — `items` остаётся обязательствами со сроком в выбранном интервале. Опциональный `overdue` — отдельная справка: просроченные утверждённые документы с положительным остатком, `asOfDate` по часовому поясу заведения, только вне выбранного интервала; `totalCount` и `totalBalanceDue` включают также просрочку внутри `items`. Черновики, отменённые и полностью оплаченные документы не считаются просроченными. Доступно `finance_read` и `finance`, кроме операционных сотрудников.
- `POST /api/finance/payables` — создаёт черновик с `categoryId`, `title`, `counterpartyName`, `basis`, `periodFrom`, `periodTo`, `dueDate`, `lines:[{description,amount}]` и обязательным `idempotencyKey` (8–120 символов). Сумма равна строкам. Черновик не создаёт денежное движение. Точный повтор возвращает сохранённые ID/ответ (`200`); тот же ключ с другими нормализованными данными даёт `409 finance_create_idempotency_conflict`. Потеря подтверждения COMMIT даёт `503 finance_create_result_unknown`; повторите запрос с прежними ключом и телом.
- `PATCH /api/finance/payables/:id` — редактирует только черновик. `PATCH` с `{status:"approved"}` подтверждает его после проверки категории и суммы строк; `{status:"cancelled"}` отменяет черновик или подтверждённое обязательство без оплат. Подтверждённые данные неизменяемы; отмена документа с оплатами запрещена.
- `GET /api/finance/accounts` — активные счета точки для оплаты; `{active:false}` возвращает также архивные. Для `finance_read`/`finance`; записи всегда ограничены текущим заведением. Ответ содержит `id`, `name`, `kind`, `allowedPaymentMethods`, `active`.
- `POST /api/finance/accounts` — `finance` создаёт кассу вне смены (`kind:cash`), банковский (`bank`) либо электронный/эквайринговый счёт (`electronic`). Методы можно сузить внутри разрешённого набора типа: cash — `cash`; bank — `bank_transfer|card|other`; electronic — `card|other`. QR пока не поддерживается для payable.
- `PATCH /api/finance/accounts/:id` — меняет название и/или архивный статус; использованный счёт нельзя удалить, изменить его code/kind/методы или повторно активировать. Каталог содержит venue-дефолт `Основная касса` (`pos_cashbox`), которую нельзя архивировать.
- `GET/POST /api/finance/funding-documents` — список и создание документов вклада владельца (`owner_contribution`) либо займа (`loan`); чтение — `finance_read`/`finance`, изменение — `finance`. Создание требует UUID `idempotencyKey`, имя контрагента и основание; для займа задаётся principal limit. `PATCH /api/finance/funding-documents/:id` изменяет только draft, `POST /:id/cancel` отменяет только draft.
- `GET /api/finance/funding-documents/:id` возвращает историю документа. `POST /api/finance/funding-documents/:id/events` записывает append-only событие `owner_contribution_received`, `loan_principal_received` или `loan_principal_repaid` с суммой, датой, активным счётом, совместимым способом, заметкой и UUID `idempotencyKey`. Погашение не может превысить полученный principal; повторный ключ с тем же payload возвращает исходный факт, с другим — 409. Проведённый факт не редактируется и не удаляется.
- `GET /api/finance/balance-event-accounts` — активные финансовые счета, доступные для перевода и начальной позиции. Доступ — `finance_read`/`finance`, кроме операционных сотрудников.
- `GET /api/finance/account-transfers?from=YYYY-MM-DD&to=YYYY-MM-DD&accountId=<uuid>` — до 500 переводов с признаком `possiblyTruncated`. `POST /api/finance/account-transfers` принимает `fromAccountId`, `toAccountId`, положительную `amount`, `transferDate`, обязательную причину `note` и UUID `idempotencyKey`. Перевод атомарно создаёт debit/credit, сохраняет снимки имён счетов, не создаёт P&L или внешний cash flow. Одинаковый повтор возвращает исходный перевод; повтор ключа с другим телом — 409. Если участвует POS-касса, разрешены только местная текущая дата и единственная открытая смена; POS-нога входит в ожидаемую наличность и снимок закрытия. `GET /api/finance/account-transfers/:id` возвращает обе ноги; `POST /:id/reverse` принимает положительную сумму (включая частичное сторно), дату, причину и UUID ключа. Сторно — новый встречный перевод с ссылкой на исходный, ограниченный непогашенным остатком.
- `GET /api/finance/opening-balances` — подтверждённые позиции счетов с историей корректировок. `POST /api/finance/opening-balances` принимает `financeAccountId`, signed `amount` (отрицательная сумма и ноль допустимы), `effectiveDate`, `evidenceReference`, `basis` и UUID `idempotencyKey`. На один счёт допускается одна исходная позиция; исправление выполняется append-only событием. Открывающий остаток фиксирует позицию на начало местного дня и не является поступлением, расходом либо текущим сверенным балансом. POS-касса запрещена: её начальная наличность фиксируется в параметрах открытия смены. `GET /:id` возвращает исходное подтверждение и корректировки; `POST /:id/adjustments` принимает ненулевой `amountDelta`, дату не раньше даты позиции, причину, документ и UUID ключа.
- `GET /api/finance/unified-report` и 15-минутные снимки включают источники `internal_transfer`, `opening_balance`, `opening_adjustment`. Переводы выводятся двумя знаковыми строками по счетам с нулевым суммарным внешним движением. Начальная позиция берётся на дату окончания отчёта и показана справочно, отдельно от денежных итогов. Корректировки позиции не считаются денежными движениями. Полный остаток счёта остаётся `incomplete`, пока не доказано покрытие остальных денежных журналов.
- Для операций через POS cashbox разрешены только наличные за текущую локальную дату при одной открытой смене; событие связано с этой сменой и включается в расчёт expected cash и неизменяемый close ledger. Другие счета смену не меняют. Эти события отражаются отдельно в `GET /api/finance/unified-report` (`financingEvents`, `source=funding`) как внешний cash flow; P&L, категории и зарплатные итоги не меняются. Это не полный остаток счёта.
- `GET /api/expenses?from=YYYY-MM-DD&to=YYYY-MM-DD` — журнал проведённых расходов. Даты должны быть реальными ISO-днями и `from <= to`; иначе `400 invalid_expense_date_range`. `limit`/`offset` управляют постраничным чтением.
- `POST /api/expenses` — создаёт проведённый расход `manual|other` только с `categoryId` (или названием legacy-категории), суммой до копейки, `expenseDate`, `paymentAccountId`, `paymentMethod` и UUID `idempotencyKey`; допускает `description` и `documentUrl`. Категория и счёт проверяются внутри текущего venue. Один `expenses` event используется и для cash flow, и для P&L; повторы сверяют полный payload и возвращают исходный event, отличие под тем же ключом даёт 409. POS-касса разрешает наличные только за текущую дату точки и блокирует открытую смену в той же транзакции, что и закрытие; прочие счета не меняют POS-наличность. Legacy расходы остаются без счёта и видны как unknown. Источники purchase/payroll не принимаются этим маршрутом.
- `GET /api/finance/payables/:id/payments` — фактические выплаты из существующего `expenses`, включая снимок счёта, смену и явную отметку `unknown_legacy` для старых событий без установленного счёта.
- `POST /api/finance/payables/:id/payments` — принимает `amount`, `paymentDate`, `paymentMethod`, обязательный `paymentAccountId`, `idempotencyKey`, необязательные `documentUrl` и `description`. Только подтверждённое обязательство; сумма ограничена остатком. Создаёт ровно одну запись `expenses` и одну связь с обязательством в транзакции. POS-касса допускает только наличные за venue-local текущую дату и требует открытую смену; банковский и внешний наличный счёт со сменой не связываются. Запись расхода входит в ожидаемую кассу и снимок закрытия только для POS-кассы. Повтор ключа идемпотентен только при совпадении обязательства, суммы, даты, способа оплаты, счёта, вложения и описания (с учётом значения описания по умолчанию); любое отличие даёт конфликт. Повтор ранее созданного legacy события без `paymentAccountId` доступен только как сверка точного повтора и не создаёт новых событий.
- `GET /api/finance/purchase-payables/:id/payments` — выплаты по проведённой закупочной накладной с датой, способом, снимком имени счёта, `shiftId`, вложением и пометкой `unknown_legacy` для старых оплат без счёта; доступно `finance`/`finance_read`, кроме операционных сотрудников.
- `POST /api/finance/purchase-payables/:id/payments` — принимает сумму, дату, способ (`cash|card|bank_transfer|other`), обязательный `paymentAccountId`, ключ идемпотентности и необязательный документ. Только проведённая накладная; общая сумма оплат ограничена закупочной стоимостью. Записывает единственное денежное событие в `expenses` (`source='purchase'`) и сохраняет снимок названия счёта. POS-касса принимает только наличные за сегодняшнюю локальную дату точки при одной открытой смене; её блокировка сериализована с закрытием. Банковский и внешний денежный счёт не меняют кассу и не получают `shiftId`. Повтор с тем же ключом требует совпадения накладной, суммы, даты, способа, счёта и вложения; точный повтор возвращает исходную оплату даже после закрытия смены, другой счёт или payload дают конфликт. Исторические оплаты не получают выдуманную атрибуцию. Оплата и стоимость прихода остаются раздельными срезами и не суммируются как два расхода.
- `GET/POST /api/finance/recurring-rules` — просмотр и создание месячных правил с начальной версией суммы и строк. `POST` требует `idempotencyKey` (8–120 символов) и принимает необязательное `endsOn` как включительную дату окончания договора; `null` означает бессрочное правило. Точный повтор возвращает сохранённый ID/ответ (`200`); тот же ключ с изменёнными данными даёт `409 finance_create_idempotency_conflict`. Потеря подтверждения COMMIT даёт `503 finance_create_result_unknown`; повторите запрос с прежними ключом и телом. Окончание раньше `startsOn` и некорректная дата отклоняются. Точные даты начала и включительного окончания договора задают период услуги. По умолчанию partialMonthPolicy=full_months_only: первый и последний неполные месяцы пропускаются. Явный выбор calendar_days рассчитывает каждую строку месячной ставки пропорционально включительным дням услуги / фактическим дням месяца с HALF_UP до копейки; итог равен сумме округлённых строк. Начальная версия ставки действует с первого числа месяца начала договора. Срок оплаты — договорный день, ограниченный последним днём месяца, но не раньше начала услуги; срок может быть после окончания услуги. Предпросмотр обязателен для генерации calendar_days. Создаются только черновики. Исходный prorationSnapshot сохраняет дни, базовую ставку, строки и результат; он не меняется при ручном уточнении черновика. Для переменной суммы подтверждается фактическая сумма периода, повторного пропорционального расчёта нет. Политика закрепляется при создании правила; изменение срока или ставки не переписывает созданные документы.
- `GET /api/finance/recurring-rules/:id/end-date-preview?endsOn=YYYY-MM-DD` (пустое значение — бессрочно) — показывает за ближайшие 12 месяцев, какие полные периоды станут доступны/недоступны для генерации, и уже созданные документы, чья доступность изменится, с суммой, оплатами и остатком. Ничего не меняет; `impactToken` подтверждает, что правило, тариф и затронутые документы не изменились после просмотра.
- `PATCH /api/finance/recurring-rules/:id` — `{action:"set_end_date",endsOn,impactToken}` меняет только границу будущей генерации. Сервер блокирует правило и затронутые документы, перепроверяет preview и отвечает `409 finance_recurring_preview_stale`, если состояние изменилось. Созданные обязательства, оплаты и признания не редактируются и не отменяются. Без `action` принимается прежний контракт паузы, возобновления или завершения: возобновление требует активную статью расходов; завершение доступно и для правила с архивной статьёй и прекращает любую будущую генерацию, сохраняя уже созданные обязательства. Завершённое правило нельзя возобновить или изменить; для возврата к регулярным платежам создайте новое правило.
- `GET /api/finance/recurring-rules/:id/versions` — полная неизменяемая история ставок с ID/номером версии, датой действия, суммой, строками, признаком переменной суммы, автором и временем. Обязательство возвращает `recurringVersionId` и `recurringVersionNumber`, чтобы связь с исторической ставкой оставалась проверяемой.
- `POST /api/finance/recurring-rules/:id/versions/preview` — строит прогноз по полному кандидату `{effectiveFrom,amount,lines,variableAmount}` на согласованном снимке правила, версий, будущих обязательств, строк и оплат. Возвращает `previewToken`; ничего не сохраняет.
- `POST /api/finance/recurring-rules/:id/versions` — добавляет неизменяемую будущую версию только при совпадении `previewToken`. В теле обязательны `idempotencyKey` (8–120 символов) и данные того же кандидата, что были просмотрены. Под блокировками правило и существующие обязательства перечитываются; изменившийся снимок даёт `409 finance_recurring_preview_stale` без записи. Точный повтор возвращает сохранённый ответ и ID версии; изменённое тело с тем же ключом даёт `409 finance_create_idempotency_conflict`. Потеря подтверждения COMMIT даёт `503 finance_create_result_unknown`; повторите прежнее тело и ключ. Версия применяется только к полным новым периодам в сроке правила; ранее созданные документы не переписываются.
- Статус «Пауза» блокирует обычную генерацию. Возобновление снова допускает штатные будущие месяцы, но не создаёт пропуски автоматически. После возобновления пользователь может явно выбрать полные пропущенные месяцы через предпросмотр и подтверждение; намеренно приостановленные месяцы нужно исключить из выбранного списка, поскольку история интервалов паузы не хранится. Восстановление создаёт только отсутствующие черновики; оплата и признание расхода не запускаются.
- `GET /api/finance/recurring-rules/:id/generate-preview?from=YYYY-MM&to=YYYY-MM` — read-only предпросмотр каждого полного месяца: ставка/строки по действовавшей версии, существующий документ, пропуск вне срока/без версии и черновик-кандидат. Диапазон ограничен 24 месяцами; предпросмотр ничего не записывает и возвращает `previewToken` для защиты от изменений между просмотром и подтверждением.
- `POST /api/finance/recurring-rules/:id/generate` с `{from:"YYYY-MM",to:"YYYY-MM",previewToken,idempotencyKey}` подтверждает предпросмотр и создаёт только отсутствующие черновики, без оплаты и признания расхода. Перед записью сервер блокирует правило, проверяет прежний токен и пропускает периоды, для которых документ уже создан; устаревший снимок возвращает `409 finance_generation_preview_stale`. Точный повтор с тем же ключом и телом возвращает исходный ответ; другой payload под тем же ключом даёт `409 finance_create_idempotency_conflict`, потеря подтверждения COMMIT — `503 finance_create_result_unknown` с требованием повторить исходный ключ и тело. Совместимый вызов без preview-полей остаётся доступен для старых клиентов.

Если выбранная версия правила помечена `variableAmount`, новый черновик нельзя утвердить обычным запросом. UI показывает строки и итог и отправляет явное подтверждение текущего снимка (`confirmVariableAmount`, `expectedTotalAmount`, `expectedLines`); сервер под блокировкой сверяет снимок с сохранённым черновиком. Несовпадение требует обновить список и сверить сумму заново. Утверждение атомарно фиксирует `variableAmountConfirmedAt` и `variableAmountConfirmedBy`; PostgreSQL также блокирует проведение без этих полей. Изменение уже созданного черновика не считается подтверждением.

Все новые записи изолированы по venue из сессии; роли записи требуют `finance`. В этой версии отчёт по обязательствам и фактическим выплатам намеренно не суммирует суммы обязательства как начисленную прибыль; для manual обязательств cash отражается по дате связанного `expenses`.

## Классификация POS-выручки

- `GET /api/finance/income-category-mappings` — список эффективных соответствий и исходных категорий активных POS-товаров и закрытых POS snapshots, с монотонной revision для каждого источника/месяца.
- `POST /api/finance/income-category-mappings` принимает `{sourceKey,categoryId,effectiveFrom:"YYYY-MM-01",expectedMappingId}`. Источник должен быть активной категорией POS-товара, иметь историю в закрытых POS allocations или быть `@minimum-adjustment`; поэтому новую категорию можно назначить до первой продажи. Соответствие применяется с текущего или будущего месяца только к новым закрытиям. Повтор текущего значения идемпотентен; другая статья создаёт append-only исправление с `supersedesMappingId` и новой revision. `expectedMappingId` защищает от затёртого конкурентного исправления; устаревшая версия возвращает `409 finance_income_mapping_changed_retry`. Закрытые чеки сохраняют прежние snapshots.
- `GET /api/finance/income-category-report?from=YYYY-MM-DD&to=YYYY-MM-DD&venueId=<uuid>` — признанные POS-суммы по дате закрытия в локальном часовом поясе точки, суммы без распределения, legacy чеки без canonical snapshot и чеки с ценовым snapshot, но без финансового snapshot классификации. `venueId` необязателен для совместимости и по умолчанию равен активной точке сессии; переданные целевые заведения сервер проверяет по текущему членству и эффективному праву `finance`/`finance_read`. Ответ возвращает выбранный контекст в `venue` и не переключает активное заведение сессии. Последние чеки не распределяются задним числом автоматически; количество и сумма явно возвращаются в `coverage.pricedWithoutCategorySnapshot*`. `refundItemValues` раскрывает стоимость возвращённых строк отдельно; это не бухгалтерское сторно и не вычет из POS-выручки. Для документного раскрытия агрегата клиент передаёт в `/api/finance/unified-report` тот же период, `source=pos`, `venueId` и ID статьи. Сводки выдаются по одному заведению: одинаковые ID статей разных заведений не суммируются.

Snapshot создаётся в транзакции закрытия чека из неизменяемой версии цены. Основа признания — закрытый чек, а не дата поступления оплаты. Старые чеки не связываются по названию меню автоматически; для них отчёт показывает покрытие legacy/unclassified. Права чтения — `finance_read`/`finance`, изменения соответствий — только `finance`.

## Источники финансового отчёта

Все SQL-чтения одного `/api/finance/unified-report` выполняются в общей транзакции PostgreSQL `REPEATABLE READ READ ONLY`. Секции, coverage, название и часовой пояс заведения относятся к одному согласованному снимку; целевое заведение и права на него проверяются до чтений отчёта. При ошибке ответ не содержит частичный отчёт.

- `GET /api/finance/unified-report?from=YYYY-MM-DD&to=YYYY-MM-DD&source=...&categoryId=...` возвращает отдельные массивы POS, денежных операций, признаний и корректировок (состав зависит от фильтра источника). `source=refund` возвращает отдельно `refundTenders` (фактические денежные выплаты) и `posRefundItems` (возвращённые товары по замороженным строкам, категориям и sequence lineage); в каждой строке `payoutAmount` и `returnedItemValueMinor` остаются разными величинами, а tender allocations остаются в `refundTenders`. Этот второй массив — read-only сверочная детализация, не денежный расход и не сторно выручки; неизвестная атрибуция возвращает null стоимости, не ноль. В деталях нет seller/guest PII или source-payment IDs, а права на существующий order endpoint не расширяются. POS allocation включает товар, source key/station, статью и сумму, чтобы расшифровать выручку до строки заказа. Для POS можно передать `unmappedOnly=true` (без `categoryId`), чтобы получить суммы только allocation без category ID; разделы ограничены 500 строками и coverage сообщает о возможном усечении. Фильтр категории не классифицирует и не возвращает `refundTenders`; он фильтрует `posRefundItems` по замороженной статье строки, возвращает только соответствующую стоимость/строки и оставляет `payoutAmount:null`, поскольку выплату нельзя распределить по статье.
- Для отчётного экрана используется `POST /api/finance/unified-report/snapshots` с теми же фильтрами в JSON body и UUID `Idempotency-Key`. Сервер сохраняет один repeatable-read результат на 15 минут; ответ содержит первую страницу до 500 строк каждой секции, полные frozen totals/coverage и `nextCursorBySection`. Следующие страницы читаются через `GET /api/finance/unified-report/snapshots/{snapshotId}/sections/{section}?venueId=...&cursor=...`. Тот же ключ и тот же фильтр возвращают исходный снимок; другой фильтр с ключом возвращает 409. Снимок свыше 50 000 строк или 32 MiB отклоняется с 413, истёкший — с 410. Доступ к целевому заведению и payroll permission проверяются заново при каждой странице; payroll-bearing cash outflows и связанные account coverage требуют target-venue `finance`. Прямой GET остаётся совместимым legacy endpoint с лимитом 500 строк на секцию и `possiblyTruncatedSections`.
- Для общего отчёта и POS-среза `coverage.posIncomeClassification` независимо от фильтра статьи показывает количество и сумму закрытых чеков без финансового category snapshot и частично распределённых чеков со статусом `unmapped`; priced legacy чеки раскрываются по отдельным заказам в `legacyPos`. Старые данные не распределяются автоматически по названиям.
- Даты отчёта локальны для заведения, а основа разная по источнику: POS — закрытие, денежные события — время события, обязательства — срок оплаты, приход — проведение; зарплата распределяется пропорционально календарным дням периода и показывается отдельно от связанного expense.
- Ответ включает `venue: {id,name,timeZone}`. Без `venueId` используется активное заведение сессии; с `venueId` сервер повторно разрешает эффективные права для этого заведения, учитывая его system-role ceiling и назначенную там custom role. `GET /api/finance/report-venues` возвращает только активные заведения организации, где у пользователя есть `finance_read` или `finance`; право `finance` на выбранной точке отдельно требуется для зарплатных сведений. Указание другого ID не меняет активную сессию. `GET /api/finance/categories?venueId=...` применяет ту же проверку, чтобы фильтр статей соответствовал выбранной точке. Даты рассчитываются по местному часовому поясу каждого выбранного заведения; источники и суммы остаются раздельными, сетевой итог не суммируется.
- Каждый объект несёт исходный ID для drilldown. Оплаты поставок и зарплаты остаются денежными расходами из `expenses`, но не добавляются второй раз к закупочной стоимости или начислению зарплаты. Стоимость проведённого прихода — закупочное приобретение, не расход P&L. Возвратные tender-события — денежный отток; признание возврата в P&L не подключено.
- `finance_read` не получает персональные начисления/выплаты зарплаты; запрос с `source=payroll` или `source=payroll_accrual` требует `finance`. Исторические POS без pricing snapshot и записи без надёжной категории остаются явной неполнотой, без подбора связи по названию.


## Статьи зарплатных начислений и закупочных документов

`POST /api/payroll/entries` принимает необязательный `financeCategoryId` (UUID расходной активной статьи текущей точки или `null`). При пересчёте черновика отсутствие поля сохраняет прежнюю статью; `null` очищает её. GET и mutation DTO содержат `financeCategoryId`, `financeCategoryNameSnapshot`. Утверждение проверяет активность/вид статьи; после утверждения снимок неизменяем. Выплата использует этот снимок в единственном payroll expense, включая случай позднего архива статьи.

`POST/PATCH /api/inventory/purchase-documents` принимает такое же поле. Права `inventory` прежние; присутствие поля дополнительно требует `finance`, включая явный `null`. При пропущенном поле складской редактор сохраняет прежнюю классификацию. Проведение фиксирует снимок, частичные оплаты наследуют его. Статья описывает назначение закупки, не добавляет её стоимость к P&L. GET/list документов возвращают оба поля. Ошибки категории возвращаются без записи документа; исторические NULL не заполняются по названию.

`GET /api/finance/unified-report` фильтрует payroll accrual и purchase receipt по сохранённому ID статьи и возвращает `categoryId`/`categoryName`. Старые NULL не совпадают с конкретной выбранной статьёй. `GET /api/finance/categories` отдельно возвращает `payrollAccrualCount` (null без права finance) и `purchaseDocumentCount`; эти числа не прибавляются к денежным операциям или денежному итогу.

## Прочие бизнес-доходы вне POS

- `GET /api/finance/other-income?from=&to=&categoryId=&status=&q=` — список документов и сумм фактических поступлений/остатка; даты фильтруются по дате признания. `GET /api/finance/other-income/:id` возвращает документ и историю поступлений.
- `POST /api/finance/other-income` создаёт черновик: `{categoryId,title,counterpartyName,basis,documentReference,recognitionDate,totalAmount,idempotencyKey}`. Ключ обязателен; повтор того же ключа и тела возвращает исходный документ, другой payload с тем же ключом — `409 idempotency_key_reused`.
- `PATCH /api/finance/other-income/:id` изменяет только черновик. `POST /api/finance/other-income/:id/post` проводит его; доход признаётся по `recognitionDate`, сумма и статья фиксируются. `POST /api/finance/other-income/:id/cancel` отменяет только черновик.
- `POST /api/finance/other-income/:id/receipts` принимает `{amount,receiptDate,paymentMethod,paymentAccountId,note,idempotencyKey}` для проведённого документа. Методы: `cash`, `card`, `qr`, `bank_transfer`, `other`. Частичная оплата поддерживается; сумма не может превысить остаток документа. События append-only и защищены блокировкой документа и уникальным ключом в пределах заведения. Для обоих событий счёт обязателен; способ оплаты должен быть разрешён выбранным счётом. POS cashbox с наличным способом принимает событие только за текущую локальную дату и при открытой смене: поступление увеличивает ожидаемую кассу, возврат уменьшает её, оба попадают в снимок закрытия один раз. Внешняя наличность, карта, QR и перевод со сменой не связываются. Точный повтор возвращает результат даже после закрытия смены; тот же ключ с другим счётом конфликтует. Исторические события без счёта остаются unknown.
- `POST /api/finance/other-income/:id/corrections` принимает `{amount,correctionDate,reason,documentReference?,idempotencyKey}` и добавляет уменьшение признанного дохода датой корректировки. Накопленное сторно не может превысить исходную сумму документа.
- `POST /api/finance/other-income/:id/receipts/:receiptId/refunds` принимает `{amount,refundDate,payoutMethod,paymentAccountId,reason,idempotencyKey}` и возвращает деньги только в пределах указанной квитанции. Это денежный отток, не сторно признания; POS-наличный возврат через cashbox связан с открытой сменой, другие источники — нет.
- Интерфейс сначала сохраняет черновик, затем позволяет изменить его и отдельным подтверждением провести. Проведение влияет на признанный доход; приём денег записывается отдельно. Денежные поступления по банковскому переводу, наличным, карте и QR отмечаются как cash-equivalent.
- Запись и проведение/поступление требуют `finance`; чтение доступно `finance_read` и `finance`. Заведение берётся из сессии. Статья должна быть активной категорией `income` при создании и проведении; после проведения название статьи и сумма неизменяемы. Архив не разрывает историю.

Это только бизнес-доход. Взнос владельца, заём, перевод, депозит/аванс или предоплата требуют отдельных балансовых/обязательственных моделей и здесь не создаются. Проведённое признание и квитанция неизменяемы: ошибку признания исправляют отдельным уменьшением, а фактически выплаченные деньги — возвратом в пределах конкретной квитанции. Эти события имеют собственные даты, причины и автора; корректировка меняет только доход, возврат только денежное движение. Возврат не сверяется с кассой/сменой и сам по себе не исправляет признание. При расхождении полученных денег и чистого признания нужна отдельная финансовая сверка.

`GET /api/finance/unified-report` отдельно возвращает `otherIncomeRecognition` по дате признания, `otherIncomeAdjustments` по дате сторно, `otherIncomeReceipts` по фактической дате получения и `otherIncomeRefunds` по дате выплаты (источники `other_income`, `other_income_recognition`, `other_income_receipt`, `other_income_adjustment`, `other_income_refund`). Корректировка меняет только recognition; возврат — только cash. Срезы не складываются между собой или с POS-признанием/оплатами.

### Признание договорных расходов

- `GET /api/finance/payables/:id/recognitions` возвращает исходное признание и append-only сторно. `GET /api/finance/payables` содержит `recognitionStatus`, `recognitionId`, исходную/чистую сумму признания и независимый `paymentStatus`.
- `POST /api/finance/payables/:id/recognitions` принимает `{recognitionDate,documentReference?,idempotencyKey}` только для `approved`. Сервер берёт всю сумму, статью, контрагента, основание и период из замороженного документа; частичное признание не поддерживается. Первый запрос отвечает `201`, точный повтор ключа/тела — `200`; иной payload/уже существующее recognition — `409`.
- `POST /api/finance/payables/:id/recognitions/:recognitionId/reversals` принимает `{amount,reversalDate,reason,documentReference?,idempotencyKey}`. Только `finance`; сумма ограничена чистым признанием. Ответ `201` для нового события и `200` при точном replay. Сторно не меняет долг или cash.
- Связанные payable payments остаются `expenses` и отражаются только как cash outflow. Analytics P&L исключает все linked payable expenses и использует gross recognition и отрицательные reversal по их датам. Approved payable без recognition по пересечению service period возвращается в recognition coverage; при наличии пробела итоговые расходы/прибыль явно помечаются неполными.
- Отмена approved payable с положительным чистым признанием запрещена до полного reversal; оплаченный payable по-прежнему нельзя отменить. Старые записи не backfill-ятся.
- `GET /api/finance/unified-report` добавляет `obligationRecognitions` и `obligationRecognitionAdjustments`, источники `obligation_recognition` и `obligation_adjustment`, а также `coverage.payableRecognition`. Категория фильтруется по snapshot ID; recognition date и reversal date — самостоятельные даты.

## Черновики ручных расходов

- `GET /api/finance/expense-drafts?status=draft|posted|cancelled|all&limit=100` — список черновиков и их состояния в текущем заведении; доступно `finance`/`finance_read`. Черновик не входит в кассу, P&L и журнал `/api/expenses`.
- `POST /api/finance/expense-drafts` — сохраняет черновик категории, суммы, даты, отдельного контрагента, описания, документа, счёта и способа оплаты. Требует `finance`, активную расходную статью, активный счёт и UUID `idempotencyKey`.
- `PATCH /api/finance/expense-drafts/:id` — изменяет только черновик с `expectedVersion`; устаревшая версия получает 409. Проведённый или отменённый черновик неизменяем.
- `POST /api/finance/expense-drafts/:id/post` — `{expectedVersion,idempotencyKey}` атомарно перепроверяет статью/счёт/метод/смену и создаёт одну запись `expenses` со ссылкой на черновик. Точный повтор возвращает тот же расход.
- `POST /api/finance/expense-drafts/:id/cancel` — `{expectedVersion}` отменяет черновик без денежной записи.

## Коррекция проведённого ручного расхода

- `GET /api/finance/expenses/:id` — возвращает исходную запись, эффективные реквизиты и append-only историю коррекций. Доступно `finance`/`finance_read`; operational roles отклоняются. В `original` сумма и статья из исходной выплаты, в `effective` — последнее подтверждённое состояние.
- `POST /api/finance/expenses/:id/corrections` — требует `finance` и тело `{expectedVersion,changes,reason,idempotencyKey}`. В `changes` допускаются только `amount` (положительная сумма с точностью до копейки) и/или `categoryId` (активная статья расходов того же заведения). Дата, счёт, метод, контрагент и смена сохраняются исходными. Поддерживаются только несвязанные `manual|other` расходы; закупки, зарплата и payable-linked расходы исправляются в своих регистрах.
- Успех создаёт одно неизменяемое событие с полными снимками до/после, ключом идемпотентности и знаковой дельтой `B−A`. Точный повтор того же ключа и payload возвращает сохранённый ответ; другой payload с тем же ключом или устаревший `expectedVersion` получает 409. Если результат COMMIT неизвестен, API возвращает 503 с тем же ключом для безопасного повтора.
- Коррекция меняет P&L/статью на исходную дату и показывается отдельной строкой отчёта. Она не меняет фактический cash flow, ожидаемую наличность или закрытый снимок смены и не создаёт вторую выплату. Фактический возврат поставщика — отдельный будущий денежный приход.
- `GET /api/finance/expenses/:id/refunds` — история фактических возвратов точного несвязанного `manual|other` расхода, исходная сумма, возвращено и доступно. Доступно `finance`/`finance_read`; operational roles отклоняются.
- `POST /api/finance/expenses/:id/refunds` — требует `finance`, тело `{amount,refundDate,paymentMethod,paymentAccountId,documentReference,reason,idempotencyKey}`. Создаёт append-only положительное поступление на выбранный активный счёт; сумма ограничена исходной оплаченной суммой минус предыдущие возвраты, дата — фактический день получения. Точный повтор безопасен, payload с изменением под тем же ключом получает 409. POS cashbox разрешает только наличные за текущую локальную дату при одной открытой смене; поступление добавляется в кассу и снимок закрытия один раз.
- Возврат сохраняет исходную выплату и не является бизнес-доходом. Для несвязанного ручного расхода `pnlEffect=not_calculated`, фильтр категории не применяется и прибыль помечается неполной. Для договорной оплаты сервер выводит payableId из точной связи платежа, возвращает `pnlEffect=separate_payable_recognition`, открывает долг обязательства и применяет фильтр его статьи. Такой возврат ограничен распределением, оставшимся на исходном обязательстве после зачётов; признание/сторно расхода остаётся отдельным действием. В unified report оба вида представлены в `expenseRefunds` по дате фактического получения.
- `POST /api/expenses` остаётся совместимым маршрутом немедленного проведения для старых интеграций; пользовательскую форму переводим на черновик → проведение.


### Зачёты договорных оплат

- `GET /api/finance/payables/:id/offsets`: документ, история обеих сторон и доступные распределения по исходному expenseId; repeatable-read снимок одного ответа. Чтение finance/finance_read, с запретом операционных staff-ролей. Чужое обязательство возвращает 404.
- `POST /api/finance/payables/:id/offsets`: expenseId, destinationPayableId, amount, offsetDate, reason, необязательный documentReference, idempotencyKey. Требуется finance. Сохраняет неденежное распределение; прямой платёж и признание не создаются.
- `POST /api/finance/payables/:sourceId/offsets/:offsetId/reversals`: amount, offsetDate, reason, необязательный documentReference, idempotencyKey. sourceId — исходный отправитель оригинального зачёта; сервер сам меняет стороны и сохраняет исходную оплату. Действуют лимиты сторно и доступного распределения.

Создание возвращает 201, точный повтор 200, изменённый payload с прежним ключом 409. Ключ блокируется до блокировок документов; exact retry доступен после последующей отмены документа. Ответ события содержит ID обеих сторон, expenseId, amount, offsetDate, reason, reversalOfId, idempotencyKey, автора и время. Чтение доступных распределений учитывает цепочки, сторно и денежные возвраты. API и пользовательская форма подключены локально. Unified report поддерживает source=payable_offset, секцию payableOffsets и сохранённые снимки; это неденежные события, отдельные от признания расхода. Browser-приёмка создания, потери ответа/reload, сторно и отображения в снимке прошла.


Для `POST /api/finance/funding-documents/:id/events` поле `createdEventId` возвращается и при создании, и при точном идемпотентном повторе. Интерфейс сверяет этот ID и реквизиты через GET документа перед снятием сохранённой попытки. Явный отказ создания документа разрешает исправление полей; неопределённый результат сохраняет ключ и payload.


### Депозиты гостей и предоплаты в едином отчёте

`GET /api/finance/unified-report` и сохранённые снимки принимают `source=guest_advance`. Секция `guestAdvanceCashEvents` объединяет существующие журналы поступлений депозитов и предоплат брони, внешних возвратов депозитов (cash/card/qr) и возвратов предоплат. `eventId`, `sourceId`, `guestId`, `reservationId` сохраняют происхождение; `eventType` различает четыре вида событий. `amount` положительная, `signedCashFlowAmount` отрицательная для возвратов, `pnlEffect=none`. Итог секции считается по signedCashFlowAmount.

Даты отбираются по created_at в локальном часовом поясе заведения, обе календарные границы включены. Поддержаны поиск по ID/текущему имени/причине и статус posted. `counterpartyNameCurrent` — текущее имя, не исторический снимок. Эти события не имеют статьи: categoryId на них не распространяется, что явно отражено в coverage.guestAdvances.categoryFilterApplied=false. Внутреннее применение депозита/предоплаты к заказу, возврат в кошелёк и legacy поле суммы брони не создают строки денежных событий.

В исходных журналах отсутствует finance_account_id: строки возвращают financeAccountId=null и accountCoverage=not_recorded. coverage.guestAdvances содержит количество и чистую сумму; coverage.cashAccounts указывает неполноту и валовую сумму событий без счёта. Счёт не выводится из способа оплаты или смены. Это детализация движения обязательств, не полный баланс счёта и не прибыль.


### Исходные документы расходных операций

GET /api/expenses дополнительно возвращает payrollEntryId из существующей same-venue связи payroll_entries.expense_id; purchase_document_id сохраняется в прежнем формате. Зарплатные расходы по-прежнему исключены без finance. Эти идентификаторы не дают дополнительных прав.

В списке расходов кнопки «Открыть закупку» и «Открыть начисление» читают существующие GET /api/inventory/purchase-documents/:id и GET /api/payroll/entries/:id. Просмотр показывает текущие данные источника, не меняет финансовые записи. Закупка требует inventory/inventory_read, начисление — finance. Обработка403/404 отделена от временной ошибки; смена контекста во время запроса отменяет показ результата. При отсутствующей старой связи UI сообщает об этом, не угадывая документ. Этот просмотр ограничен текущим заведением списка расходов; multi-venue report navigation не подключена.


`GET /api/finance/source-documents/{purchase|payroll|pos}/:id?venueId=<uuid>` читает источник в явно выбранном авторизованном заведении без переключения сессии. На выбранной точке нужны finance/finance_read и право исходного модуля: inventory/inventory_read для закупки, finance для начисления, orders для чека. Операционные роли исключены.
